## 0. 这份文档解决什么问题

Agent 里每一个"原子扫描能力"（IP 存活、端口、服务、OS、Web、目录、子域名、漏洞、爆破……）都必须同时满足两个使用场景：

1. **CLI 场景**：用户直接执行 `neoAgent scan xxx -t target`，本地单次运行。
2. **Master 编排场景**：Master 集群下发任务，Agent 的 `agentTaskService` 接收后自动执行。

这两条路径**必须走同一份注册表、同一个执行入口**，否则会出现"CLI 能跑，Master 跑不了"（或反过来）的能力不一致问题——这正是本文档写作的直接原因（2026-08-04 修复了 `WebScanner` 未注册到 `RunnerManager`，以及 `dir`/`subdomain`/`vuln` 三个命令是空壳只打印 JSON 不做真实扫描的历史遗留问题）。

**核心铁律：新增一个原子扫描能力，必须同时完成"实现 → 注册 → 双路径验证"三件事，缺一不可。**

## 0.1 原子扫描器隔离原则（2026-08-07 确立，同样是铁律）

**各原子扫描器的内部实现（抓取、解析、分析等）必须自成一体，扫描器之间不共享内部模块，各自的能力在各自的包内独立实现。**

这条原则不是理论推导出来的，而是一次真实的架构反转踩坑后确立的：曾经尝试把 `WebScanner` 内部的爬虫子模块（`scanner/web/crawler`）下沉为 `core/lib/crawler`，做成一个"通用抓取模块"，供 `WebScanner` 和新增的 `ApiScanner` 共享调用（`FetchAndCrawl` 统一入口）。这个方向已经完整实现过（详见 `docs/爬虫/web扫描模块重构文档.md`/`web扫描模块重构实施文档.md` 的历史记录），但最终判定**不值得做**，已完整回退。

**为什么"共享通用模块"这条路不通**：
1. 两个扫描器对"抓取"这件事的真实需求天然不同（`WebScanner` 需要截图/favicon/CDN 判断，`ApiScanner` 需要的是运行时 JS 执行环境），为了让一个通用接口同时满足两者，被迫引入回调（`OnPageReady`）等间接层，接口复杂度不降反升；
2. 扫描器各自的特殊逻辑（如 `WebScanner` 的升级重渲染 `escalateIfNeeded`）需要拿到抓取过程的中间状态（如 `*crawler.Crawler` 实例本身），一旦抓取逻辑被抽到独立包、返回值收窄成"最终结果"，这类特殊逻辑就没有合适的挂载点，最终又要在通用模块里开洞（暴露内部类型/方法）迁就单个调用方，通用模块名不副实，变成了"事实上只服务一个调用方、但形式上装作通用"的抽象；
3. 收益不成立：两个扫描器目前只有 `WebScanner` 是真实功能，`ApiScanner` 抓取能力尚未开始实现，"复用"本身是对着一个不存在的需求做的预先设计，属于过度设计。

**新标准**：
- 每个原子扫描器的内部包（如 `scanner/web/crawler`）只能被自己所属的扫描器 import，不能被其他扫描器 import；
- 如果未来发现多个扫描器之间确实存在完全无状态的通用纯函数（比如某种字符串处理、正则规则），可以下沉到 `internal/pkg` 一类的公共工具层，但下沉的对象必须是**无状态的纯函数**，而不是一整个"抓取流程"这种带副作用、带状态、带特殊路径的复杂模块；
- 判断一个能力该不该抽取成共享模块，先问：现在**已经有两个真实存在（不是规划中）的调用方**，且它们的**核心流程一致、只有末端处理不同**吗？两个条件都满足才考虑抽取，只满足一个就不做。

## 1. 整体架构：一条数据流，两个入口

```
                         ┌─────────────────────┐
                         │   底层 Scanner       │  纯粹的扫描逻辑
                         │ scanner/xxx/xxx.go   │  不知道 Task/TaskType 的存在
                         └──────────┬───────────┘
                                    │ 被工厂持有并初始化
                         ┌──────────▼───────────┐
                         │   Factory            │  Single Source of Truth
                         │ factory/xxx_factory.go│ 统一配置：限流器/超时/规则库
                         └──────────┬───────────┘
                                    │ 工厂产物实现/适配 Runner 接口
                         ┌──────────▼───────────┐
                         │   Runner 接口         │  Name() TaskType + Run(ctx, task)
                         │ (原生实现 或 adapter) │
                         └──────────┬───────────┘
                                    │ 注册进唯一的注册表
                         ┌──────────▼───────────┐
                         │   RunnerManager       │  map[TaskType]Runner
                         │ runner/manager.go     │  Execute() 按 TaskType 查表分发
                         └──────┬───────────┬────┘
                                │           │
                    ┌───────────▼───┐   ┌──▼────────────────────┐
                    │  CLI 入口      │   │  Master 编排入口        │
                    │ cmd/agent/scan│   │ agentTaskService        │
                    │ /xxx.go       │   │ .processTask()          │
                    └───────────────┘   └─────────────────────────┘
```

**只有一个执行核心**：`RunnerManager.Execute(ctx, task)`。CLI 和 Master 都必须调用它，不允许任何一方绕过去直接 new 底层 Scanner 调用（历史上 `os.go`/`web.go` 曾经这么干过，已经改掉，见第 5 节反面教材）。

## 2. Task 类型是唯一的契约

`internal/core/model/task.go` 里的 `TaskType` 常量，是连接 Master、CLI、RunnerManager 三方的唯一语言：

```go
const (
    TaskTypeIpAliveScan TaskType = "ip_alive_scan"
    TaskTypePortScan    TaskType = "port_scan"
    TaskTypeServiceScan TaskType = "service_scan"
    TaskTypeOsScan      TaskType = "os_scan"
    TaskTypeWebScan     TaskType = "web_scan"
    TaskTypeDirScan     TaskType = "dir_scan"
    TaskTypeVulnScan    TaskType = "vuln_scan"
    TaskTypeBrute       TaskType = "brute_force"
    TaskTypeSubdomain   TaskType = "subdomain"
    TaskTypeProxy       TaskType = "proxy"
    TaskTypeRawCmd      TaskType = "raw_cmd"
)
```

新增扫描能力前先确认：这个类型是否已经存在？如果 Master 侧已经有对应的业务场景（参考 `docs/Master-Agent扫描类型映射说明.md`），直接复用已有 `TaskType`；如果确实是全新能力，才新增常量。

## 3. 新增一个原子扫描器：标准 5 步

以假设新增 `DirScanner`（目录扫描，当前仓库里是空壳，可作为练手对象）为例。

### 第 1 步：实现底层 Scanner（纯业务逻辑，不碰 Task）

路径：`internal/core/scanner/dir/dir_scanner.go`

```go
package dir

type DirScanner struct {
    // 内部依赖：HTTP Client、限流器、字典加载器等
}

func NewDirScanner() *DirScanner { ... }

// Scan 只接受具体类型的参数，完全不知道 model.Task 的存在
func (s *DirScanner) Scan(ctx context.Context, target string, dict []string, extensions []string) ([]DirResult, error) {
    // 真正的扫描逻辑
}
```

**原则**：底层 Scanner 是"特种兵"，只做一件事，参数是具体类型（`string`/`[]string`），不依赖 `model.Task`、不知道 `TaskType`。这样它可以被单独测试、单独复用，不被上层任务系统污染。

### 第 2 步：在 Factory 里开一个统一构造入口

路径：`internal/core/factory/dir_factory.go`

```go
package factory

import "neoagent/internal/core/scanner/dir"

// NewDirScanner 创建目录扫描器，统一配置限流器/超时/默认字典等
func NewDirScanner() *dir.DirScanner {
    return dir.NewDirScanner( /* 统一配置 */ )
}
```

**为什么必须过 Factory，不能到处 `new`**：`factory` 包是 Single Source of Truth（详见 `internal/core/factory/README.md`）。如果 CLI 和 RunnerManager 各自 `new` 一份、配置还不一样（比如限流阈值不同），会出现"同一个命令，CLI 跑出来的结果和 Master 下发跑出来的不一样"的诡异 bug。

### 第 3 步：实现 `Runner` 接口（原生实现 或 适配器）

`Runner` 接口定义（`internal/core/runner/interface.go`）：

```go
type Runner interface {
    Name() model.TaskType                                          // 返回自己对应的 TaskType
    Run(ctx context.Context, task *model.Task) ([]*model.TaskResult, error)
}
```

两种写法，二选一：

**写法 A：Scanner 直接实现 Runner**（推荐，`WebScanner`/`BruteScanner`/`IpAliveScanner` 都是这样）

如果 Scanner 本身可以接受直接在 `Run` 里解析 `task.Params`，就让它自己实现 `Runner`：

```go
func (s *DirScanner) Name() model.TaskType {
    return model.TaskTypeDirScan
}

func (s *DirScanner) Run(ctx context.Context, task *model.Task) ([]*model.TaskResult, error) {
    dict, _ := task.Params["dict"].(string)
    extensions, _ := task.Params["extensions"].(string)
    results, err := s.Scan(ctx, task.Target, parseDict(dict), parseExt(extensions))
    // 包装成 []*model.TaskResult 返回
}
```

> **真实案例对照：`WebScanner`（仓库里写法 A 的完整已验证范例）**
>
> `DirScanner` 是假想示例，`WebScanner`（`internal/core/scanner/web/web_scanner.go`）才是仓库里真正跑通了"实现 → 注册 → CLI/Master 双路径"全流程的原生案例，建议直接对照阅读源码。它的 `Runner` 接口实现长这样：
>
> ```go
> // Name 扫描器名称
> func (s *WebScanner) Name() model.TaskType {
>     return model.TaskTypeWebScan
> }
>
> // Run 执行扫描任务，是纯编排层：把 task.PortRange（"80,443"/"1-100"/"top100"
> // 这类范围字符串）解析成具体端口列表，每个端口独立探测（各自猜协议、各自抓取、
> // 各自可能触发 BFS），互不影响、并发执行，最后把所有端口的结果汇总返回。
> func (s *WebScanner) Run(ctx context.Context, task *model.Task) (results []*model.TaskResult, err error) {
>     s.ensureInit() // 懒加载指纹规则，避免构造函数阶段做重量级 IO
>
>     ports := parsePortsForScan(task.PortRange)
>     if len(ports) == 0 {
>         return s.runOnePort(ctx, task, startTime, task.PortRange, protocolHint)
>     }
>     // 多端口并发探测，每个端口独立成功/失败，只有全部端口都失败才向上抛错误，
>     // 避免一个端口失败掩盖掉其他端口已经拿到的结果
>     // ...
> }
> ```
>
> 三个值得学习的设计点：
> 1. **`Name()` 只返回一个常量**，不做任何逻辑判断——`Runner.Name()` 就应该这么简单，复杂逻辑放在 `Run()` 里。
> 2. **`Run()` 是纯编排层**：真正的单端口探测逻辑在私有方法 `runOnePort()` 里，`Run()` 只负责把 `task.PortRange` 拆解成端口列表、并发调度、合并结果。这样即使以后要支持"多目标批量扫描"，改的也只是编排层，不动探测逻辑。
> 3. **局部失败不等于整体失败**：`len(results) == 0 && len(errs) > 0` 才返回错误，只要有一个端口探测成功，就把已有结果正常返回——这是 Runner 实现里处理"部分成功"场景的标准做法，`DirScanner`/`SubdomainScanner` 以后如果也是多目标探测，应该照抄这个模式。
>
> 对应的工厂方法（`internal/core/factory/web_factory.go`）：
>
> ```go
> // NewWebScanner 创建一个标准的 Web 扫描器
> // 预配置了浏览器管理器、自适应限流器和指纹引擎
> func NewWebScanner() *web.WebScanner {
>     return web.NewWebScanner()
> }
> ```
>
> 对应的 `RunnerManager` 注册（`internal/core/runner/manager.go`，2026-08-04 修复补上的一行）：
>
> ```go
> ws := factory.NewWebScanner()
> m.Register(ws)
> ```
>
> 对应的 CLI 命令（`cmd/agent/scan/web.go`）：
>
> ```go
> task := opts.ToTask()
> task.Params["screenshot"] = screenshot
> manager := runner.NewRunnerManager()
> results, err := manager.Execute(ctx, task)
> ```
>
> 四个文件、四个环节，`model.TaskTypeWebScan` 这一个常量把它们串成一条线——这就是本文档反复强调"`TaskType` 是唯一契约"的具体样子。

**写法 B：用 Adapter 隔离**（`OsScanner`/`PortServiceScanner→ServiceRunner` 是这样）

如果想让底层 Scanner 保持完全独立（不 import `model` 包），就在 `internal/core/runner/adapter_xxx.go` 写一个适配器做"参数解包 → 调用 → 结果封装"：

```go
// runner/adapter_dir.go
type DirRunner struct {
    scanner *dir.DirScanner
}

func NewDirRunner(scanner *dir.DirScanner) *DirRunner {
    return &DirRunner{scanner: scanner}
}

func (r *DirRunner) Name() model.TaskType {
    return model.TaskTypeDirScan
}

func (r *DirRunner) Run(ctx context.Context, task *model.Task) ([]*model.TaskResult, error) {
    // 解包 task.Params，调用 r.scanner.Scan(...)，封装结果
}
```

**怎么选**：能力如果只服务于 Task 系统、以后不会被单独抽出来复用，选 A，代码更少。如果这个 Scanner 未来可能被其他项目当库直接引用（不希望它依赖 `model` 包），选 B。**不确定就选 A**，这是当前仓库里大多数 Scanner 的做法，简单直接，不要过度设计。

### 第 4 步：注册进 `RunnerManager`（最容易漏掉的一步，也是本次修复的问题根源）

路径：`internal/core/runner/manager.go`

```go
func NewRunnerManager() *RunnerManager {
    m := &RunnerManager{runners: make(map[model.TaskType]Runner)}

    m.Register(factory.NewFullBruteScanner())
    m.Register(factory.NewAliveScanner())
    m.Register(factory.NewPortScanner())
    m.Register(NewServiceRunner(factory.NewPortScanner()))
    m.Register(NewOsRunner(factory.NewOsScanner()))
    m.Register(factory.NewWebScanner())

    // 新增的 Scanner 必须在这里注册，否则：
    // 1. Master 下发对应 TaskType 的任务会报 "no runner found for task type: xxx"
    // 2. CLI 命令即使实现了也调不到（因为 CLI 也是通过 RunnerManager 执行的，见第 4 节）
    m.Register(factory.NewDirScanner())        // 写法 A 直接注册
    // 或者
    m.Register(NewDirRunner(factory.NewDirScanner()))  // 写法 B 注册适配器

    return m
}
```

**检查清单（每次新增 Scanner 后必须自问）**：
- [ ] `task_to_core.go`（`internal/service/adapter/task_to_core.go`）里 Master 下发的任务类型字符串，是否已经 `case` 到了正确的 `model.TaskType`？
- [ ] `NewRunnerManager()` 里是否注册了这个 `TaskType` 对应的 Runner？
- [ ] 两者的 `TaskType` 是否完全一致（大小写、下划线，一个字符都不能错）？

### 第 5 步：接 CLI 命令，必须走 `RunnerManager`，不允许绕过

路径：`cmd/agent/scan/dir.go`

```go
func NewDirScanCmd() *cobra.Command {
    opts := options.NewDirScanOptions()

    cmd := &cobra.Command{
        Use:   "dir",
        RunE: func(cmd *cobra.Command, args []string) error {
            if err := opts.Validate(); err != nil {
                return err

            opts.Output = globalOutputOptions
            task := opts.ToTask()

            // 唯一正确的执行方式：通过 RunnerManager，
            // 工厂内已完成全部原子扫描器的统一注册，
            // CLI 与 Master 调度共用同一份注册表，避免能力不一致。
            manager := runner.NewRunnerManager()
            results, err := manager.Execute(context.Background(), task)
            if err != nil {
                return fmt.Errorf("scan failed: %w", err)
            }

            console := reporter.NewConsoleReporter()
            console.PrintResults(results)
            // ... 按需保存 JSON/CSV
            return nil
        },
    }
    // ... 绑定 flags
    cmd.AddCommand 到 scan/root.go 的 NewScanCmd()
    return cmd
}
```

同时别忘了 `internal/core/options/scan_dir.go` 里的 `ToTask()` 要把 `TaskType` 设对：

    // ...

## 4. 完整运行流程（两条路径殊途同归）

> 下面用 `dir_scan`（假想）画时序，把 `dir` 换成 `web`、`DirRunner.Run`/`DirScanner.Run` 换成 `WebScanner.Run`，就是 `neoAgent scan web` 和 Master 下发 `web_scan` 任务时的真实运行流程——两者结构完全一样，只是 `dir_scan` 目前还没有真实 Scanner 可以验证。

### 路径 A：CLI 单机运行

```
用户执行 neoAgent scan dir -t http://x.com
    │
    ▼
cmd/agent/scan/dir.go: NewDirScanCmd().RunE
    │  1. opts.Validate() 校验参数
    │  2. opts.ToTask() 组装成 *model.Task{Type: TaskTypeDirScan, Params: {...}}
    │  3. manager := runner.NewRunnerManager()  ← 全量注册表，与 Master 路径完全一致
    │  4. manager.Execute(ctx, task)
    ▼
RunnerManager.Execute
    │  runner, _ := m.Get(task.Type)   // map 查表，O(1) 找到 DirRunner/DirScanner
    │  return runner.Run(ctx, task)
    ▼
DirRunner.Run / DirScanner.Run
    │  解析 task.Params → 调用底层扫描逻辑 → 封装 []*model.TaskResult
    ▼
console.PrintResults(results)  // 终端输出 + 可选 JSON/CSV 落盘
```

### 路径 B：Master 集群编排运行

```
Master 下发任务 (HTTP 轮询响应)
    │  { "task_id": "xxx", "task_type": "dir_scan", "input_target": "..." }
    ▼
agentTaskService.StartWorker → processTask(task)
    │  1. masterService.ReportTask(..., "running", ...)   上报状态
    │  2. coreTask, _ := translator.ToCoreTask(&task)      Master协议 → model.Task
    │       (adapter/task_to_core.go: case "dir_scan": coreTask.Type = model.TaskTypeDirScan)
    │  3. results, err := s.runnerManager.Execute(ctx, coreTask)  ← 同一个 RunnerManager.Execute
    ▼
RunnerManager.Execute（与路径 A 完全相同的执行核心）
    │  runner, _ := m.Get(task.Type)
    │  return runner.Run(ctx, task)
    ▼
DirRunner.Run / DirScanner.Run（与路径 A 完全相同的业务逻辑，结果必然一致）
    ▼
agentTaskService 上报结果
    │  masterService.ReportTask(..., "completed", json.Marshal(results), "")
```

**两条路径唯一的区别**是"任务从哪来、结果送去哪"（CLI 是本地参数+终端输出，Master 是网络协议+上报接口），**执行核心 `RunnerManager.Execute` 及其下游完全相同**。这就是为什么第 3 节"注册"这一步不能省——漏注册的后果是两条路径都会失败，只是报错时机不同（CLI 立即报错，Master 会在任务真正下发时才报错）。

## 5. 反面教材：曾经踩过的坑（2026-08-04 修复记录）

| 问题 | 现象 | 根因 | 修复方式 |
| :--- | :--- | :--- | :--- |
| `WebScanner` 未注册到 `RunnerManager` | Master 下发 `web_scan`/`api_scan` 任务必然失败（`no runner found`），但 CLI `scan web` 能跑（因为 CLI 曾经绕过 `RunnerManager` 直接 `new WebScanner` 调用） | 实现了 Scanner、也接了 CLI，但漏了 `NewRunnerManager()` 里的注册 | 补上 `m.Register(factory.NewWebScanner())` |
| `os.go`/`web.go` 跳过 `RunnerManager` | CLI 和 Master 两条路径用的不是同一份代码，一旦某一处改了参数解析逻辑，另一处不会同步 | CLI 图省事直接 `factory.NewXxxScanner().Run()`，没有走注册表查找 | 统一改为 `manager := runner.NewRunnerManager(); manager.Execute(...)` |
| `alive.go`/`port_service.go` 手工二次注册 | 每个 CLI 命令都手工 `manager.Register(单个scanner)`，`NewRunnerManager()` 里全量注册的逻辑形同虚设，容易和 Master 路径的能力集"看起来一致实际有偏差"的错觉 | 历史遗留写法，没有信任工厂的全量注册 | 直接 `manager := runner.NewRunnerManager()`，去掉手工 `Register` |
| `dir`/`subdomain`/`vuln` 命令是空壳 | 命令能跑、能打印一段看似正常的 Task JSON、返回 `nil`（退出码 0），但**没有调用任何 Scanner，没有真实扫描发生** | Scanner 从未实现，CLI 命令却先行注册进了 `root.go`，`RunE` 里只做了 `ToTask()` + `json.MarshalIndent` 打印 | 在 Scanner 真正实现之前，明确 `return fmt.Errorf("xxx scan not implemented yet")`，绝不假装成功 |

**教训提炼成一句话**：**没有实现的功能，宁可让命令报错，也不能让它看起来"成功"。虚假的成功比明确的失败更危险，因为用户会基于错误的扫描结果做安全判断。**

## 6. 新增扫描器完成后的自检清单

- [ ] 底层 Scanner 在 `scanner/xxx/` 下实现，不 import `model` 包（除非选择写法 A）
- [ ] `factory/xxx_factory.go` 提供统一构造函数，所有调用方都通过它拿实例，不到处 `new`
- [ ] 实现（或适配）`Runner` 接口，`Name()` 返回正确且唯一的 `TaskType`
- [ ] `NewRunnerManager()` 里已注册
- [ ] `internal/service/adapter/task_to_core.go` 里 Master 任务类型字符串能正确 `case` 到该 `TaskType`（如果 Master 也需要下发这个能力）
- [ ] `internal/core/options/scan_xxx.go` 的 `ToTask()` 设置了正确的 `TaskType`
- [ ] `cmd/agent/scan/xxx.go` 通过 `runner.NewRunnerManager() → manager.Execute()` 执行，不绕过
- [ ] 命令已挂载到 `cmd/agent/scan/root.go` 的 `NewScanCmd()`
- [ ] `go build ./...` 编译通过，`go vet` 无新增问题
- [ ] 手动执行一次 CLI 命令，确认真实产生了扫描结果（而不是打印任务描述就退出）
- [ ] 如果这是"占位但未实现"的阶段性提交，命令必须显式 `return error`，不能假装成功
