# 给自研爬虫的借鉴建议

本篇不复述"它做了什么"，而是回答"我该抄哪些、怎么抄、优先级如何"。按投入产出比从高到低排列，并给出可直接落地的伪代码/清单。无论你的爬虫是用 Go、Python 还是其它语言实现，这些原则都是语言无关的。

---

## 第一梯队：几乎零成本、立刻能用的原则

### 1. 用一个数值化的"优先级分数"代替 if/else 调度逻辑

**问题**：很多自研爬虫的队列调度是"先判断是否重试 → 再判断深度 → 再判断是否是种子页"这种层层 if 嵌套，越写越乱，加一个新维度（比如"限流页面延后处理"）就要改好几处判断。

**做法**：设计一个综合评分函数，把所有优先级维度编码成一个可比较的数：

```
score = depth
      + extra_hops_penalty * out_of_scope_hops
      + retry_penalty * retry_count
      - priority_boost（可选：种子页/高价值页面给负数提权）
```

用最小堆/优先级队列（Redis ZSET、Go 的 `container/heap`、内存里的堆）替代普通 FIFO 队列，出队逻辑永远只有一行 `pop_min()`。

**收益**：新增一个调度维度只需要调整公式里的系数，不需要改任何调用方代码。

### 2. 所有跨步骤的状态变更做成原子操作

**问题**：分布式/多协程爬虫最常见的 bug 是"查询队列大小 → 判断未满 → 插入"这种非原子操作在并发下产生超量入队、重复抓取。

**做法**：
- 如果用 Redis：优先用 Lua 脚本（`EVAL`）或者 `MULTI/EXEC` 事务把"检查+修改"打包成一次往返。
- 如果用关系型数据库：用 `SELECT ... FOR UPDATE` 或乐观锁（版本号）。
- 如果纯内存：用一把锁保护"读-判断-写"整个临界区，而不是只锁写。

**收益**：消灭一整类难以复现、偶发的并发 bug，测试成本大幅降低。

### 3. 退出码要分级，为重试策略服务

**问题**：很多爬虫非 0 即 1 地退出，外部编排系统（K8s/systemd/cron）无法区分"该重试的临时错误"和"重试也没用的永久错误"。

**做法**：至少区分以下几类退出码：
- 成功
- 通用/未知错误（值得重试）
- 资源类错误（磁盘满、内存不足——通常不该无脑重试，需要人工介入）
- 网络/代理错误（值得重试，甚至可以退避重试）
- 达到限流阈值（应该退避后重试，间隔要比普通错误更长）
- 致命配置错误（不应该重试，重试只会浪费资源）

**收益**：接入 K8s CronJob/Deployment 时可以配置精细化的重启策略（`restartPolicy` + 自定义 sidecar 判断退出码），避免"配置错误导致的爬虫无限重启风暴"。

### 4. Scope（抓取范围）判断统一抽象成一个函数 + 数据表驱动

**问题**：很多爬虫的"该不该抓这个链接"逻辑散落在各处（有的在抽取链接时判断，有的在入队前判断，有的在下载后判断），规则不一致导致有的地方漏判、有的地方重复判断。

**做法**：把"允许模式列表 + 排除模式列表 + 最大深度 + 额外跳数"抽象为一个纯函数 `IsInScope(url, depth, extraHops) -> (allow bool, newExtraHops int)`，全爬虫只在一个地方调用它（比如"准备入队前"），其它地方一律信任队列里已经在 scope 内的假设。

**收益**：规则变更只改一处；新增"额外跳数"这种进阶特性不需要重构现有代码。

## 第二梯队：需要一定设计投入，但对生产可用性影响巨大

### 5. Direct Fetch：分层过滤，贵的操作放最后

**原则**：先用最便宜的手段（HEAD 请求或只读 headers 的 GET）判断资源类型，只有确认需要"重"处理（渲染 JS、执行行为脚本）时才启动昂贵资源（无头浏览器）。

**落地到自己的爬虫**：
- 如果目标大多是静态资源（图片、文档、API JSON），先用普通 HTTP 客户端探测 `Content-Type`，只有明确是 HTML 且需要 JS 渲染才交给浏览器池处理。
- 即使全站都要浏览器渲染，也可以对已知的静态资源后缀（`.jpg/.pdf/.zip`）直接跳过浏览器直连下载。

**收益**：浏览器实例是最贵的资源（内存、CPU、并发数受限），能省一次是一次，通常可以把整体吞吐提升数倍。

### 6. 内容寻址去重（Content-Addressed Dedup），而不仅仅是 URL 去重

**原则**：只做 URL 去重解决不了"同一内容换个 URL 参数就要重新下载存储"的问题（CDN、时间戳参数、镜像站点很常见）。

**落地**：
- 对下载的内容计算哈希（SHA-256 足够，性能与冲突率平衡好）。
- 维护一个 `hash -> 首次见到的URL/位置` 的索引（可以是简单的 KV 存储）。
- 命中时只存"指针记录"（类似 WARC 的 revisit 语义），不重复存储 body。

**收益**：对增量爬取、镜像站点抓取，存储空间可以节省一个数量级。如果你的爬虫需要反复对同一批站点做定期抓取（监控类场景），这个收益尤其明显。

### 7. 未完成任务不能污染共享状态——两阶段提交思维

**原则**：如果多个爬取任务共享一个去重索引/统计库，"进行中"的任务数据不应该在完成前就对外可见，否则任务失败/取消后会留下脏数据，且可能被其它任务误判断为"已存在"从而漏抓。

**落地**：给每次任务运行一个唯一 ID，写入时都标记这个 ID；任务成功结束后，用一次批量操作把这次任务的数据"提升"为全局可见；任务失败/取消则清理掉这批带有该 ID 的临时数据。

**收益**：任务可以放心地被杀死重启，不用担心留下无法追溯的脏数据。

### 8. 磁盘/资源水位要"预测"，不要等写满才报错

**原则**：不要只检查"现在还剩多少空间"，要结合"接下来这个步骤大概还需要多少空间"做预测性判断（比如你知道接下来要把所有临时文件打包成一个压缩包，那至少要预留原始数据体积的空间）。

**落地**：在触发昂贵的后处理步骤（打包、格式转换、上传）之前，加一个"预估所需资源 vs 剩余资源"的检查点，不够就提前优雅停止而不是让进程在半途因为写盘失败而崩溃产生半成品文件。

### 9. 三级中断处理，保证进程被杀死时数据不损坏

**落地清单**：
1. 收到第一次终止信号：停止接受新任务，让正在处理的任务自然完成，flush 所有缓冲区/文件句柄，保存断点状态，再退出。
2. 收到第二次终止信号（用户等不及了）：立即中断正在进行的任务，但已经写入缓冲区的数据必须完整落盘（不能写一半的文件）。
3. SIGKILL（无法拦截）：唯一的保护手段是"设计上要求任何时刻磁盘上的文件本身都是自洽的"——比如追加写而不是原地改写，用"写临时文件 + rename"代替直接覆盖等原子写入手法。

**收益**：这是决定一个爬虫"能不能在生产环境放心跑"的分水岭。很多自研爬虫在这方面几乎是空白，一旦被强制终止就产生损坏的输出文件。

### 10. 断点续爬要序列化"完整状态"而不只是"已完成列表"

**原则**：仅保存"哪些 URL 已完成"不足以精确恢复，还需要保存：待抓队列（含优先级信息）、正在处理中但未完成的任务（重启后要重新入队而不是永久丢失）、失败重试计数、运行时新发现的种子。

**落地**：断点文件设计成"完整重建当时内存/Redis 状态所需的最小信息集合"，恢复时直接反序列化重建，而不是"重新跑一遍发现逻辑"。

## 第三梯队：视自身场景选择性借鉴

### 11. 云原生集成细节

- 提供标准健康检查端点（`/healthz`），配合错误计数阈值，比"进程存活即健康"更准确地反映真实工作状态。
- 如果用 StatefulSet/多副本部署，考虑从 `hostname` 里解析副本序号来分配全局唯一的 worker ID 区间，避免多副本之间 ID 冲突导致的日志/监控混乱。
- 支持外部信号动态调整运行中的爬取规则（比如通过消息队列推送"新增一条排除规则"），避免必须重启整个爬取任务才能生效。

### 12. 限流/反爬检测作为一等公民

**原则**：把"是否被限流/遇到验证码"作为每个任务状态的显式字段，而不是通过异常/日志事后分析。

**落地**：
- 维护滑动窗口计数器：最近 N 秒内命中限流特征（403/429/503 或页面文本匹配验证码关键词）的次数。
- 超过阈值时，主动降低并发度或暂停对该域名的抓取，而不是无脑重试把 IP 榨干。
- 命中限流的任务要能重新排队，但优先级应该低于正常任务（复用第 1 条的评分公式思路）。

### 13. 页面/资源级别的双层规则：抓取范围 vs 资源过滤

**原则**：区分"这个页面要不要抓"（scope 规则）和"这个页面里的某些子资源要不要加载/记录"（block 规则），两者复杂度和使用频率不同，不要用同一套规则系统硬凑。

### 14. 行为脚本用"可中断的生成器"而非同步脚本

如果爬虫需要模拟页面交互（滚动、点击、展开评论区），把交互脚本写成可以逐步 `yield` 状态的生成器/协程，而不是一段不可打断的同步代码。这样任何时候需要超时熔断，都能在一个安全的边界点上退出，不会让浏览器停留在不可预测的中间状态。

### 15. 详尽、面向决策的文档

不要只写"这个参数是什么类型、默认值是什么"，要写"什么场景该用哪个选项、这两个相似选项该怎么选"。这个项目的 `crawl-scope.md` 是很好的范本——每个功能点都配一个"什么时候该用它 vs 不该用它"的对比说明。

## 优先级落地路线图（建议顺序）

如果要把这些经验应用到自己的爬虫（无论是重构现有项目还是新起项目），建议按以下顺序推进：

1. **先把调度和状态管理的原子性做对**（第 1、2 条）——这是所有并发正确性的地基，越早做成本越低，事后补几乎等于重写。
2. **补齐进程健壮性**（第 9、10 条：优雅退出 + 断点续爬）——决定了系统能不能在生产环境无人值守运行。
3. **按实际瓶颈引入性能优化**（第 5 条 Direct Fetch、第 6 条内容去重）——如果你的场景确实存在大量非核心内容/重复内容，这里的收益最直接。
4. **视规模决定是否要做云原生集成和多任务共享状态的两阶段提交**（第 7、11 条）——单机小规模爬虫可以先跳过，等真正需要水平扩展时再引入，避免过度设计。
5. **限流对抗和反爬处理**（第 12 条）——根据实际抓取目标站点的严格程度决定投入多少，多数场景下"基础的状态码识别 + 退避重试"已经够用。

---

## 一句话总结

这个项目最值得学习的不是某个具体技巧，而是一种贯穿始终的工程态度：**把"进程随时可能被杀死、多个副本随时并发运行、磁盘随时可能写满"当作默认假设去设计，而不是事后补丁**。这种假设一旦在最初的数据结构和状态管理里落地，后续所有的健壮性都是自然而然的结果，而不需要靠大量的异常处理代码去堆砌。
