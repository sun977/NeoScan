# Browsertrix Crawler 项目亮点

本篇聚焦"这个项目在工程上到底做对了什么"，每一条都标注了具体代码位置，方便回查。

## 1. 数据结构驱动设计：用一个公式消灭优先级调度的所有分支

爬虫的核心问题之一是"下一个抓哪个 URL"。多数简单实现会写一堆 if/else（先抓深度浅的、失败的往后排、超范围的额外跳数要降权……）。

Browsertrix 的做法是把所有优先级因素编码进**一个数值**，直接作为 Redis ZSET 的 score：

```137:1539:src/util/state.ts
_getScore(data: QueueEntry) {
  return (
    (data.depth || 0) +
    (data.extraHops || 0) * MAX_DEPTH +
    (data.retry || 0) * MAX_DEPTH * 2
  );
}
```

`zadd`/`zpopmin` 天然实现了：
- 广度优先（depth 小的先出队）
- "额外跳数"页面统一延后（乘以 `MAX_DEPTH`，保证不会因为深度小就抢占正常范围内的页面）
- 失败重试的页面进一步延后（乘 2 倍 `MAX_DEPTH`）

没有任何 `if (depth < x) else if (retry > y)` 的分支，调度逻辑就是一次 ZSET 的 pop。这是教科书级别的"好品味"：**通过数据结构设计消灭特殊情况**，而不是罗列特殊情况。

## 2. 分布式状态机全部用 Redis Lua 脚本做原子化

爬虫在多 worker、甚至多 Pod 并发下，队列的"出队+标记处理中"、"失败+计数+决定是否重试"等操作如果不是原子的，会出现漏抓、重复抓、计数错乱。项目里把这些复合操作全部下沉为 Lua 脚本：

```926:1078:src/util/state.ts
redis.defineCommand("addqueue", { ... })   // 查重 + 容量检查 + 入队 + 清理pending，一次原子操作
redis.defineCommand("getnext", { ... })    // 出队 + 标记pending，一次原子操作
redis.defineCommand("requeuefailed", {...}) // 失败计数 + 判断是否超过重试上限 + 重新入队或丢弃
redis.defineCommand("addnewseed", {...})   // 去重检查 + 追加新种子，防止并发重复添加
```

这种设计使得**多个爬虫进程/Pod 共享同一个 Redis 时天然线程安全**，不需要额外的分布式锁。这是分布式爬虫最容易踩坑也最容易被简化掉的一环，Browsertrix 处理得非常彻底。

## 4. Direct Fetch：非 HTML 资源跳过浏览器渲染

浏览器渲染开销巨大，但如果目标 URL 直接是图片/PDF/视频等非 HTML 资源，用浏览器打开纯属浪费。Browsertrix 会先尝试用 `undici` 直接发 HTTP 请求探测 headers：

```1535:1599:src/util/recorder.ts
async directFetchCapture({ url, headers, cdp, state }) {
  ...
  if (!(await fetcher.loadHeaders())) { return ...; }
  const mime = reqresp.getMimeType() || "";
  if (reqresp.status !== 200) { return reqresp.status; }
  if (isHTMLMime(mime)) {
    return STATUS_IS_HTML_NO_DIRECT_FETCH;   // 是HTML，回退给浏览器渲染
  }
  await fetcher.loadDirectPage(state);        // 不是HTML，直接抓取写WARC，完全不用开浏览器页面
  return reqresp.status;
}
```

只有当直接抓取失败或确认是 HTML 页面时才会退回浏览器渲染流程（`crawlPage` 中的 `doDirectFetch()`）。这是典型的"先便宜后昂贵"的分层探测（cheap check before expensive operation）优化范式。

## 5. 统一的"内容寻址去重"贯穿单次爬取与跨爬取

所有网络响应最终都要经过同一个函数 `serializeToWARC`，其中做了 SHA-256 内容哈希查重：

```1906:1953:src/util/recorder.ts
const hash = responseRecord.warcPayloadDigest || "";
...
const res = await this.crawlState.getHashDupe(hash);
if (res) {
  // 命中重复内容，把 response record 转换为 revisit record，只保留指针
  ({ responseRecord, serializer } = await createRevisitForResponse(...));
  await this.crawlState.addDupeCrawlDependency(crawlId, index);
}
```

去重索引分两层：
- **单次爬取内**默认开启，`WRITE_DUPE_KEY` 避免同一个 URL 重复写入。
- **跨爬取**可选（`--redisDedupeUrl`），共享一个 `DUPE_ALL_HASH_KEY` 哈希表，且有**未提交（uncommitted）→ 提交（committed）**两阶段状态，只有爬取正常完成才会把本次哈希"发布"到全局共享索引，失败/取消的爬取数据不会污染全局去重库（见 `RedisDedupeIndex.commitDedupeDone` / `clearUncommitted`）。这本质上是一种简化版的两阶段提交（2PC），非常适合"任务可能被杀死重启"的云原生场景。

## 6. WARC/WACZ 依赖关系追踪，让"去重"不等于"丢数据"

如果 B 爬取相对 A 爬取去重了，B 的 WACZ 里只有 `revisit` 记录指向 A。如果 A 被删除，B 就成了"看起来完整实际残缺"的存档。Browsertrix 在 `datapackage.json` 里显式记录 WACZ 间的 `requires` 依赖关系（`res.requires[0].crawlId/filename/size/hash`），任何消费这份存档的下游工具都能知道"我还需要另一个文件才能完整回放"。这是**存档系统对数据完整性的诚实态度**，很多简化实现会忽略这个问题从而导致数据静默丢失。

## 7. 精细的"三级"崩溃/中断处理，做到永不产生损坏文件

`common-options.md` 文档明确定义了三种中断级别：

1. 第一次 SIGINT/SIGTERM：优雅完成当前页面 → flush WARC → 生成 WACZ → 保存 Redis 状态再退出。
2. 第二次信号：立即关闭浏览器，但仍保证已缓冲的 WARC 记录被写完整（WARC 文件本身不会损坏，只是可能不完整）。
3. SIGKILL：无法处理，只能靠"下次重启从 saved state 恢复"兜底。

代码上通过 `main.ts` 的信号处理 + `crawler.ts` 的 `gracefulFinishOnInterrupt` / `serializeAndExit` 分级实现，并且 `WARCWriter` 的所有写入都走 `PQueue({concurrency: 1})` 串行队列，`flush()` 时 `await warcQ.onIdle()` 保证退出前全部落盘。**这是对"数据完整性优先于响应速度"这一原则的彻底贯彻**。

## 8. 面向 Kubernetes 的原生设计，而不是事后包一层

- Worker ID 会自动从 `hostname`（形如 `crawl-id-name-N`）解析出 Pod 序号，从而让每个 Pod 内的 worker 编号全局不重叠（`runWorkers` 里的 offset 计算，`src/util/worker.ts`）。
- `HealthChecker` 提供标准 `/healthz` 端点，接入 K8s liveness probe。
- 细分了 20 多个退出码（`ExitCodes` 枚举），区分"应该重试"（如 `ProxyError`）和"不应该重试"（如 `Fatal`），供外部编排系统做退避策略。
- `--restartsOnError` / `isCrawlPaused()` / `isCrawlCanceled()` 等状态位都存在 Redis 里，是为了支持"进程可能被随时杀死重启，状态必须在外部持久化"这一云原生假设而设计。

这些不是外挂的"云原生 checklist"，而是渗透到调度、日志、退出码设计里的一等公民考虑。

## 9. Scope（作用域）规则用统一的正则表达式集合抽象所有场景

## 10. 限流/反爬检测是一等公民而非事后打补丁

- 内置状态码限流识别（403/429/503 默认视为限流）+ 自定义正则内容检测（`--rateLimitOnMatch`，可以识别页面文本里的验证码/人机验证提示）。
- 有独立的滑动窗口计数器（`incRateLimited` / `isRateLimited`，带 TTL），支持"最近 N 秒内限流次数超过阈值就主动中断爬取"，而不是傻乎乎地一直重试耗尽资源。
- 针对 Cloudflare 的"5秒盾"有专门检测循环等待：

```2873:2896:src/crawler.ts
while (await timedRun(page.$("div.cf-browser-verification.cf-im-under-attack"), ...)) {
  await sleep(5.5);
}
```

反爬对抗从来不是"锦上添花"的功能，而是生产环境爬虫必须面对的常态，这个项目把它当作核心状态机的一部分来设计（`rateLimitStatus` 是 `PageState` 的一等字段）。

## 11. 自定义行为（Behavior）系统：把"人类操作"抽象为可插拔脚本

支持 JS 类和 DevTools Recorder 的 JSON User Flow 两种格式，behavior 是一个**异步迭代器**（`async* run(ctx)`），每 `yield` 一次代表一个可被安全中断/续传的"步骤"。系统还内置了针对 Facebook/Instagram/Twitter/YouTube 等主流站点的专属行为脚本，并支持 `--failOnContentCheck` 在检测到"未登录"等异常内容时主动使爬取失败，而不是产出一份看似成功实则空洞的存档。这种"可中断的生成器语义 + 站点插件化"的设计，比同步脚本注入更健壮。
