# Browsertrix Crawler 实现原理

本篇按"一个 URL 从入队到落盘"的完整生命周期，逐层拆解核心机制的具体实现。

---

## 一、总体生命周期

```
main.ts
  └─ Crawler.run()
       ├─ bootstrap()      初始化：Redis连接/目录/代理/种子解析/UA/robots配置
       ├─ crawl()          主循环：启动浏览器 → runWorkers(N个并发) → 等待全部完成
       │    └─ PageWorker.runLoop()  (每个worker独立循环)
       │         ├─ crawlState.nextFromQueue()   从Redis ZSET原子出队
       │         ├─ isInScope() 二次校验(动态添加的排除规则可能使其失效)
       │         ├─ initPage()  复用或新建浏览器Tab
       │         ├─ timedCrawlPage()
       │         │    └─ crawlPage()
       │         │         ├─ doDirectFetch() 尝试免浏览器直接抓取(非HTML)
       │         │         ├─ loadPage()      浏览器导航 + 状态判定
       │         │         ├─ doPostLoadActions() 截图/文本抽取/Behavior执行
       │         │         └─ extractLinks()  链接抽取 → queueInScopeUrls() 递归入队
       │         └─ pageFinished()  写pages.jsonl / 标记完成或失败重试 / 检查各类限制
       └─ postCrawl()       合并CDX索引 → 生成WACZ → 上传S3 → 提交去重索引 → 清理本地
```

## 二、调度与队列：Redis 作为唯一真源（Single Source of Truth）

### 2.1 数据结构

每个爬取任务（crawlId）在 Redis 中维护一组 key：

| Key | 类型 | 作用 |
|---|---|---|
| `{crawlId}:q` (`qkey`) | ZSET | 待抓取队列，score 编码优先级 |
| `{crawlId}:p` (`pkey`) | HASH | 正在处理中（pending）的 URL → JSON详情 |
| `{crawlId}:s` (`skey`) | SET | 已见过的 URL（seen，用于去重判断是否已在队列/已完成） |
| `{crawlId}:d` (`dkey`) | Counter | 已完成计数 |
| `{crawlId}:f` (`fkey`) | LIST | 永久失败（超过重试上限）的 URL |
| `{crawlId}:extraSeeds`/`esMap` | LIST/HASH | 运行时新增的种子（如重定向产生） |
| `{crawlId}:excluded` (`exKey`) | SET | 被排除的 URL |

### 2.2 出入队的原子性保障

所有跨多个 key 的复合操作全部封装为 Redis Lua 脚本（`_initLuaCommands`），避免"读-判断-写"之间的竞态窗口。以入队 `addqueue` 为例：

```lua
-- KEYS: pkey, qkey, skey, esKey, exKey  ARGV: url, score, json, limit
local size = scard(skey) - llen(qkey_pending) - scard(exKey)  -- 计算当前有效队列大小
if limit > 0 and size >= limit then return 1 end               -- 超过 --limit 直接拒绝
if sadd(skey, url) == 0 then return 2 end                      -- 已存在则视为重复URL
zadd(qkey, score, json)                                        -- 真正入队
return 0
```

一次 Redis 调用完成"容量检查 + 去重判断 + 入队"，天然避免了"两个 worker 同时判断'未满'然后都插入导致超限"的经典并发 bug。

### 2.3 优先级评分公式

```js
score = depth + extraHops * MAX_DEPTH + retry * MAX_DEPTH * 2
```

- `depth` 保证同一批次内**广度优先**（先抓浅层页面）。
- `extraHops`（超出 scope 但被 `--extraHops` 允许的"额外跳数"页面）乘以一个远大于正常深度上限的系数，保证这类页面总是排在所有正常范围页面之后处理。
- `retry`（失败重试次数）系数是 extraHops 的两倍，保证反复失败的页面被无限期推迟，但不会被永久阻塞（仍在队列里，只是权重最低）。

这个公式的本质是把"多维优先级"编码为"一维可比较的分数"，是很多调度系统（包括分布式任务队列）通用的设计模式。

### 2.4 失败重试与限流联动

`markFailed()` 根据是否命中限流选择不同的重试上限：

```js
const retries = noRetries ? 0 : isRateLimit ? this.rateLimitMaxRetries : this.maxRetries;
return await this.redis.requeuefailed(pkey, qkey, fkey, url, retries, MAX_DEPTH);
```

`requeuefailed` Lua 脚本读出该 URL 当前重试次数，若未超限则 `retry+1` 后重新计算 score 并 `zadd` 回队列；若超限则移入永久失败列表 `fkey`。限流场景可以配置独立的重试次数上限（`--rateLimitMaxRetries`），与普通网络错误的重试策略解耦。

## 三、URL 归一化与作用域判断

### 3.1 归一化（Normalization）

统一通过 `normalizeUrl()`（基于 `normalize-url` 库）处理：只做"排序 query 参数"，不去除 `www.` 前缀、不去除 hash、不去除尾部斜杠——这些差异化处理交给 scope 层的正则去兼容，归一化只解决"参数顺序不同但语义相同"的 URL 被判定为两个不同页面的问题。

### 3.2 Scope 规则引擎

`ScopedSeed` 类把 7 种 scope 类型统一转换为正则表达式集合：

| scopeType | 生成的正则逻辑 |
|---|---|
| `page` | 精确匹配种子 URL 本身 |
| `page-spa` | 种子 URL + 任意 hash 后缀（单页应用路由） |
| `prefix` | 种子 URL 所在目录前缀 |
| `host` | 同 origin |
| `domain` | 同注册域名及所有子域名（正则里把 `www<N>.` 替换成 `([^/]+\.)*`） |
| `any` | `/.*/`（不限制） |
| `custom` | 完全由用户提供的 `--include` 正则 |

判断一个链接是否应该被抓取时，`isIncluded()` 依次执行：

1. 归一化后与自身种子 URL 相同 → 直接判定为"自引用，允许"。
2. 若 `ignoreScope` 标记为真（如 behavior 通过 `addLink` 强制添加）→ 视为在 scope 内。
3. 否则遍历 `include` 正则数组，命中任意一个即在 scope 内。
4. 若不在 scope 内但设置了 `extraHops`，且当前 `extraHops` 计数未超过上限，则标记为"越界但允许"（`isOOS = true`），并让调用方把该链接的 `extraHops` 计数 +1 传递下去（下一跳如果还不在 scope 内且计数已达上限，则彻底丢弃）。
5. 最后应用 `exclude` 正则数组，排除规则始终优先于包含规则。

`extraHops` 的传播在 `queueInScopeUrls()` 中体现：

```js
depth += 1;
const newExtraHops = extraHops + 1;
// isOOS ? 传newExtraHops（继续累加） : 传原extraHops（未越界不消耗额度）
extraHops: isOOS ? newExtraHops : extraHops,
```

### 3.3 种子重定向的处理

如果种子页面（depth===0）重定向到了一个不在原 scope 内的 URL：
- 默认（`--addRedirectedSeeds` 关闭）：仅加载这一个跳转后的页面内容，但不把新 URL 当作种子（不会以它为起点继续扩展抓取范围）。
- 开启后：调用 `crawlState.addExtraSeed()`（内部走 `addnewseed` Lua 脚本，去重防止并发重复添加）把新 URL 注册为等价的新种子，后续从它出发的链接也会按同样 scope 规则继续抓取。

## 四、页面加载状态机（`loadPage`）

页面加载被建模为一个多阶段状态机，用 `LoadState` 枚举贯穿：

```
FAILED(0) → CONTENT_LOADED(1) → FULL_PAGE_LOADED(2) → EXTRACTION_DONE(3) → BEHAVIORS_DONE(4)
```

关键事件监听在 `page.goto()` 之前提前挂好：

```js
page.once("requestfailed", (req) => { downloadResponse = getDownloadResponse(req); });
page.on("response", waitFirstResponse);          // 记录第一个非重定向响应
page.once("domcontentloaded", () => data.loadState = LoadState.CONTENT_LOADED);
```

`page.goto()` 之后依据不同的失败/成功组合分别处理：

- **完全加载成功** → `fullLoadedResponse` 有值 → `FULL_PAGE_LOADED`。
- **超时但已经 `domcontentloaded`** → 判定为"慢页面"，跳过 Behavior 但仍继续走链接抽取（`data.skipBehaviors = true`），不算失败。
- **`net::ERR_ABORTED` 但捕获到一个"下载响应"** → 说明这其实是文件下载（如 PDF 直链），走 `downloadResponse` 分支同样判定 `FULL_PAGE_LOADED`。
- **`net::ERR_BLOCKED_BY_RESPONSE`** → 已被 blockRules/recorder 拦截，判定为 `Skipped`，不计入失败重试。
- **其它异常** → 判定为 `pageFailed`，交给 `markFailed` 走重试流程。

加载成功后，还会做几个容易被忽视的边界检查：
- **Chrome 内部错误页**（`chrome-error://`）→ 视为失败。
- **种子页面若重定向出了 scope** → 按 3.3 节逻辑决定是否注册新种子。
- **`failOnInvalidStatus` + 4xx/5xx** → 可选择性地把 HTTP 错误状态当作页面失败处理。
- **iframe 有效性过滤**（`shouldIncludeFrame`）→ 通过检查 `frameElement.tagName` 排除"看起来是 iframe 实际是 PDF viewer 之类的 embed 对象"，避免行为脚本/文本抽取在错误的上下文里运行。

只有确认是 HTML 页面（根据 `Content-Type` 或"是否走了完整的 page load"兜底判断）才会继续做 Cloudflare 检测、`netIdle` 等待、行为脚本执行和链接抽取；非 HTML 页面在此提前返回，不做任何后续处理。

## 五、网络层记录管道（Recorder）

这是全项目最复杂的子系统，本质是把 **CDP 的网络事件流** 转换成 **符合 WARC 规范的 request/response 记录对**。

### 5.1 两种拦截模式

- **`Network.*` 事件**（被动监听）：`requestWillBeSent` / `responseReceived` / `loadingFinished` / `loadingFailed`，用于记录浏览器自然发出的请求，不影响请求本身的执行。
- **`Fetch.requestPaused`**（主动拦截）：当需要重写响应内容（HLS/DASH manifest 改写、去重后返回精简 revisit 内容）时，用 CDP Fetch 域暂停请求，读取/修改 body 后再用 `Fetch.fulfillRequest` 放行。

两者通过 `requestId` 关联到同一个 `RequestResponseInfo` 对象，记录该请求从发起到结束的完整状态（headers、body、status、resourceType、是否来自缓存等）。

### 5.2 内容重写（Rewriting）

对特定 MIME 类型的响应体做即时重写，复用 `@webrecorder/wabac` 库里与"回放时重写"完全相同的规则（保证抓取与回放行为一致）：

| Content-Type | 重写内容 |
|---|---|
| `application/x-mpegurl`, `vnd.apple.mpegurl` | HLS 播放列表，改写分片 URL 为可归档形式 |
| `application/dash+xml` | DASH manifest，同上 |
| `text/html`/`application/json`/`*javascript*` | 通用重写器（如把绝对路径替换、注入必要的存档标记） |

重写过程中还会检查 `--rateLimitOnMatch` 自定义正则，命中即判定为限流/验证码页面（`markRateLimited`），做到"边下载边检测"而不是下载完才发现是验证码页。

### 5.3 流式处理与大文件保护

对于大文件（如视频），使用 `Fetch.takeResponseBodyAsStream` + 自定义异步迭代器 `takeStreamIter` **边读边写**，而非一次性读入内存再处理：

- `MAX_NETWORK_LOAD_SIZE`（200MB）：超过则截断，避免单个超大响应拖垮内存。
- `MAX_BROWSER_DEFAULT_FETCH_SIZE`（5MB）：超过此值的 payload 不会重新塞回浏览器内存（写入 WARC 后不回传，因为回传需要重新读入完整内存，得不偿失）。
- `WARCSerializer` 支持 `externalBuffer`（临时文件缓冲），当内存缓冲超过阈值时自动落盘到临时文件，避免大文件把 Node 进程内存打爆。

### 5.4 内容寻址去重（Content-Addressed Dedup）

所有响应最终都要经过 `serializeToWARC`：

1. 计算 payload 的 SHA-256（`warcPayloadDigest`）。
2. 用哈希查 `RedisDedupeIndex.getHashDupe(hash)`：
   - 先查全局共享表 `DUPE_ALL_HASH_KEY`（跨爬取），未命中再查当前爬取自己的哈希表（`h:{crawlId}`，处理"单次爬取内跨 URL 但同内容"的情况）。
3. **命中**：把已经生成的 `response` record 转换为 `revisit` record（只保留 headers + 指向原始记录的引用，丢弃 body），并记录跨 WACZ 的依赖关系（`addDupeCrawlDependency`）。
4. **未命中**：正常写入完整 `response` record，并把新哈希写入当前爬取自己的哈希表（`addHashNew`，此时还未提交到全局共享表）。

### 5.5 两阶段提交式的跨爬取去重

- 爬取开始：`addCrawlForDedupe()` 把 crawlId 加入 `DUPE_UNCOMMITTED` 集合（除非 `--dedupeConcurrent` 直接走 autoCommit）。
- 爬取正常结束（`postCrawl` 里 `finalExit` 分支）：`commitDedupeDone()` 遍历本次爬取的哈希表，逐个 `hsetnx` 进全局表，然后把 crawlId 从 `DUPE_UNCOMMITTED` 移到 `DUPE_ALL_CRAWLS`。
- 爬取被取消/失败：`clearUncommitted()` 直接删除本次爬取贡献的所有哈希（不影响全局表，因为从未提交）。

这保证了"未完成的爬取不会污染跨爬取去重索引"，是简化爬虫系统里几乎不会考虑到的正确性细节。

## 六、WARC/WACZ 落盘

### 6.1 WARCWriter：串行队列 + 按体积滚动

```js
warcQ = new PQueue({ concurrency: 1 });   // 保证同一时刻只有一个写操作在进行
writeRecordPair(...)  → addToQueue(() => this._writeRecordPair(...))
```

- 每次写入前检查 `offset >= rolloverSize`（默认 1GB），超过则关闭当前文件、开启新文件（文件名带时间戳）。
- 每条 WARC 记录写入的同时，如果配置了 `warcCdxDir`，会用 `CDXIndexer` 同步生成 CDX 索引行并写入独立的 `.cdx` 文件——索引与数据同步生成，而不是事后单独扫描 WARC 重建索引（节省一次全量 IO）。

### 6.2 WACZ 打包

`postCrawl()` 阶段：先 `mergeCDXJ()` 合并所有分散的 CDX 索引（>50KB 自动 gzip），再由 `generateWACZ()` 把 `archive/`、`indexes/`、`pages/` 等目录打包为标准 WACZ（zip）文件，同时写入 `datapackage.json`（含去重依赖关系 `relation.requires`）。

### 6.3 磁盘水位预测

`checkDiskUtilization()` 不只看"当前磁盘用了多少"，还会**预测生成 WACZ/合并 WARC 后大概还需要多少额外空间**（`combineWARC && generateWACZ` 时预留 4 倍当前归档目录大小的余量），提前触发 `InterruptReason.DiskUtilization` 优雅停止，而不是等到磁盘写满才抛异常。

## 七、Behavior（页面行为）执行机制

1. 浏览器启动后，通过 `page.evaluateOnNewDocument()` 把 `browsertrix-behaviors` 打包后的 JS（`btrixBehaviors`）和用户自定义 behavior 脚本一起注入到每个新文档（保证 SPA 内部跳转也能重新拿到注入代码）。
2. `self.__bx_behaviors.selectMainBehavior()` 在页面侧根据每个 behavior 类的 `isMatch()` 静态方法选出当前页面应使用的"主行为"（site-specific 优先于通用 Autoscroll）。
3. Node 侧通过 `runBehaviorsInFrame()` 对每个 frame 分别调用 `self.__bx_behaviors.run()`，并监听 `framenavigated` 事件动态给新出现的 iframe 也补跑一次（`runBehaviors()` 里的 `attachIframe`）。
4. behavior 内部是一个异步生成器（`async* run(ctx)`），每 `yield` 一次即上报一次状态到 Node 侧日志（通过 `page.exposeFunction` 暴露的 `BehaviorLogFunc`），因此行为执行可以被外部超时机制（`behaviorTimeout`）随时安全打断，不会处于"写一半"的状态。
5. `--failOnContentCheck` 场景下，behavior 可在 `awaitPageLoad()` 钩子里调用 `assertContentValid()`，通过 `ContentCheckFailed` 的 `exposeFunction` 回调到 Node 侧，直接使整个爬取任务失败退出（例如检测到"未登录"页面时，避免产出没有意义的空存档）。

## 八、代理体系

`initProxy()` 统一处理三种代理来源的优先级：单一 `--proxyServer`/`PROXY_SERVER` < 多规则 `--proxyServerConfig`（除非设置 `--proxyServerPreferSingleProxy`）。

对于 `ssh://` 代理，会调用 `runSSHD()` 用 `autossh` 建立本地端口转发隧道（`ServerAliveInterval=10` 保活，`ExitOnForwardFailure=yes` 快速失败），把 SSH 隧道伪装成本地 SOCKS5 代理供浏览器使用，浏览器本身并不知道背后是 SSH。多代理规则（`proxyConfigFile`）按正则匹配 host 到不同代理，在 `getProxyDispatcher()` 中被 undici 请求和 Chrome `--proxy-server` 参数复用同一套匹配逻辑。

## 九、CLI 参数与配置的合并策略

`argParser.ts` 使用 `yargs` 定义 176 个选项，支持三种输入来源并存：命令行参数 > YAML 文件（`--config`）> stdin（`--config stdin`，用于容器化场景不便挂载文件时通过管道传入）。所有参数最终被解析为强类型的 `CrawlerArgs` 接口，其余模块通过 `this.params.xxx` 访问，避免了裸的 `process.env` 或全局变量散落各处。

## 十、退出与状态持久化

爬取状态优先级判断（`getFinalCrawlState`）：Finished > Stopped > Canceled，任何时刻 Redis 中的状态位都是唯一真源。`--saveState` 支持 `always`/`never`/自动（仅中断时保存）三种策略，中断时把当前 Redis 队列/pending/failed/extraSeeds 等全部序列化为 YAML（`serialize()`），下次通过 `--config <savedstate>.yaml` 传入即可从断点精确恢复，包括所有已发现但未处理的链接和失败重试计数，不会丢失爬取进度。
