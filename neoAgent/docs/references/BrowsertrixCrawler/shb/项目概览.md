# Browsertrix Crawler 项目概览

> 分析对象：`webrecorder/browsertrix-crawler`（版本 1.14.1，AGPL-3.0-or-later）
> 分析目的：吃透一个生产级、高保真度的浏览器爬虫系统的架构设计，为自研爬虫项目提供借鉴

## 1. 这是一个什么项目

Browsertrix Crawler 不是一个"抓数据"的爬虫，而是一个**网页高保真存档（Web Archiving）系统**。它的目标不是提取结构化数据，而是**完整、忠实地记录一个网页被浏览器加载和运行的全过程**（包括所有网络请求/响应、JS 执行产生的动态内容、视频音频流等），并把这个过程封装成标准格式（WARC/WACZ），使得多年后仍然可以在 [ReplayWeb.page](https://replayweb.page) 等工具中"重放"这个网站，就像当时用浏览器访问一样。

它是 Webrecorder 公司 [Browsertrix](https://browsertrix.com) 云服务（SaaS 网页存档平台）的核心引擎，本体开源、单机可用，同时也支持在 Kubernetes 集群中大规模分布式运行。

它的前身服务于 [Zimit](https://github.com/openzim/zimit)（配合 Kiwix 做离线知识库）项目，后独立成为 Webrecorder 的核心组件，经过了较长时间的生产打磨（当前是 1.x 大版本，说明经历过大的架构演进和收敛）。

## 2. 技术栈

| 层面 | 选型 | 说明 |
|---|---|---|
| 语言 | TypeScript（ESM，`node --experimental-global-webcrypto`） | 全量类型标注，`tsc` 编译到 `dist/` |
| 浏览器自动化 | Puppeteer-core + Chrome DevTools Protocol (CDP) | 直接用 CDP 而非仅 Puppeteer 高层 API，深入控制网络层 |
| 浏览器内核 | Brave Browser（基于 Chromium，默认自带广告/跟踪拦截 Shields） | 通过独立的 `browsertrix-browser-base` 基础镜像提供 |
| 容器化 | 单一 Docker 镜像，`ENTRYPOINT` 三个子命令：`crawl` / `qa` / `create-login-profile` / `indexer` | 通过 Dockerfile 的 `MINIMIZE_IMAGE_SIZE` 参数支持"快速构建"和"极小镜像"两种模式 |
| 分布式协调 | Redis（ioredis），大量自定义 Lua 脚本做原子操作 | 单机自带内嵌 Redis，也可接外部/集群 Redis，是多 worker、多 pod 协作的核心 |
| 存档格式 | WARC/WARC.gz（ISO 28500 标准）+ WACZ（zip 打包 + CDXJ 索引） | 通过 `warcio` 库读写，遵循 Web 存档社区标准规范 |
| 页面行为自动化 | `browsertrix-behaviors`（独立子项目，注入页面的 JS 行为库） | 自动滚动、自动播放、自动点击、站点定制脚本 |
| 回放/校验 | `@webrecorder/wabac`（浏览器内回放引擎） | 复用同一套 rewriting 逻辑，用于 HLS/DASH/HTML 等内容重写 |
| 对象存储 | S3 兼容存储（`@aws-sdk/client-s3`） | WACZ 产物上传、断点续传友好设计 |
| 网络层 | `undici`（直接 HTTP 请求）+ 自定义代理 Dispatcher | 支持 HTTP/SOCKS5/SSH 隧道代理 |
| 测试 | Jest + 大量端到端 Docker 集成测试 | 测试直接跑 `docker run` 验证真实爬取行为，而非仅 mock 单测 |

## 3. 代码规模与模块划分

核心源码位于 `src/`，约 15,000+ 行 TypeScript，按职责清晰拆分：

```
src/
├── main.ts                 # 进程入口：信号处理(SIGINT/SIGTERM/SIGABRT)、启动 Crawler/ReplayCrawler
├── crawler.ts               # 核心类 Crawler（~2900行）：爬取生命周期总控
├── replaycrawler.ts          # QA 模式：基于已有 WACZ 重放并做质量对比
├── create-login-profile.ts   # 交互式登录，生成可复用的浏览器 Profile
├── indexer.ts                # 独立的去重索引维护工具（导入/提交/清理 WACZ 到 dedupe 索引）
└── util/
    ├── worker.ts             # PageWorker：单个浏览器窗口的工作循环、页面复用、崩溃隔离
    ├── state.ts               # RedisCrawlState + RedisDedupeIndex（~1660行）：分布式队列、去重、状态持久化，大量 Lua 脚本
    ├── recorder.ts            # Recorder（~2100行）：CDP 网络事件 → WARC 记录的核心管道
    ├── warcwriter.ts          # WARC 文件滚动写入 + CDX 索引同步生成
    ├── browser.ts             # 浏览器启动参数、Profile 加载、多窗口/CDP会话管理
    ├── seeds.ts                # ScopedSeed：URL scope（作用域）规则引擎
    ├── sitemapper.ts           # sitemap.xml / sitemap index 解析
    ├── robots.ts               # robots.txt 抓取、解析、缓存、请求合并
    ├── blockrules.ts           # 页面资源级别的 URL 拦截规则（区别于 scope 排除规则）
    ├── reqresp.ts              # 单次请求/响应的完整状态机封装
    ├── originoverride.ts       # 按 origin 重写请求目标（镜像/代理场景）
    ├── proxy.ts                # HTTP/SOCKS5/SSH隧道代理统一抽象，多代理规则匹配
    ├── screencaster.ts         # WebSocket 实时画面推送（screencast）
    ├── screenshots.ts          # 截图（视口/整页/缩略图）
    ├── textextract.ts          # 基于 CDP snapshot 的文本抽取
    ├── flowbehavior.ts         # DevTools Recorder JSON User Flow 回放支持
    ├── wacz.ts                 # WACZ 打包、datapackage.json 依赖关系生成
    ├── storage.ts              # S3 上传、磁盘用量预测、文件名模板
    ├── healthcheck.ts          # K8s 健康检查 HTTP 端点
    ├── redis.ts                # Redis 连接与错误退出策略
    ├── argParser.ts            # yargs CLI 参数定义（176 个 `.option()`）与 YAML 配置合并
    ├── constants.ts            # 退出码、超时时间、枚举等所有魔法数字的唯一出处
    ├── logger.ts                # 结构化 JSON 日志 + 致命错误统一退出通道
    └── timing.ts                # 统一超时包装 timedRun()
```

## 5. 命令行入口（多态 CLI）

单一 Docker 镜像通过软链接暴露 4 个子命令，复用同一套底层能力：

- `crawl`：标准爬取/存档
- `qa`：对已有 WACZ 做"重放质量分析"（截图/文本/资源计数三维比对）
- `create-login-profile`：交互式生成登录态浏览器 Profile（配合 noVNC 网页可视化操作）
- `indexer`：维护跨爬取的去重索引（导入历史 WACZ、提交/撤销未完成爬取、清理无用哈希）

## 6. 定位总结

这是一套**面向"存档保真度"而非"数据提取效率"** 的爬虫系统，几乎所有设计决策都围绕两个目标展开：

1. **完整性**：不遗漏任何被浏览器实际请求过的资源，哪怕是流媒体分片、Service Worker 缓存、懒加载图片。
2. **可重放性**：产出的存档能在离线环境下被精确重放，因此对 URL 归一化、去重、内容重写（HLS/DASH manifest 改写）有极高要求。

这与"爬取结构化数据"的传统爬虫（如 Scrapy）在设计哲学上有本质区别，但其在**并发调度、状态管理、容错恢复、云原生集成**方面的工程实践，对任何类型的爬虫系统都极具参考价值，详见 `项目亮点.md`、`项目实现原理.md` 和 `借鉴建议.md`。
