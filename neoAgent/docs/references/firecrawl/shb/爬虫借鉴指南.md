# 面向自研爬虫的借鉴指南

本文档是"看完 Firecrawl 之后，我该怎么改自己的爬虫"的落地清单。按 **投入产出比从高到低** 排序，每一条都给出可以直接抄的最小实现思路（不限定语言，Go/Python/Node 通用）。

---

## 优先级 P0：立刻能做、成本极低、收益极高

### 1. URL 归一化去重（抄 `generateURLPermutations` 思路）

**问题**：大部分自研爬虫的去重就是 `set[url] = true`，但 `http://a.com` 和 `http://a.com/` 和 `https://www.a.com` 会被当成三个不同 URL 重复抓取。

**做法**：定义一个 `canonicalize(url) string` 函数：
1. 统一协议（可选：把 http 视为等价于 https，取决于你的场景）
2. 去掉/统一 `www.` 前缀
3. 去掉末尾多余的 `/`、`index.html`、`index.php`
4. 排序/清理 query 参数（如果 `ignoreQueryParameters`）
5. 清空无意义的 hash（除非是 SPA 路由 `#/xxx`）

去重时只存 `canonicalize(url)` 到 Set/Bloom Filter 里。这一条几乎零成本，但能立刻消除"重复抓取同一页面"的浪费。

### 2. 拒绝原因可解释（抄 `DenialReason` 思路）

**问题**：爬虫过滤掉一个 URL 时，日志只打"skip"，出问题时很难排查"为什么这个我明明想要的页面没被抓"。

**做法**：给每种过滤规则一个明确的原因常量+可读文案，过滤时把 `(url, reason)` 记录到一个 map/表里，暴露一个查询接口或写进日志：

```go
type DenialReason string

const (
    ReasonDepthLimit    DenialReason = "超出最大深度限制"
    ReasonExcludePath   DenialReason = "命中exclude规则"
    ReasonRobotsTxt     DenialReason = "被robots.txt禁止"
    ReasonFileType      DenialReason = "非文档类文件后缀"
)
```

调试爬虫"为什么少抓了页面"时，这个记录能帮你节省大量时间。

### 3. 错误分类而非"一刀切重试"

**问题**：很多爬虫遇到任何错误都是"重试3次，还不行就跳过"，不区分错误类型。

**做法**：把错误分成几类，分别处理：
- **应该换策略重试**（如 403/429 疑似反爬）→ 升级到更强的抓取方式（换代理/换UA/加渲染）
- **应该立刻放弃**（如 DNS 解析失败、SSL证书过期且用户没关闭校验）→ 不要浪费时间重试
- **应该降级但继续**（如某个可选字段抽取失败）→ 记录 warning，继续流程

用 Go 举例可以定义一个 sentinel error 集合 + `errors.Is`/`errors.As` 判断：

```go
var (
    ErrLikelyBlocked = errors.New("likely blocked by anti-bot")
    ErrPermanentFail = errors.New("permanent failure, do not retry")
)
```

### 4. 关键路径埋点（哪怕只是结构化日志）

**问题**：不知道"这次抓取慢在哪一步"（DNS？TLS握手？渲染？解析？）。

**做法**：不需要一开始就上 OpenTelemetry，先做到：每次抓取记录 `{url, engine_used, duration_ms, status_code, retry_count, cache_hit}` 这样一条结构化日志（JSON），跑一段时间后你就能用简单的 SQL/grep 分析出"哪类站点最慢"、"哪个引擎成功率最低"。

## 优先级 P1：值得投入 1-2 周实现的架构改进

### 5. 多策略抓取仲裁器（抄"瀑布+竞速"思路，简化版）

不需要 Firecrawl 那么复杂的 Promise.race 竞速，一个简化版的"分级重试仲裁器"就很有价值：

```go
type Strategy struct {
    Name     string
    Quality  int              // 越高越优先
    Fetch    func(url string) (*Result, error)
    Timeout  time.Duration
}

func ScrapeWithFallback(url string, strategies []Strategy) (*Result, error) {
    sort.Slice(strategies, func(i, j int) bool {
        return strategies[i].Quality > strategies[j].Quality
    })
    var lastErr error
    for _, s := range strategies {
        ctx, cancel := context.WithTimeout(context.Background(), s.Timeout)
        result, err := s.Fetch(url) // 用 ctx 控制超时
        cancel()
        if err == nil && isGoodResult(result) {
            return result, nil
        }
        lastErr = err
        if isPermanentError(err) {
            break // 不再继续尝试
        }
    }
    return nil, fmt.Errorf("all strategies failed: %w", lastErr)
}
```

策略从便宜到贵排列：`纯HTTP请求` → `带Cookie/Session的HTTP` → `TLS指纹伪装客户端(如 utls/curl_cffi)` → `无头浏览器`。质量判定函数 `isGoodResult`可以参考 Firecrawl 的思路：**内容长度是否达标 + HTTP状态码是否正常 + 是否有页面级错误标记**，三者综合判断，而不是只看状态码。

**进阶（如果你的并发量大、对延迟敏感）**：把"重试下一个策略"改成"超时后并行发起下一个策略，谁先成功用谁"（即 Firecrawl 的竞速瀑布），能显著降低 P95 延迟，代价是偶尔会浪费一次多余的请求——这是用"资源"换"延迟"的经典权衡，建议先上线简单版，观察到延迟瓶颈后再升级。

### 6. 团队/来源维度的并发限流（不只是全局限流）

**问题**：很多爬虫只有一个全局并发数控制，导致"某个客户/某个任务疯狂抓取"把整个爬虫集群的资源占满，影响其他任务。

**做法**：参考 `team-semaphore.ts`，用 Redis + Lua 脚本实现一个"按 key（可以是用户ID/任务ID/目标域名）维度"的分布式信号量：

```lua
-- acquire.lua (简化版, 实际生产要处理好过期清理)
local key = KEYS[1]
local holder = ARGV[1]
local limit = tonumber(ARGV[2])
local ttl = tonumber(ARGV[3])
local now = redis.call('TIME')[1]

redis.call('ZREMRANGEBYSCORE', key, '-inf', now - ttl)  -- 清理过期持有者
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, holder)
    return {1, count + 1}
else
    return {0, count}
end
```

这一条对"多租户爬虫平台"或"同时跑多个采集任务"的场景价值极大——能避免一个任务拖垮全局。

### 7. 按目标站点动态学习抓取参数（`urlSpecificParams` 思路）

**问题**：不同网站需要不同的抓取策略（有的需要渲染JS、有的需要特定UA、有的有已知的反爬规则），硬编码在代码里难以维护。

**做法**：维护一张"域名 → 抓取参数覆盖"的配置表（可以是数据库表，不需要复杂的机器学习）：

```json
{
  "example.com": { "engine": "headless_browser", "wait_ms": 2000, "user_agent": "..." },
  "another.com": { "engine": "http_only", "extra_headers": {"Referer": "..."} }
}
```

抓取前查一次这张表，命中则覆盖默认策略。运营一段时间后，把"总是失败必须用重型引擎才能成功"的域名手动录入这张表，可以省掉每次都要"先试轻量再升级"的浪费。

### 8. 简单的"缓存层"而非每次都抓

**问题**：如果你的场景是"监控/聚合类"（需要重复抓同一批网站），每次都完整抓取是巨大的浪费。

**做法（简化版 Firecrawl 索引缓存）**：
1. 存储层：`(url_hash, fetched_at, content_hash, storage_path)` 一张表 + 对象存储（S3/OSS/本地磁盘均可）存正文。
2. 查询时先查这张表，如果 `now - fetched_at < max_age`（可以按域名配置不同的 max_age，更新频繁的站点给更短的缓存期），直接返回缓存内容。
3. 可选：加一个**负缓存**（记录"最近确认某URL不存在/抓取失败"），避免对死链接反复发起请求。

不需要一开始就上 Dragonfly/Redis 分布式缓存，单机场景一个 SQLite/Postgres 表 + 内存 LRU 就能拿到 80% 的收益。

## 优先级 P2：规模化后再考虑的架构决策

### 9. 队列选型的取舍参考

Firecrawl 从 BullMQ(Redis) 走向自研 FoundationDB 队列，本质原因是：
- Redis 队列在**超大规模**、**强一致性分组任务**（一个crawl下几万个子任务的整体状态管理）场景下运维复杂度陡增。
- 需要**跨语言/跨进程**的任务分发和"任务组"语义（不是简单的生产者消费者）。

**给你的建议**：如果你现在的量级是"单机几个worker、几千并发任务"，**不要**一开始就自建复杂队列，优先用成熟方案：
- 中小规模：Redis + 简单的 List/ZSet 实现（甚至用现成的 asynq(Go)/Celery(Python)/BullMQ(Node)）
- 需要"任务组""事务性出队""强一致性"时，再考虑上 Postgres 的 `SELECT ... FOR UPDATE SKIP LOCKED` 模式做队列（这是一个被低估的简单方案，很多场景不需要上 FoundationDB 那么重的基础设施）

### 10. 可序列化的类型化错误（跨进程/跨语言场景）

如果你的爬虫是"调度进程 + 独立worker进程"架构（哪怕只是简单的"主进程发redis消息，worker消费"），务必设计一套**错误也能带类型信息传输**的机制，而不是把错误 stringify 成一行文本就扔了。

Go 的实现思路（用 JSON tag 区分错误类型）：

```go
type ScrapeError struct {
    Code    string `json:"code"`    // "SSL_ERROR" / "DNS_ERROR" / "BLOCKED"
    Message string `json:"message"`
    Details map[string]any `json:"details,omitempty"`
}

func (e *ScrapeError) Error() string { return e.Message }

// worker 端反序列化后可以做:
if scrapeErr.Code == "SSL_ERROR" { /* 走特定处理分支 */ }
```

### 11. 开源可自托管 + 闭源增值层的产品分层（如果你要做成产品/对外服务）

如果你的爬虫未来要对外提供服务或开源，参考 Firecrawl 的"能力开关"模式：核心抓取/解析逻辑保持通用可自托管，把"反爬引擎/全网缓存/威胁情报"这类需要持续运营成本的能力做成可选的付费/云端组件，通过 feature flag（环境变量/配置开关）自然降级，而不是散落 `#ifdef` 式硬编码判断。

## 反面案例警示（Firecrawl 代码里能看到的"教训"）

阅读代码过程中能看到不少体现"踩过坑才加上"的防御性设计，这些也值得你提前规避：

1. **`shouldSkipMarkdownCheck`**（`scrapeURL/index.ts` 里对 >300KB 的 HTML 跳过 markdown 质量校验）——说明"每次都做完整内容转换来判断成功与否"在大页面场景下会拖垮性能，**质量判定逻辑本身也要考虑性能代价**。
2. **`errorLimit = 3`（Fire-Engine 轮询容错）**——轮询型异步任务一定要设置"连续失败N次就放弃"的熔断，否则一个远端服务的抖动会让你的爬虫无限空转。
3. **`negativeHit`/自愈缓存清理**——缓存系统一定要考虑"缓存和真实数据不一致"的场景（这里是 GCS 文档被删但索引还在），否则会有一批 URL 永远返回错误却无法自愈。
4. **`priorityThreshold` 判断引擎能力是否达标，而非"完全匹配才选中"**——过于严格的匹配逻辑会导致"没有引擎百分百满足所有 flag 时直接抛错"，适当的"够用就行"容错阈值能让系统更健壮。
5. **`AbortManagerThrownError` 区分 tier**——超时之后一定要能分清"是这一层超时该重试，还是上层已经决定放弃了"，否则会出现"外层已经放弃了，内层还在傻乎乎重试"的资源浪费。

## 建议的实施路线图

如果你打算真的动手改造自己的爬虫，建议按以下顺序推进（每一步都是独立可交付的）：

1. **Week 1**：URL 归一化去重 + 拒绝原因日志（P0第1、2条）—— 立刻减少无效抓取
2. **Week 2**：错误分类 + 结构化埋点日志（P0第3、4条）—— 为后续优化提供数据基础
3. **Week 3-4**：多策略抓取仲裁器（P1第5条）—— 提升成功率、降低平均成本
4. **按需**：并发限流（P1第6条，多租户/多任务场景）、缓存层（P1第8条，重复抓取场景）
5. **规模化后再评估**：队列选型升级、错误跨进程序列化（P2）

不建议一开始就照搬 Firecrawl 的全部架构复杂度——它的复杂度是"服务数万付费客户、日抓取量级达到数十亿页面"这个规模逼出来的，你的爬虫应该按照自己的真实规模和真实痛点，从上面的清单里挑选性价比最高的几条先落地。
