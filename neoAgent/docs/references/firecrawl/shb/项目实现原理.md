# Firecrawl 项目实现原理剖析

本文档深入到关键子系统的实现细节，配合代码引用，帮助你理解"为什么这么设计"而不只是"设计了什么"。

## 一、单 URL 抓取管线：`scrapeURL`

### 1.1 整体分层

```
scrapeURL(id, url, options, internalOptions, costTracking)
  └─ buildMetaObject()           构造不可变(近似)的 Meta 上下文对象
  └─ 威胁情报检查 checkUrl()       抓取前先判定域名是否恶意
  └─ robots.txt 检查
  └─ scrapeURLLoop(meta)          【核心】引擎选择+竞速+瀑布
       └─ buildFallbackList()     生成按质量排序的引擎候选队列
       └─ scrapeURLWithEngine()   实际调用某个引擎的 handler
       └─ postprocessors[]        后处理（如 youtube 转写）
       └─ executeTransformers()   转换器管道：html→markdown→llm抽取→...
  └─ 外层 while 循环：捕获 AddFeatureError/RemoveFeatureError/PDFAntibotError
     等"信号型异常"，动态调整 featureFlags 后重新执行 scrapeURLLoop
```

**关键设计**：`Meta` 对象承载一次抓取的全部上下文（URL、options、featureFlags、abort 信号、pdf/document 预取缓存等），除了 `logger` 和少量运行时字段外基本不可变，这让整个管线的数据流非常容易追踪——不会有"某个深层函数偷偷改了全局状态"的问题。

### 1.2 Feature Flag 驱动的引擎选择算法

`buildFallbackList()`（`engines/index.ts`）的核心算法：

1. 把请求 options 翻译成一组 `FeatureFlag`（如 `actions`/`screenshot`/`mobile`/`stealthProxy`），每个 flag 有一个"优先级权重"（`featureFlagOptions`）。
2. 对所有引擎，计算它能满足多少 flag（`supportScore`），要求 `supportScore >= 所需权重总和的一半`（`priorityThreshold`）才有资格入选——这避免了"引擎支持了一个无关紧要的 flag 就被选中"的问题。
3. 剩下候选引擎优先选 `quality > 0` 的（正数是"正常引擎"，负数是"退化/特殊引擎"，如 PDF/文档解析器）。
4. 按 `supportScore` 降序、`quality` 降序最终排序，生成 fallback 队列。
5. 特殊短路：命中 X/Twitter 或 Wikimedia 域名时，直接把引擎队列替换成对应专用引擎（`x-twitter`/`wikipedia`）；`lockdown`（合规锁定模式）或 `agentIndexOnly` 时强制只用 `index` 引擎，不触碰真实网络。

### 1.3 竞速 + 瀑布调度（Waterfall Race）

`scrapeURLLoop`（`scrapeURL/index.ts`）的调度循环本质是一个"渐进式并发池"：

```
remainingEngines = [引擎1(最优), 引擎2, 引擎3, ...]

while remainingEngines 不空:
    取出下一个引擎，加入 enginePromises 并发池
    Promise.race([
        ...enginePromises,                    # 已启动的所有引擎
        setTimeout(waitUntilWaterfall) → 拒绝, # 触发"该启动下一个了"的信号
        setTimeout(globalTimeout) → 拒绝       # 总超时熔断
    ])
    
    若某引擎报错 → 从并发池移除该 promise，其余继续 race
    若超时信号 → break 内层循环，外层 while 启动下一个引擎（不取消已启动的）
    若某引擎成功 → 整体返回，其余引擎的 promise 被丢弃(不 await，但也不强制 cancel)
```

`waitUntilWaterfall = getEngineMaxReasonableTime(引擎) + 固定延迟`，即"每个引擎有一个预估合理耗时，超过这个时间还没回来，先把下一个候选也跑起来，谁先成功用谁"。这比"傻等引擎A失败再试B"快得多，尤其在 A 引擎"偶尔会很慢但不一定失败"的场景下（比如无头浏览器排队）。

### 1.4 Abort/超时的分层传播（AbortManager）

`lib/abortManager.ts` 实现了一个三层信号量级（`tier: "external" | "scrape" | "engine"`）：

- `external`：调用方主动取消（如 HTTP 连接断开）
- `scrape`：整个 scrape 的超时（`options.timeout`）
- `engine`：单个引擎调用的超时（竞速循环里的 `snipeAbort`）

`AbortManager.child()` 可以派生出"继承父级所有 abort 条件 + 新增自己特有条件"的子管理器，任何一层触发都会包装成 `AbortManagerThrownError(tier, inner)` 向上抛，上层可以根据 `tier` 判断"是该继续瀑布下一个引擎"还是"整个请求都得失败"。这是一个通用性很强的多层超时管理模式。

### 1.5 转换器管道（Transformers）

`transformers/index.ts` 里的 `transformerStack` 是一个固定顺序的函数数组，每个转换器接收 `(meta, document)`，返回修改后的 `document`：

```
rawHtml → HTML清洗(deriveHTMLFromRawHTML) → Markdown(deriveMarkdownFromHTML)
  → 内容清理/PII脱敏 → 链接/图片提取 → 品牌信息提取 → 元数据提取
  → 商品/菜单结构化(垂直领域) → 写入全网索引/搜索索引
  → LLM结构化抽取 → 确定性JSON → 摘要 → 问答 → Agent
  → 移除base64图片(省流量) → diff(变更追踪) → 音频/视频转写
  → coerceFieldsToFormats(按用户请求的formats裁剪最终字段)
```

**亮点**：每个转换器内部都有"是否需要执行"的判断（`hasFormatOfType`），不需要的直接 no-op 返回，整个链条是可预测、可测试的纯函数序列（`index.test.ts` 对这条链单独做了顺序回归测试）。最后一步 `coerceFieldsToFormats` 统一按用户声明的 `formats` 字段做"清场"——多算的字段会被删除并打 warn 日志（这是个很好的"防止意外多返回敏感/多余数据"的兜底机制）。

## 二、整站爬取：Crawl 的状态机

### 2.1 存储模型

一次 crawl 在 Redis 里对应一组 key（`lib/crawl-redis.ts`）：

| Key | 类型 | 作用 |
|---|---|---|
| `crawl:{id}` | String(JSON) | `StoredCrawl` 主体：原始URL、爬取选项、team信息 |
| `crawl:{id}:jobs` | Set | 所有已派发的子任务 ID |
| `crawl:{id}:jobs_done` | Set | 已完成的子任务 ID |
| `crawl:{id}:jobs_donez_ordered` | ZSet(按完成时间) | 支持"按顺序分页获取已完成结果" |
| `crawl:{id}:visited` / `visited_unique` | Set | 去重（含URL排列组合归一化 与 精确URL两套） |
| `crawl:{id}:kickoff:finish` | String | sitemap 阶段是否已经完成"启动扫描" |
| `active_crawls` | Set | 全局活跃 crawl 索引，用于后台巡检 |

所有 key 都设置 24 小时 TTL，`finishCrawl()` 完成时主动清理 `visited`/`visited_unique`（节省内存）并把威胁拦截记录（ZDR 合规要求）也一并删除。

### 2.2 URL 发现两条路径

1. **Sitemap 优先**：`WebCrawler.tryGetSitemap()` 并行抓取 `robots.txt` 里声明的所有 sitemap + 猜测的 `/sitemap.xml`，还会智能识别"当前是子域名"的情况去同时抓主域名的 sitemap 并按 hostname 过滤。
2. **正文链接提取**：抓到一个页面后，从其 HTML 中提取 `<a>` 标签（`extractLinksFromHTMLRust`，Rust 实现，失败时降级到 Cheerio），作为新的候选 URL 反馈回爬取队列。

两条路径产出的 URL 都要经过统一的 `filterLinks`（Rust 实现，`@mendable/firecrawl-rs` 的 `filterLinks`）过滤：深度限制、include/exclude 正则、robots.txt、跨域、backward crawling、文件类型黑名单、协议白名单——每种拒绝都有详细原因记录到 `denialReasons` Map，最终会展示在 crawl 状态查询接口里，方便用户排查"为什么某个页面没被抓到"。

### 2.3 去重的两级策略

- `crawl:{id}:visited`：如果开启 `deduplicateSimilarURLs`，存的是 `generateURLPermutations(url)[0].href`（即该 URL 所有等价形式中排序后的"代表元"）；否则存精确归一化后的 URL。
- `crawl:{id}:visited_unique`：始终存精确归一化 URL，用于给用户返回真实抓取过的 URL 列表统计。

`lockURL()` 用一次 Redis pipeline 同时完成"检查是否超过 limit"、"SADD 判断是否新 URL"、"更新 visited_unique"，保证高并发下多个 worker 同时发现同一个 URL 时只有一个会真正入队。

### 2.4 完成判定

`isCrawlFinished()`：`jobs_done` 集合大小 == `jobs` 集合大小，且 sitemap 阶段的 kickoff 也已完成（`sitemap_jobs_done == sitemap_jobs`）。这个"双阶段完成"判定避免了"sitemap 还没解析完就误判 crawl 已完成"的竞态问题。

## 三、队列与并发控制

### 3.1 从 BullMQ 到 NuQ 的演进

- **BullMQ(Redis)**：早期/仍在用于非核心队列（`generateLlmsTxtQueue`/`deepResearchQueue`/`billingQueue` 等），基于 Redis List + Sorted Set 实现，简单可靠但在超大规模、强一致性分组任务管理上有局限。
- **NuQ**：自研队列抽象层，`nuq-router.ts` 按 `teamId` 决定走 **Postgres 后端** 还是 **FoundationDB 后端**（`isFdbTeam`），支持灰度迁移。核心抽象在 `nuq-fdb/queue.ts`（`NuQFdbQueue`）：
  - **分组任务（Job Group）**：一次 crawl 的所有子任务是一个 group，可整体查询/取消/收尾。
  - **Slot（外部槽位）**：`NuqFdbExternalSlots` 用于"同步抓取占用配额"场景（用户发起同步 scrape 时也要计入团队并发限制，即使它不走标准队列）。
  - **Sweeper（清扫器）**：`NuqFdbSweeper` 后台巡检超时/僵死任务，防止 worker 崩溃后任务永久卡住。

### 3.2 团队级并发信号量（`team-semaphore.ts`）

用 Redis + Lua 脚本实现的分布式信号量：

- `acquire`：原子地检查当前持有者数量是否小于 `limit`，是则插入并返回成功。
- `heartbeat`：持有者定期续约（`SEMAPHORE_TTL = 30s`），证明"我还活着，没有崩溃占着坑不用"。
- `acquireBlocking`：带指数退避 + 随机抖动（jitter）的阻塞式获取，避免"信号量刚释放，所有等待者同时冲进来"的惊群效应。
- **双后端镜像**：`mirrorSlotAcquire`/`mirrorSlotRelease` 在信号量真正生效的同时，还会往 FDB 或 PG 的"镜像账本"里占一个槽位，这样同步请求（bypass 队列）产生的并发消耗，也能被异步队列看到，两边流量能公平分享同一个并发上限。

### 3.3 计费闭环

`billTeam()` 的执行顺序体现了"先扣费、失败再退款"的最终一致性思路：

```
1. autumnService.trackCredits()   先在计费系统里标记扣费(trackedInRequest)
2. queueBillingOperation()        排队做真正的数据库计费记录（异步批处理，减少DB压力）
3. 若 (2) 失败 且 (1) 成功过        autumnService.refundCredits() 补偿退款
```

这是一种"乐观执行 + 补偿事务"模式，配合 `services/billing/batch_billing.ts` 的批量聚合写入，在保证计费准确性的同时避免每次抓取都同步写一次计费数据库造成性能瓶颈。

## 四、全网索引缓存的实现原理

### 4.1 三层查询链路

```
scrapeURLWithIndex(meta)
  1. 计算 maxAge（显式指定 / 域名动态学习 / 默认2天），带200ms超时保护，超时直接退化用默认值
  2. deriveIndexVariantKey()：把 (urlHash, isMobile, blockAds, isStealth, country, languages) 哈希成一个变体key
  3. 若开启 useIndexCache：查 Dragonfly（150ms超时），命中则本地过滤 maxAge/minAge/screenshot能力等约束
  4. 缓存未命中/过滤后为空 → 查负缓存（确认"近期已知无数据"，跳过DB）
  5. 都没有 → 查 Postgres（index_get_recent_5），命中则回写缓存/负缓存
  6. 拿到 URL→索引ID 的映射后，去 GCS 下载实际文档 JSON
  7. 文档不存在（GCS被删了但索引没删）→ 自愈：清除缓存条目，抛 EngineError 触发下一个引擎
```

### 4.2 为什么要"负缓存"

对于"每天抓几万个新域名，其中大部分从没被抓过"的场景，如果没有负缓存，每次都要打一次 Postgres 才能确认"没有缓存"，这会浪费大量 DB 查询。负缓存记录"某个 key 在 [dbStart-maxAge, dbStart] 这个时间窗口内确认为空"，之后同 key 的请求只要还在这个窗口内就可以直接跳过 DB。

### 4.3 写入侧：`sendDocumentToIndex`

一次成功抓取后，是否要写入索引由一长串条件把关（`shouldCache`）：用户是否要求存缓存（`storeInCache`）、是否 ZDR（零数据保留，绝不允许缓存）、是否本身就来自缓存（避免"缓存的缓存"）、是否来自 Exchange（Exchange 交付的内容有独立的账本机制，不能在 Firecrawl 侧落地）、是否有自定义 headers/actions/profile（这些让结果变得"千人千面"，不适合共享缓存）。

写入过程本身是 **fire-and-forget 异步**（外层是一个立即 `return document` 之后台 `(async () => {...})()` 执行的 IIFE），不阻塞主抓取流程返回给用户，但会：
1. 生成一个 `indexId` UUID，同步挂到 `document.metadata.indexId` 上（供后续用）。
2. 把完整文档（html/json/screenshot等）存 GCS。
3. 把索引元数据（URL哈希、URL的多级前缀哈希 `urlSplits`、域名多级前缀哈希 `domainSplits`）写入 Postgres 插入队列。
4. 域名前缀哈希还会触发 `addOMCEJob`（可能是"域名级元数据/信誉"异步计算任务）。

**`urlSplits`/`domainSplits` 的设计意图**：把一个 URL 或域名按层级拆解成多个前缀（如 `a.b.com` → `[com, b.com, a.b.com]`），分别哈希存储，这样可以支持"某个域名下所有页面"或"某个路径前缀下所有页面"的范围查询/统计，而不需要在 Postgres 里对完整 URL 做模糊匹配（性能差）。

## 五、反爬引擎的实现细节

### 5.1 Fetch 引擎（最基础）

`engines/fetch/index.ts` 用 `undici` 发请求，值得学习的细节：
- **字符编码自动探测**：优先用 HTTP 头 `Content-Type` 里的 charset，失败再尝试从 HTML `<meta charset>` 标签里探测，最后兜底 UTF-8 —— 三级降级探测，避免中文站点常见的乱码问题。
- **SSL 错误精确识别**：捕获 `CERT_HAS_EXPIRED` 等具体 error code，转换成语义化的 `SSLError`，而不是让原始的 undici 错误裸露给用户。
- **Mock 回放系统**：`meta.mock`/`saveMock` 支持把真实请求录制下来，之后用录制数据重放，用于自托管测试环境中模拟 Fire-Engine 的效果（不需要真实反爬引擎也能跑通全部测试用例）。

### 5.2 Fire-Engine（Chrome CDP / TLS Client）

`engines/fire-engine/index.ts` 的 `performFireEngineScrape` 是一个"异步任务提交+轮询"的模式：
1. 提交抓取请求，如果 Fire-Engine 返回 `processing`，说明是异步任务，进入轮询循环（`fireEngineCheckStatus`），每 500ms 查一次状态。
2. 轮询循环有**独立的错误容忍窗口**（`errorLimit = 3`）：网络抖动等临时性查询失败允许最多 3 次，超过就放弃并主动调用 `fireEngineDelete` 清理远端任务（避免僵尸任务占用 Fire-Engine 资源）。
3. 拿到结果后自动处理 gzip 解压（透明处理"响应体被压缩"的情况）、JSON content-type 的内层反序列化。
4. **A/B 测试基础设施**：`abTestFireEngine(request)` 支持把一部分流量路由到"分流(split)"或"镜像对比(mirror)"模式——mirror 模式会真实抓取两份结果做对比（`scheduleABComparison`），用于新版本引擎上线前的效果验证，这是相当成熟的灰度发布实践。

### 5.3 Action（页面交互）转译层

`waitFor`/`screenshot`/`branding` 等"格式"选项，在 Chrome CDP 引擎里被统一翻译成一个 `actions` 数组（`type: "wait"|"screenshot"|"executeJavascript"|"getCookies"`）再发给 Fire-Engine——即用户声明式的"我要什么格式"被编译成命令式的"按顺序做什么动作"，这是一种典型的"声明式 API → 内部指令序列"的编译层设计，方便后续新增格式而不需要改动引擎调用的核心协议。

## 六、AI 抽取管线

### 6.1 Schema 复杂度驱动的模型选择

`llmExtract.ts` 的 `selectModelForSchema`：检测 schema 字符串里是否含 `$ref`/`$defs`/`definitions`（递归/复杂引用结构）来判定复杂度，复杂 schema 用更强模型（`gpt-4.1`），简单场景用便宜模型（`gpt-4o-mini`）。这是"用最省钱的方式满足质量底线"的典型工程权衡。

### 6.2 多页抽取结果的合并与溯源

场景：Crawl 抓了 50 个页面，每页都做了结构化抽取，怎么合并成一份结果，同时知道每条数据来自哪个页面？

`SourceTracker` 类：
1. `transformResults()`：把每个页面的抽取结果统一转换成 `transformArrayToObject` 格式（区分是"数组输出" 还是"对象输出"两种 schema 形态）。
2. `trackPreDeduplicationSources()`：合并/去重前，先给每条数据记一笔"它在哪些页面的抽取结果里出现过"（用 `JSON.stringify(item)` 做内容级别的比对key）。
3. `mapSourcesToFinalItems()`：最终去重合并完成后，反向映射回"这条最终结果的来源 URL 集合"（`areMergeable` 判断两条记录是否可以视为同一实体的不同信息补充）。

这套机制的价值在于：LLM 抽取天然存在"同一个实体在不同页面上被提取出略有差异的信息"的问题（比如页面A有公司名没有地址，页面B反过来），`mix-schema-objs`/`merge-null-val-objs` 等 helper 负责"信息互补合并"，`SourceTracker` 负责让合并后还能审计溯源。

### 6.3 Deep Research：多轮迭代式调研 Agent

`ResearchStateManager`（`research-manager.ts`）用一个显式状态机管理多轮"搜索→抓取→分析gap→再搜索"的循环：
- `currentDepth`/`maxDepth` 控制迭代轮数上限。
- `failedAttempts`/`maxFailedAttempts` 防止陷入死循环（比如 LLM 一直生成搜索不到东西的查询）。
- `seenUrls` 去重，避免重复抓取同一信息源。
- `findings`/`summaries` 只保留最近 50 条，防止长时间调研导致内存/上下文爆炸。
- 每一步都实时 `updateDeepResearch()` 写回 Redis，前端可以流式展示"当前在做什么"（activities）。

这本质上是一个轻量级的 ReAct（Reasoning + Acting）风格 Agent 循环，用显式状态类（而不是让 LLM 自己维护上下文）管理进度，更可控、更容易加超时/预算护栏。

## 七、错误处理与可观测性

### 7.1 `TransportableError`：让错误可以"坐队列穿越进程"

普通 JS Error 被 `JSON.stringify` 后会丢失原型链信息（`instanceof` 判断失效），这在"API 进程 → Redis 队列 → Worker 进程"的架构里是致命的。Firecrawl 的解法：

```ts
abstract class TransportableError extends Error {
  abstract serialize(): { code: ErrorCodes; message: string; stack?: string; ...自定义字段 };
  static deserialize(code, data): TransportableError; // 每个子类各自实现
}
```

队列层统一按 `code` 字段反序列化回具体的错误类实例，上层业务代码依然可以用 `error instanceof SSLError` 做类型安全的分支判断——本质上是手搓了一套跨进程的"错误 RTTI（运行时类型信息）"。

### 7.2 全链路 Tracing

`withSpan`/`setSpanAttributes`（基于 OpenTelemetry）贯穿：请求入口 → 威胁检查 → robots检查 → 引擎循环 → 单个引擎调用 → Fire-Engine 具体请求。每一层都标记了对应的语义化属性（`engine.winner`、`scrape.index_hit`、`fire-engine.poll_count`），这些 span 可以直接导入 Jaeger/Tempo 等系统做火焰图分析，快速定位"这次抓取慢在哪一步"。

## 八、Rust/NAPI 原生模块的定位

`apps/api/native/`（编译为 `@mendable/firecrawl-rs`）承担的都是"CPU密集 + 高调用频次"的任务：

- `crawler.rs`：链接过滤规则引擎（深度/正则/robots判定）
- `html.rs`：HTML 解析、链接/图片提取
- `pdf.rs`：PDF 解析
- `document/`：DOCX/ODT/RTF/XLSX 等 Office 文档解析（`providers/` 每种格式一个实现，`factory.rs` 做格式分发）
- `engpicker.rs`：引擎选择的辅助判定逻辑

**双轨设计**：几乎每个 Rust 能力在 TS 侧都保留了一份"降级实现"（如 `extractLinksFromHTMLCheerio` 对应 `extractLinksFromHTMLRust`），Rust 调用失败会 `catch` 后自动切换，业务可用性优先于性能优化——这是"性能优化不应引入新的单点故障"的良好实践。
