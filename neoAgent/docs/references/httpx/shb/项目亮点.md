# httpx 项目亮点

本文按"对自研爬虫的借鉴价值"排序，逐条剖析 httpx 中值得学习的工程实践。每条都附带代码位置和"为什么这样做更好"的分析。

## 亮点 1：三层熔断/降级体系，杜绝"一个坏目标拖死全局"

这是 httpx 中**最值得借鉴**的设计，直接对应爬虫系统最常见的生产事故：某几个目标响应极慢或连接被 RST，导致整个抓取进程的吞吐量断崖式下跌，甚至耗尽连接池/文件描述符。

httpx 用三层机制解决：

**第一层：单请求超时 + 有限重试**（`common/httpx/httpx.go` 通过 `retryablehttp` 库）

```30:35:common/httpx/option.go
	Timeout time.Duration
	// RetryMax is the maximum number of retries
	RetryMax      int
```

**第二层：host 级错误熔断缓存**（`runner/runner.go`），这是最关键的一层：

```1841:1848:runner/runner.go
	// check if we have to skip the host:port as a result of a previous failure
	hostPort := net.JoinHostPort(URL.Host, URL.Port())
	if r.options.HostMaxErrors >= 0 && r.HostErrorsCache.Has(hostPort) {
		numberOfErrors, err := r.HostErrorsCache.GetIFPresent(hostPort)
		if err == nil && numberOfErrors >= r.options.HostMaxErrors {
			return Result{URL: target.Host, Err: errors.New("skipping as previously unresponsive")}
		}
	}
```

失败时累加计数（同样在 `analyze()` 内，约 2030-2038 行），一旦某个 `host:port` 累计错误数超过阈值（默认 30），后续所有针对它的路径/端口/方法探测直接跳过——**不再产生任何网络 I/O**，用一个 `gcache.Cache[string, int]` 就实现了完整的熔断器语义，比引入 `hystrix`/`sony/gobreaker` 这类专用库更轻量、更贴合场景。

**第三层：协议自适应降级**（同一函数内 `goto retry` 模式）：

```2003:2028:runner/runner.go
	if err != nil {
		...
		if !retried && origProtocol == httpx.HTTPorHTTPS {
			// switch protocol and adjust port accordingly
			if protocol == httpx.HTTPS {
				protocol = httpx.HTTP
				if URL.Port() == "443" {
					URL.UpdatePort("80")
					target.Host = net.JoinHostPort(URL.Hostname(), "80")
				}
			} else {
				protocol = httpx.HTTPS
				...
			}
			retried = true
			goto retry
		}
```

**借鉴价值**：自研爬虫几乎必然会遇到"目标站点抽风"的场景（超时、DNS 解析失败、SSL 握手失败、连接被拒）。如果没有 host 级熔断，你的爬虫在面对几个"黑洞"目标时会不断重试消耗资源；如果没有协议降级，你会漏掉一大批只支持 HTTP 而不支持 HTTPS（或反之）的站点。**三层熔断应该是任何批量网络采集系统的标配，而不是事后补丁。**

## 亮点 2：并发数与速率解耦的双旋钮限流模型

很多自研爬虫只有一个"并发数"参数，这其实混淆了两个完全不同的概念：

- **并发数（Threads）**：同一时刻允许多少个请求"在飞"（占用连接/内存）
- **速率（Rate Limit）**：单位时间内允许发起多少个新请求（对目标服务器的压力）

httpx 用两个独立组件实现：

```1506:1506:runner/runner.go
	wg, _ := syncutil.New(syncutil.WithSize(r.options.Threads))
```

```418:424:runner/runner.go
	if options.RateLimitMinute > 0 {
		runner.ratelimiter = *ratelimit.New(context.Background(), uint(options.RateLimitMinute), time.Minute)
	} else if options.RateLimit > 0 {
		runner.ratelimiter = *ratelimit.New(context.Background(), uint(options.RateLimit), time.Second)
	} else {
		runner.ratelimiter = *ratelimit.NewUnlimited(context.Background())
	}
```

请求发出前调用 `r.ratelimiter.Take()`（`runner.go:1920`）阻塞式获取令牌。

`AdaptiveWaitGroup`（`projectdiscovery/utils/sync`）还支持运行时动态 `Resize()`（`runner.go:1670-1674`），意味着并发度可以在程序运行过程中被外部调整——这对做"自适应限速"（比如探测到目标返回 429 后自动降并发）的高级爬虫非常有用。

**借鉴价值**：把"并发度"和"QPS"拆成两个独立可调的旋钮，是任何生产级采集系统的基本功。默认值 `threads=50, rate-limit=150/s` 也说明作者刻意让速率成为默认的主约束（防止把目标打垮/被封），并发只是资源上限。

## 亮点 3：极简的断点续传实现——用一个索引代替一堆状态

很多人做断点续传会想着"记录每个 URL 的处理状态存 KV/DB"，实现复杂且容易出 bug。httpx 的做法极其简洁：

```28:30:runner/resume.go
type ResumeCfg struct {
	ResumeFrom   string
	Index        int
	current      string
	currentIndex int
}
```

处理循环里每处理一个目标就自增索引，索引 ≤ 已保存索引的目标直接跳过（`runner.go:1515-1520`）：

```1515:1520:runner/runner.go
	if r.options.resumeCfg != nil {
		r.options.resumeCfg.current = k
		r.options.resumeCfg.currentIndex++
		if r.options.resumeCfg.currentIndex <= r.options.resumeCfg.Index {
			return nil
		}
	}
```

中断时保存当前索引（`SaveResumeConfig`，`runner.go:2913-2918`）；`cmd/httpx/httpx.go` 里监听 `os.Interrupt`，**第一次 Ctrl+C** 触发 `Interrupt()`（停止派发新任务，让在途请求跑完），**第二次 Ctrl+C** 强制退出：

```76:88:cmd/httpx/httpx.go
	c := make(chan os.Signal, 1)
	signal.Notify(c, os.Interrupt)
	go func() {
		<-c
		gologger.Info().Msgf("CTRL+C pressed: Exiting\n")
		httpxRunner.Interrupt()
		<-c
		gologger.Info().Msgf("Forcing exit\n")
		os.Exit(1)
	}()
```

**借鉴价值**：断点续传不必追求"记录每条数据的处理状态"，只要输入是**有序且确定性的流**，一个游标索引就足够。同时"两级 Ctrl+C"（优雅停止 vs 强制退出）是命令行工具的标准礼仪，实现成本极低但用户体验提升巨大。

## 亮点 4：基于 SimHash 的近似去重，而非精确 Hash 去重

海量扫描场景下常见噪音：大量不同域名/IP 解析到同一后端，返回内容几乎相同的默认页/错误页/停放页（parking page）。如果用精确 hash（如 MD5）去重，一个字节的差异（比如页面里嵌的时间戳、随机 nonce）就会导致去重失效。

httpx 使用 SimHash + 汉明距离阈值判断"近似重复"：

```640:653:runner/runner.go
func (r *Runner) duplicate(result *Result) bool {
	respSimHash := simhash.Simhash(simhash.NewWordFeatureSet(converstionutil.Bytes(result.Raw)))
	ip := result.HostIP

	for storedHash, storedIPs := range r.simHashes.GetALL(false) {
		if simhash.Compare(storedHash, respSimHash) > 3 {
			continue
		}
		if ip == "" || sliceutil.Contains(storedIPs, ip) {
			gologger.Debug().Msgf("Skipping duplicate response (simhash %d, ip %s) for URL %s\n", respSimHash, ip, result.URL)
			return true
		}
	}
	...
```

同样的思路还用在截图去重上，用**感知哈希（pHash）+ 汉明距离阈值 22**做视觉相似度聚类（`runner.go:1364-1382`，阈值来源见 `runner.go:127-128` 的注释，直接引用了业界经验博客）：

```127:128:runner/runner.go
// picked based on try-fail but it seems to close to one it's used https://www.hackerfactor.com/blog/index.php?/archives/432-Looks-Like-It.html#c1992
const hammingDistanceThreshold = 22
```

**借鉴价值**：文本去重不要止步于 MD5/SHA。当抓取目标存在大量模板化/近似内容时（这在爬虫场景中极其常见：分页、镜像站、CDN 默认页），SimHash 汉明距离比对是性价比最高的近似去重手段，实现简单（几十行）又有效。

## 亮点 5：CDN/私有 IP/内网地址的显式排除策略

批量探测/爬取时，命中 CDN 节点或内网地址往往是无意义甚至危险的（SSRF 风险）。httpx 内建了完整的排除框架：

- `-e/-exclude` 支持 `cdn`、`private-ips`、CIDR、IP、正则 多种排除条件（`runner/options.go` 中体现）
- `common/httpx/cdn.go` 通过 `cdncheck.Client` 判断 IP 是否属于已知 CDN/WAF 段
- `networkpolicy.NetworkPolicy`（`runner/runner.go:466` `createNetworkpolicyInstance`）统一管理允许/拒绝的网段，并直接注入到 `fastdialer` 的拨号层——即**在 DNS 解析和 TCP 连接建立的最底层就做拦截**，而不是拿到响应后再判断，这样可以避免真正对内网发起连接请求（SSRF 防护的正确姿势）。

**借鉴价值**：如果自研爬虫会处理不可信输入（用户提交的 URL 列表、第三方数据源），**必须在 dialer 层面做网段黑白名单**，而不是在业务逻辑层"事后过滤"，否则无法防御 SSRF。

## 亮点 6：可插拔的 Filter 接口 + DSL 表达式引擎双轨匹配

httpx 同时支持两种匹配/过滤方式，覆盖简单和复杂两种场景：

1. **简单场景**：预定义的 flag（`-mc`状态码、`-ml`长度、`-ms`字符串、`-mr`正则），底层通过统一 `Filter` 接口实现（`common/httpx/filter.go`）：

```9:12:common/httpx/filter.go
type Filter interface {
	Filter(response *Response) (bool, error)
}
```

`FilterString`、`FilterRegex`、`FilterCustom`（接受回调函数）都实现该接口，`HTTPX.Verify()` 级联调用所有 filter，一旦命中即返回（短路求值）。

2. **复杂场景**：DSL 表达式（`-mdc`/`-fdc`），允许 `contains(content_type, "text/plain") && contains(body, "Contact:")` 这样的组合逻辑，底层是 `projectdiscovery/dsl` 库，通过反射把 `Result` 结构体转成 `map[string]any` 后求值（`runner/types.go:147-176`）。更巧妙的是用 `go-faker` 自动生成一个假的 `Result` 实例来推导出所有可用的 DSL 变量名（`-ldv` 参数，`runner/types.go:129-145`），**做到了文档和代码字段永远同步，不需要手动维护变量列表文档**。

**借鉴价值**：简单过滤用固定接口，复杂逻辑开个 DSL 口子，两者不冲突。用反射+faker自动生成可用字段列表这个技巧，可以直接照搬用于任何"用户提供表达式来过滤结构化结果"的场景，避免文档与代码脱节。

## 亮点 7：域名/子域名深度挖掘——不止正则，还做 HTML+JS AST 解析

大部分爬虫在页面中找链接/域名只会用简单正则。httpx 的 `BodyDomainGrab`（`common/httpx/domains.go`）做了三级递进：

1. 判断响应体类型（看起来像 HTML？像 JS？其他？），走不同分支（`looksLikeHTML`/`looksLikeJavaScript`）
2. HTML 走 `goquery` DOM 解析，专门提取 `href/src/action/formaction/poster/cite/data-url` 等**8种**可能携带 URL 的属性，还处理 `srcset` 逗号分隔格式和 `<meta http-equiv="refresh">` 跳转
3. 内联 `<script>` 标签的内容送入 `goja`（JS 解析器）做**真正的 AST 遍历**，从字符串字面量和模板字符串中提取候选域名（`extractDomainsFromJS` + `walkNode`，处理了近 30 种 AST 节点类型），只有在脚本过大（>512KB）时才降级为正则兜底

配合 `publicsuffix-go` 库做真正的公共后缀（eTLD+1）判断，过滤掉误判（纯数字、常见文件后缀、Android/iOS 包名格式如 `com.example.app`）。

**借鉴价值**：如果爬虫需要做子域名/资产发现，"正则提取所有形如 xxx.xxx 的字符串"噪音极大（会把 `1.2.3` 这种版本号、`com.example.package` 这种包名也误判为域名）。httpx 展示了一套完整的"结构化解析优先，正则兜底"的降噪流水线，是可以直接复用的模式。

## 亮点 8：多策略认证系统——声明式配置 + 域名匹配路由

面对需要登录态才能访问的目标批量探测场景，httpx 设计了一套认证策略框架（`common/authprovider/authx/`）：

- 五种策略统一实现 `AuthStrategy` 接口（`Apply`/`ApplyOnRR`）：`BasicAuth`、`BearerToken`、`Header`、`Cookie`、`Query`
- 通过 YAML/JSON 声明式配置文件定义"哪些域名（精确匹配或正则）用哪种认证方式"
- `MultiAuthProvider` 支持组合多个 provider，按顺序查找第一个匹配的策略（`common/authprovider/multi.go`）

```9:16:common/authprovider/authx/strategy.go
type AuthStrategy interface {
	// Apply applies the strategy to the request
	Apply(*http.Request)
	// ApplyOnRR applies the strategy to the retryable request
	ApplyOnRR(*retryablehttp.Request)
}
```

**借鉴价值**：如果爬虫需要抓取多个需要不同认证方式的站点（登录票据、API Key、Basic Auth 混合），与其在业务代码里写一堆 `if domain == "xxx"` 分支，不如像这样做成"策略接口 + 域名路由表 + 声明式配置"，新增一个站点的认证只需要改配置文件，不需要碰代码。

## 亮点 9：结果流水线式过滤 + 多态输出，新增输出格式零侵入

`RunEnumeration` 内部用一条 `for resp := range output` 循环，把「DSL 匹配 → 页面类型过滤 → 去重 → 状态码/长度/正则过滤」等十几种过滤器串成流水线，任何一步 `continue` 即短路，逻辑扁平、没有多层嵌套 if（`runner.go:1117-1300+` 区间）。

输出侧则用 `OnResult`/`OnClose` 回调实现"发布-订阅"式扩展：终端输出、JSON 文件、CSV 文件、Markdown 文件、数据库写入（`internal/db`）、云端上传（`internal/pdcp`）全部是独立的回调，在 `cmd/httpx/httpx.go` 里通过链式包装组合（`setupDatabaseOutput` 里可以看到"包一层调用原有回调"的模式）：

```194:201:cmd/httpx/httpx.go
	// Chain with existing OnResult callback if present
	existingCallback := opts.OnResult
	opts.OnResult = func(r runner.Result) {
		if existingCallback != nil {
			existingCallback(r)
		}
		writer.GetWriterCallback()(r)
	}
```

**借鉴价值**：过滤条件多时用"顺序 continue"代替"深层嵌套 if-else"能极大提升可读性和可维护性（这也是 Linus 式"消除特殊情况"的具体体现）。输出目的地用回调链而非 switch-case，新增一种输出方式（比如推送到 Kafka）完全不需要修改已有代码，只需要包装一层已有回调。

## 综合评价

| 维度 | 评分 | 说明 |
|---|---|---|
| 并发/限流设计 | 🟢 好品味 | 双旋钮解耦、三层熔断，是本项目最值得学的部分 |
| 数据结构设计 | 🟢 好品味 | `Result` 结构体一个字段打三种 tag（json/csv/md/mapstructure），一份定义支撑所有输出格式 |
| 错误处理 | 🟢 好品味 | 熔断代替无脑重试，协议自动降级代替用户手动指定 |
| 代码复杂度 | 🟡 凑合 | `runner.go` 单文件 3000+ 行，`analyze()` 单函数近 900 行，职责过重，是本项目为数不多的"坏味道" |
| 可扩展性 | 🟢 好品味 | Filter 接口、AuthStrategy 接口、OnResult 回调链，扩展点设计得当 |
| 依赖管理 | 🟡 凑合 | 依赖 ProjectDiscovery 自家生态（fastdialer/retryablehttp/ratelimit等）较深，独立复用这些组件需要打包引入一整套生态库 |
