# httpx 项目实现原理

本文深入拆解 httpx 各关键子系统"是怎么工作的"，侧重网络层细节与算法实现，为自研爬虫的底层设计提供可直接复用的技术方案。

## 1. 网络请求层：三个客户端各司其职

`HTTPX` 结构体（`common/httpx/httpx.go`）内部维护了**三套**不同用途的 HTTP 客户端，而不是一套打天下：

```37:47:common/httpx/httpx.go
type HTTPX struct {
	client        *retryablehttp.Client
	client2       *http.Client
	...
	Dialer        *fastdialer.Dialer
	NetworkPolicy *networkpolicy.NetworkPolicy
}
```

- **`client`**（`retryablehttp.Client`）：主力请求客户端，处理绝大多数探测，内置重试/退避逻辑
- **`client2`**（原生 `http.Client` + `http2.Transport`）：专门用于 HTTP/2 探测，因为需要绕开自动协议协商，强制走 h2 明文/密文通道去判断服务端是否真的支持 HTTP/2
- **`Dialer`**（`fastdialer.Dialer`）：底层拨号器，被两个 Transport 共享，统一处理 DNS 解析、连接建立、TLS 握手、JA3 指纹伪装

这种"多客户端分职责"而非"一个万能客户端加一堆 if 分支"的设计，本身就是清晰数据结构优先于复杂控制流的体现。

### 1.1 fastdialer：所有网络访问的统一入口

所有实际的网络 I/O 都通过 `fastdialer.Dialer` 完成（`transport.DialContext = httpx.Dialer.Dial`），它提供了普通爬虫自己实现往往会遗漏的能力：

- **DNS 结果缓存**（`WithDialerHistory: true`），避免对同一域名重复解析
- **自定义 DNS 协议支持**：`protocol:resolver:port` 格式同时支持 `doh|tcp|udp`（DNS over HTTPS/TCP/UDP）
- **TLS 指纹伪装（JA3）**：`DialTLSWithConfigImpersonate`，可以让 Go 程序发出的 TLS ClientHello 与 Chrome 浏览器一致，绕过基于 JA3 指纹的 WAF/反爬识别

```220:234:common/httpx/httpx.go
func (h *HTTPX) buildTLSDialer(options *Options) func(ctx context.Context, network, addr string) (net.Conn, error) {
	if options.TlsImpersonate == "" {
		return func(ctx context.Context, network, addr string) (net.Conn, error) {
			return h.Dialer.DialTLS(ctx, network, addr)
		}
	}
	tlsCfg := &tls.Config{InsecureSkipVerify: true, MinVersion: tls.VersionTLS10}
	strategy, identity := resolveImpersonateStrategy(options.TlsImpersonate)
	return func(ctx context.Context, network, addr string) (net.Conn, error) {
		return h.Dialer.DialTLSWithConfigImpersonate(ctx, network, addr, tlsCfg, strategy, identity)
	}
}
```

- **网络策略（NetworkPolicy）注入到拨号层**：`fastdialerOpts.NetworkPolicy = options.NetworkPolicy`，意味着黑白名单检查发生在**建立 TCP 连接之前**，而不是拿到响应后再判断——这是防御 SSRF（服务端请求伪造）的正确位置。

**原理总结**：把"如何安全、高效地建立一条网络连接"这件事完全下沉到一个独立的 Dialer 抽象里，上层的 `http.Transport`/`http2.Transport` 只需要注入这个 Dialer，就能获得 DNS 缓存、网段过滤、TLS 伪装等能力，不需要在业务代码里重复处理。

### 1.2 retryablehttp：重试与退避的标准实现

`DefaultOptionsSpraying` 是 `retryablehttp-go` 库针对"大量不同目标各打一次"场景（相对于对同一目标反复打的 "flooding" 场景）预置的参数集合，核心语义：

- `RetryMax`：网络错误/超时的最大重试次数（来自 `httpx.Options.RetryMax`，`runner` 里由 `-retries` 参数控制）
- 使用指数退避 + 抖动（jitter）计算重试间隔，避免"雪崩式重试"（大量请求在同一时刻集中重试，加重目标或自身负担）
- 与普通 `http.Client` 的关键区别：**请求体会被完整缓存**（通过 `req.Body` 包装），因为 HTTP 重试要求能重新发送相同的请求体，普通 `http.Client` 的 `Body` 是一次性 `io.Reader`，重试前必须有机制重置

### 1.3 请求执行的完整生命周期（`HTTPX.Do`）

`common/httpx/httpx.go` 的 `Do()` 方法（255-404 行）是单次请求处理的核心，按顺序做了这些事，每一步都在处理一个真实世界会遇到的边界情况：

1. **HEAD 请求特殊容错**：`Unsafe` 模式下 HEAD 请求出错（非超时）时容忍错误继续处理（有些服务器对 HEAD 请求返回畸形响应但仍然可用）
2. **响应体大小硬限制**：`io.LimitReader(httpresp.Body, MaxResponseBodySizeToRead)`，防止读取一个几个 GB 的响应体撑爆内存——**这是任何爬虫都必须有的防御措施**
3. **状态码驱动的跳过读取**：`101 Switching Protocols`（WebSocket 升级后没有传统 body）和 `304 Not Modified` 不读取 body，避免阻塞等待不存在的数据
4. **gzip 异常自愈重试**：

```299:305:common/httpx/httpx.go
		// Edge case - some servers respond with gzip encoding header but uncompressed body, in this case the standard library configures the reader as gzip, triggering an error when read.
		if !gzipRetry && strings.Contains(err.Error(), "gzip: invalid header") {
			gzipRetry = true
			req.Header.Set("Accept-Encoding", "identity")
			goto get_response
		}
```
   这是一个非常"实战出真知"的补丁：某些服务器声明 `Content-Encoding: gzip` 但实际返回未压缩内容，标准库按 gzip 解码会报错。httpx 遇到这个特定错误就换用 `Accept-Encoding: identity` 重新发起请求，从根源避免这类服务器返回的数据被判定为"抓取失败"。
5. **零拷贝优化**：`DecodeData` 在无需转码时直接返回原切片而不复制（`RawData`/`Data` 共享底层数组），只有真正需要字符集转换（GBK/BIG5等）时才产生新内存——代码注释明确写了这个优化动机。
6. **单词数/行数统计避免中间字符串**：直接对 `[]byte` 用 `bytes.Count` 计数，而不是 `strings.Split` 产生一个完整的切片再取长度，减少一次内存分配。

## 2. 并发调度的完整机制

### 2.1 AdaptiveWaitGroup：可动态伸缩的信号量式 WaitGroup

`syncutil.AdaptiveWaitGroup`（`projectdiscovery/utils/sync`）本质是 `sync.WaitGroup` + 一个有缓冲的 channel 做并发上限控制的组合：`Add()` 会阻塞直到获得一个"槽位"，`Done()` 释放槽位。与标准库 `WaitGroup` 相比，多了 `Resize()` 能力，可以在运行时改变槽位总数（`runner.go:1670-1674` 每次 `process()` 调用都会尝试同步一次线程数，支持配置热更新场景）。

### 2.2 递归式目标展开：TLS 证书域名 / CSP 域名的二次探测

`process()` 函数中一个容易被忽略但很精妙的设计：**探测过程中发现的新目标会被递归地送回 `process()` 自身**：

```1693:1703:runner/runner.go
						if scanopts.TLSProbe && result.TLSData != nil {
							for _, tt := range result.TLSData.SubjectAN {
								if !r.testAndSet(tt) {
									continue
								}
								r.process(tt, wg, hp, protocol, scanopts, output)
							}
							if r.testAndSet(result.TLSData.SubjectCN) {
								r.process(result.TLSData.SubjectCN, wg, hp, protocol, scanopts, output)
							}
						}
```

也就是说：探测 `example.com` 时如果打开了 `-tls-probe`，会解析其 TLS 证书里的 SAN（Subject Alternative Names）字段，把里面列出的所有域名（往往是同一企业的其他子域名）**自动加入探测队列**。这是一种轻量级的、无需额外爬取的"资产发现"能力，靠的是 TLS 证书本身携带的信息，而不是遍历链接。`-csp-probe` 同理，从 `Content-Security-Policy` 响应头里提取域名后继续探测。

`testAndSet()`（基于 `hybrid.HybridMap`，内存+磁盘混合存储的 KV）保证同一目标不会被递归探测两次，天然避免了无限循环。

### 2.3 令牌桶限速器的确切生效位置

限速器 `Take()` 调用在 `analyze()` 内、**请求真正发出之前**的多个位置分别调用（普通请求、vhost 探测、pipeline 探测、http2 探测各调用一次），这意味着 httpx 把"每一次实际的网络往返"都计入速率，而不是笼统地在最外层限速一次——**如果一次 `analyze()` 触发了 4 种探测，就会消耗 4 个令牌**，精确反映真实的网络请求量。

## 3. 探测能力的实现细节

### 3.1 Favicon 指纹（Shodan 风格 MMH3 Hash）

`HandleFaviconHash`（`runner/runner.go:2745-2863`）的流程：
1. 若当前请求路径本身就是 `.ico`，直接对当前响应体算 hash
2. 否则解析 HTML `<link rel="...icon...">` 标签提取候选 favicon URL 列表，同时处理 `<base href>` 相对路径解析
3. 若没有显式声明，回退到约定俗成的 `/favicon.ico`
4. 支持 `data:` URI（base64 内联图标）直接解码计算，无需额外请求
5. 最多尝试 2 次网络请求（`tries == 2` 时终止），获取字节后计算 **MMH3（MurmurHash3）** 和 MD5 两种哈希

MMH3 哈希是行业标准做法（Shodan/Censys 等搜索引擎都用同样算法），使得 httpx 算出的哈希值可以直接拿去 Shodan 搜索同指纹的其他资产——这是"输出格式与生态对齐"带来的隐性价值。

### 3.2 虚拟主机（VHost）探测算法

`IsVirtualHost`（`common/httpx/virtualhost.go`）核心思路：向目标发送两次请求——一次用原始 Host 头，一次用随机生成的、几乎不可能存在的 Host 头（`xid.New()` 生成唯一 ID 拼接）。如果服务器针对这两个不同的 Host 返回了**不同的响应**（状态码、内容长度、字数、行数、内容相似度任一维度超过阈值），说明服务器做了基于 Host 头的虚拟主机路由，即原始 Host 是一个"真实存在"的虚拟主机，而非默认兜底页面。相似度使用 `strsim`（字符串相似度算法）计算，阈值可配置（默认 85%）。

这本质是一种**差分探测（Differential Probing）**思想：通过对比"预期匹配"和"预期不匹配"两次请求的响应差异来推断服务端行为，而不依赖任何服务端主动暴露的信息。这个思路可以移植到很多场景，比如探测接口是否做了参数校验（发送正常值 vs 发送随机不存在的值，对比响应差异）。

### 3.3 HTTP/2 与 HTTP Pipeline 探测

- **HTTP/2**：区分明文 h2c（HTTP 场景，通过 `Connection: Upgrade` + `Upgrade: h2c` 头触发协议升级，检查返回 `101 Switching Protocols`）和密文 h2（HTTPS 场景，直接用配置了 `AllowHTTP: true` 的 `http2.Transport` 发起连接，检查响应的 `Proto` 字段是否为 `"HTTP/2.0"`）。两种协议升级路径完全不同，httpx 分别处理。
- **HTTP/1.1 Pipeline**：绕开标准库（标准库不支持真正的 pipelining），直接用裸 TCP/TLS 连接，在**不等待响应的情况下连续写入 10 个请求**，然后限时读取响应，统计有多少个 "HTTP/1.x" 起始的响应片段——如果读到 ≥2 个说明服务器把多个请求的响应管道化返回了。这是一个非常底层、绕过标准库限制、直接操作 socket 的探测手法。

### 3.4 字符编码自动识别与转换

`DecodeData`（`common/httpx/encodings.go`）优先读取 HTTP 响应头 `Content-Type` 里的 `charset` 声明（`gb2312`/`gbk`/`euc-kr`），如果头部没有声明，退化为**从 HTML body 前部用正则提取 `<meta charset="...">` 声明**（`reContentType`），支持 GBK、BIG5（繁体中文）、EUC-KR（韩文）到 UTF-8 的转换。这是任何面向中文互联网的爬虫都会踩坑的地方——大量老旧中文站点仍在使用 GBK 编码，如果不处理会导致中文内容变成乱码。

### 3.5 标题提取：DOM 解析优先，正则兜底

`ExtractTitle`（`common/httpx/title.go`）优先用 `golang.org/x/net/html` 做真正的 DOM 树遍历定位 `<title>` 节点（能正确处理嵌套标签、属性干扰等场景），解析失败（比如响应体根本不是合法 HTML）才退化到正则 `<title.*>(.*?)</title>`。这个"结构化解析优先、正则兜底"的模式在 httpx 中反复出现（域名提取、标题提取都是同一套思路），是一条通用的工程原则。

## 4. 配置与生命周期管理

### 4.1 goflags 分组式命令行框架

`runner/options.go` 使用 `goflags.FlagSet.CreateGroup()` 把 200+ 个命令行参数按语义分组（INPUT/PROBES/MATCHERS/FILTERS/RATE-LIMIT/OUTPUT/CONFIGURATIONS/DEBUG...），这不只是美化 `-h` 输出，更重要的是让参数定义本身具备文档性——阅读 `options.go` 的分组结构基本等价于阅读设计文档。同时支持从 YAML 配置文件加载（`$HOME/.config/httpx/config.yaml`），CLI 参数覆盖配置文件，是标准的"配置文件+命令行覆盖"优先级模型。

### 4.2 NetworkPolicy 的构建过程

`createNetworkpolicyInstance`（`runner.go:466-498`）把用户提供的 `-exclude` 参数（可能是字面量 `cdn`/`private-ips`、CIDR、ASN 编号、端口号或正则）统一展开成 IP/CIDR 层面的 DenyList，其中 ASN 会通过 `mapcidr/asn` 库查询该 ASN announce 的所有 CIDR 段再展开成具体 IP。这套"多形态输入 → 统一规范化为底层可执行策略"的转换逻辑，是任何需要支持"人类友好输入"的系统都要做的工作。

### 4.3 优雅关闭与资源释放

`Runner.Close()`（`runner.go:916-925`）依次关闭：本地缓存文件句柄（`hm.Close()`）、拨号器连接池（`hp.Dialer.Close()`）、限速器（`ratelimiter.Stop()`）、错误缓存（`HostErrorsCache.Purge()`），确保进程退出时不留下未清理的连接、goroutine 或文件句柄泄漏——这是长时间运行的批量任务经常被忽视但极其重要的收尾工作。
