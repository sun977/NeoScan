# httpx 项目概览

> 分析对象：`github.com/projectdiscovery/httpx`
> 分析目的：为自研爬虫/批量网络探测系统提供架构与工程实践参考

## 1. 项目是什么

`httpx` 是 ProjectDiscovery 团队开发的**高并发 HTTP 探测（Probing）工具集**，本质上不是传统意义的"爬虫"（不做全站递归抓取、不解析链接跟进），而是一个**大规模、高吞吐的单跳/浅层 HTTP 元数据采集引擎**：给定大批量目标（域名/URL/IP/CIDR/ASN），并发发起 HTTP(S) 请求，提取指纹、标题、状态码、证书、技术栈、CDN 归属、favicon 哈希等结构化信息。

它是网络安全侦察（recon）领域的事实标准工具之一（GitHub 12k+ stars），被广泛用作 subfinder → httpx → nuclei 这条资产发现流水线的核心一环。

对做爬虫/批量采集系统的人来说，`httpx` 的价值不在于"爬取网页内容"，而在于其**工业级的网络层健壮性设计**：如何在面对数万到数百万个未知目标时，做到不崩溃、不卡死、不误判、可恢复、可观测。这恰恰是绝大多数自研爬虫最欠缺的部分。

## 2. 整体架构分层

项目严格遵循分层解耦，职责边界非常清晰：

```
cmd/httpx/httpx.go          ← 程序入口（CLI），只做参数解析 + 生命周期编排
        │
runner/                     ← 编排层（Controller/Service 合一）
  ├─ options.go              配置定义、CLI flag 绑定、校验
  ├─ runner.go               并发调度、输入管理、结果过滤、输出落盘（核心，3000+ 行）
  ├─ resume.go                断点续传状态
  ├─ healthcheck.go           自检（网络连通性、配置文件权限）
  ├─ headless.go              无头浏览器截图（可选能力）
  ├─ cpe.go / wordpress.go     应用指纹识别附加能力
  └─ wellknown_recipes.go      内置的"知名路径探测配方"（security.txt等）
        │
common/httpx/               ← 探测引擎层（Domain/Service）
  ├─ httpx.go                 HTTP 客户端封装（基于 retryablehttp）
  ├─ tls.go / csp.go           TLS 证书抓取、CSP 域名提取
  ├─ cdn.go                    CDN/WAF 识别
  ├─ domains.go                 响应体中的子域名/FQDN 挖掘（HTML+JS AST 解析）
  ├─ virtualhost.go             虚拟主机探测（差异对比算法）
  ├─ filter.go                  可插拔 Filter 接口
  ├─ pipeline.go / http2.go      协议能力探测
  └─ favicon (stringz 包)        favicon mmh3/md5 指纹
        │
common/*                    ← 基础设施与工具层（Repository/Utils）
  ├─ authprovider/authx/       多策略认证（Basic/Bearer/Header/Cookie/Query）
  ├─ customheader/             自定义请求头解析
  ├─ customports/               nmap 语法端口解析
  ├─ customlist/                黑白名单
  ├─ customextract/             预置正则提取器（url/ipv4/mail）
  ├─ inputformats/               Burp Suite XML 导入
  ├─ hashes/                     md5/sha/mmh3/simhash 统一封装
  ├─ httputilz/                  HTTP 底层工具（normalize等）
  └─ stringz/                    字符串/favicon 工具
        │
internal/                   ← 私有实现（不对外暴露）
  ├─ db/                       结果落库（MongoDB/MySQL/Postgres）
  └─ pdcp/                     ProjectDiscovery 云平台上传
```

这是典型的 **Controller → Service → Engine → Utils** 四层结构：
- `cmd/httpx` 相当于 Controller，只负责启动/信号处理/收尾
- `runner` 相当于 Service，是全部业务编排逻辑所在
- `common/httpx` 相当于领域引擎（Domain Engine），封装"如何安全地发一个 HTTP 请求并拿到全部有用信息"这件事本身，不关心上层怎么调度
- `common/*` 和 `internal/*` 是无状态或强内聚的工具/基础设施

这种分层的最大好处：`common/httpx` 包可以被**单独作为库使用**（`examples/simple/main.go` 演示了这一点），不依赖 `runner` 的任何调度逻辑。这是良好模块化的直接证据。

## 3. 核心数据流

```
输入源(文件/stdin/CIDR/ASN/Burp导出)
        │  inputformats + prepareInput/streamInput
        ▼
   targets() 展开        ← CIDR→IP流, ASN→IP流, 域名直接传递
        │
   process()              ← 按 协议×端口×HTTP方法 做笛卡尔积展开
        │  wg.Add() 起 goroutine，AdaptiveWaitGroup 控制并发数
        ▼
   analyze()               ← 单次探测的完整生命周期：
        │                     1. 查 HostErrorsCache 熔断缓存，判断是否跳过
        │                     2. CDN/私有IP 等 skip 规则判断
        │                     3. 构造请求，应用认证策略、自定义 Header
        │                     4. ratelimiter.Take() 限速
        │                     5. hp.Do() 实际发出请求（含重试、gzip异常兜底）
        │                     6. 协议自动降级重试 (https失败→http，goto retry)
        │                     7. 附加探测：TLS抓取/favicon/title/tech-detect/截图...
        │                     8. 记录错误到 HostErrorsCache（熔断计数）
        ▼
   output channel (chan Result)
        │
   过滤器链                ← 状态码/长度/正则/DSL表达式/去重(simhash)/CDN...
        │
   多格式输出               ← 终端/JSON/CSV/Markdown/文件落盘/数据库/云端上传
```

## 4. 关键设计取舍

| 决策点 | httpx 的选择 | 背后原因 |
|---|---|---|
| 并发模型 | 每个 target 起 goroutine + `AdaptiveWaitGroup` 限制并发数 | 比 worker pool + channel 队列更简单，避免队列积压导致的内存问题 |
| 限速 | 令牌桶 `ratelimit.Limiter`，请求发出前 `Take()` 阻塞 | 与并发数解耦：线程数决定"同时在飞的请求数"，速率决定"每秒发出数"，两个维度独立可调 |
| 失败处理 | 单目标失败不重试整个流程，而是 host 级熔断计数 (`HostMaxErrors`) | 避免一个失联的目标拖慢/拖死整批任务（这是自研爬虫最常翻车的地方） |
| 协议探测 | 默认 HTTPS 优先，失败自动降级 HTTP（`goto retry`） | 兼容真实网络环境，减少用户参数负担 |
| 去重 | 内容 SimHash + 汉明距离，而非精确 hash | 应对同一 IP 大量近似错误页/默认页场景（海量资产扫描的常见噪音） |
| 断点续传 | 仅记录"已处理到第几个目标"的索引，而非每个目标的状态 | 极简实现，配合"流式顺序处理"假设即可保证幂等 |
| 输出 | 多格式(txt/json/csv/md) + 多目的地(文件/数据库/云端) 通过统一 `Result` 结构和回调链实现 | `OnResult`/`OnClose` 回调可无限链式叠加，新增输出目的地不侵入核心逻辑 |
