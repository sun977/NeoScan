# 面向自研爬虫的借鉴指南

> 目标读者：正在用 Go 写爬虫/采集/扫描类工具的开发者
> 用法：不要通篇照搬，按你项目当前所处阶段，挑对应章节的"可落地决策"来抄

---

## 0. 先明确一个认知边界

xray 仓库里**看不到爬虫本身怎么爬**（URL 去重、并发调度、DOM/JS 渲染、表单识别这些硬核逻辑全部闭源）。所以本指南不能告诉你"xray 的爬虫是怎么实现的"，而是提炼**它开放出来的架构决策**——这些决策同样适用于任何数据采集/自动化探测类系统，不局限于安全扫描。

如果你需要的是"爬虫内核怎么写"（并发模型、去重算法、渲染引擎选型），这个仓库帮不了你，需要另外参考 Colly、Scrapy、Katana 等开源爬虫的源码。

---

## 1. 【强烈建议抄】规则与代码分离：给你的爬虫加一层 DSL

### 你可能遇到的真实场景

- 抽取规则经常变（今天要抓标题，明天甲方要加一个抓价格的字段）
- 反爬识别规则经常变（今天是检测某个 header，明天变成检测某个 cookie 特征）
- 每次改规则都要重新编译发版，效率低，团队里非开发人员没法参与维护规则

### xray 的解法（可直接抄的模式）

```
你的爬虫 Go 代码（解释器，稳定，很少改）
    │  加载
    ▼
YAML/JSON 规则文件（数据，频繁改，谁都能改）
    │  运行时求值
    ▼
表达式引擎（cel-go / expr）
```

### 具体落地建议

1. **表达式引擎选型**：Go 生态直接用 `github.com/google/cel-go`（xray 同款）或更轻量的 `github.com/expr-lang/expr`。cel-go 语法能力更强（支持自定义类型、宏），expr 上手更快、依赖更小，个人/小团队项目建议先用 expr。

2. **规则文件的最小 Schema**（照抄 xray 的三段式）：

```yaml
name: extract-product-price
set:
    priceRe: '"\\$([0-9.]+)"'
match:
    expression: priceRe.matches(page.html)
extract:
    price: priceRe.submatch(page.html)["1"]
```

3. **规则与解释器的接口边界要清晰**：解释器只暴露"领域函数"（比如 `page.html`、`page.status`、正则相关函数），不要让规则文件里出现只有开发者能理解的内部实现细节。

4. **落地顺序建议**：不要一上来就设计一个大而全的 DSL。先从"最频繁变化的那一类规则"（通常是反爬识别或字段抽取）单独抽出来做 YAML 化，验证好用了再逐步扩展覆盖面。

## 2. 【强烈建议抄】搭建自己的"评测靶场"，而不是纯人工 review

这是本仓库对爬虫开发者最有价值的一条经验，重要性甚至超过 DSL 本身。

### 你可能遇到的真实场景

- 反爬对抗规则改了一版，怀疑会不会误伤正常页面（比如把正常的验证码页面误判为反爬拦截，或反之）
- 内容抽取规则改了一版，怀疑会不会在某些边界 HTML 结构上抽错
- 每次改动后靠"人工点开几个页面看看"来验证，主观且不可复现

### xray evilpot 的核心思路（抽象出来的通用方法论）

> **把"已知容易让规则出错的陷阱场景"固化成一个可重复运行的靶场，用"是否触发预期外结果"作为唯一客观标准，而不是靠人工主观判断。**

### 具体落地建议（爬虫场景的对应实现）

1. **建一个"陷阱页面"靶场服务**（可以就是几个静态 HTML + 一个简单的 Go/Python HTTP server）：
   - 页面里塞入你的抽取规则最容易踩坑的结构：多层嵌套的相似 DOM、假的分页控件、编码错乱的文本、超长文本截断边界、空值/null 字段
   - 页面里模拟你的反爬识别规则最容易误判的特征：正常网站也常见的 429/503 状态码页面、正常的登录墙、正常的验证码占位图但不是真的拦截

2. **把"预期结果"写成断言，跑靶场时自动比对**：
   - 陷阱页面 A 的价格字段应该被抽取为 "99.9"，如果抽出别的值就是回归失败
   - 陷阱页面 B 明明是正常内容，如果被反爬规则误判为"被拦截"就是误报

3. **每次改动规则/抽取逻辑前后都跑一遍靶场**，作为 CI 的一部分（参考 xray 的 `check_poc.yml` 思路：用你自己发布的工具自检自己的规则）。

4. **像 evilpot 一样"真的执行"陷阱里的可疑操作**：如果你的反爬绕过逻辑里有类似"检测到 JS 里有 sleep 就认为是限速"这种基于关键字的判断，靶场就应该真的塞一个不影响功能的假 sleep 关键字进去，测试你的规则会不会被字符串表面欺骗。这是比"构造几个正常样本"更进一步的对抗性思维。

## 3. 【建议抄】三种运行模式的产品设计思路

xray 把使用场景切成"面 / 流 / 点"三种模式，这个划分思路本身很值得复用到任何采集工具上：

| 模式 | xray 对应 | 你的爬虫可以怎么设计 |
|---|---|---|
| 面（全量遍历） | `--basic-crawler` 主动爬虫 | 给一个种子 URL/站点列表，自动发现并遍历全部目标 |
| 流（旁路监听） | `--listen` 被动代理 | 监听消息队列/日志流/代理端口，实时处理经过的流量，不主动发起请求 |
| 点（精确单次） | `--url` 单点扫描 | 只处理一个明确指定的目标，便于测试、复现问题、CI 集成 |

**设计建议**：即使你现在只做了"面"模式，也应该尽早预留"点"模式的接口（只处理单个 URL/单条记录，不依赖爬虫队列），这对调试和单元测试非常有价值——xray 的 `--url` 模式本质上就是给开发者和用户提供的"最小可复现单元"。

## 4. 【建议抄】下游处理用插件注册表模式，别用 if/else

### 你可能遇到的真实场景

爬到/抽取到数据后，下游要做很多不同的事：存数据库、去重、推送消息队列、写 Excel、触发告警……而且这个列表会一直增长。

### xray webhook 的模式（30 行代码可以完全照抄的核心逻辑）

```python
# 抽象基类，定义钩子，默认空实现
class BasePlugin:
    def process_item(self, item): pass

# 反射式加载 + 注册表
_registry = []
def init_plugins(config):
    for name, conf in config.items():
        if not conf.enabled:
            continue
        cls = import_class(f"plugins.{name}.Plugin")
        _registry.append(cls(**conf.args))

# 分发时遍历注册表，异步隔离
def dispatch(item):
    for p in _registry:
        pool.submit(safe_call, p.process_item, item)
```

用 Go 实现同样思路（更符合 Go 的接口习惯）：

```go
type Processor interface {
    Process(item *Item) error
}

var registry []Processor

func Register(p Processor) {
    registry = append(registry, p)
}

func Dispatch(item *Item) {
    for _, p := range registry {
        go func(p Processor) {
            defer func() {
                if r := recover(); r != nil {
                    log.Printf("processor panic: %v", r)
                }
            }()
            if err := p.Process(item); err != nil {
                log.Printf("processor error: %v", err)
            }
        }(p)
    }
}
```

**关键点**：
1. 新增一种下游处理 = 新增一个实现了接口的类型 + 注册一行代码，主流程代码零改动（开闭原则）
2. 每个 processor 的异常必须被隔离捕获，不能因为一个下游处理失败影响其他处理器或主流程
3. 用配置文件控制启用哪些 processor，不要写死在代码里

## 5. 【酌情参考】反连/外部可观测锚点的思路

如果你的爬虫需要验证"某个操作是否真实产生了外部副作用"（比如：验证某个下载链接是否真的可访问、验证某个 webhook 回调是否真的被触发），可以参考 xray 反连机制的抽象方式：

```go
type Probe struct {
    ID  string
    URL string
}

func NewProbe() *Probe { /* 生成唯一标识，注册到本地/远程观测服务 */ }
func (p *Probe) Wait(timeout time.Duration) bool { /* 轮询观测服务，查询该 ID 是否被访问过 */ }
```

不需要一开始就搭建复杂的 DNSLog 平台，最简单的实现可以是：自己的服务里维护一个 `map[string]bool`，探针 URL 指向自己的一个 HTTP 端点，被访问时置位，`Wait()` 轮询这个 map。这个模式的价值在于**把"是否被外部触达"这件事封装成统一对象，而不是在业务代码里到处写"发个请求然后 sleep 3 秒看看有没有反应"的临时代码**。

## 6. 【酌情参考】报告产物：单文件离线方案

如果你的爬虫/采集结果需要交付给非技术人员，或者要在无网络环境查看，参考 xray report 的构建配置：
- 禁用代码分割（`splitChunks: false`）
- 用 `html-webpack-inline-source-plugin` 把 JS/CSS 内联进 HTML
- 数据以 `<script>window.DATA = {...}</script>` 形式直接写入产物

这比自建一个在线报告服务的投入产出比高得多，尤其适合中小型工具、内部工具、甲方交付场景。

## 7. 不建议照搬的部分（避免过度设计）

按 Linus 的实用主义标准，以下是我认为**不值得**在小型/中型自研爬虫项目里照搬的部分，避免陷入"为了学习而过度设计"的陷阱：

1. **不要一开始就搞 CEL/表达式引擎**：如果你的规则一个月都不变一次，直接写 Go 代码分支就够了，不要为了"看起来专业"引入表达式引擎。只有当规则变化频率明显超过代码发布频率时，这个投入才划算。
2. **不要照搬 45 条正则平铺 `||` 的指纹识别写法**：那是 xray 在"必须兼容尽可能多历史遗留设备"这个特殊约束下的产物。如果你的目标网站范围明确，用更精确的少量规则 + 合理的优先级排序即可，不需要堆砌规则数量。
3. **不要为了"插件生态"而设计插件系统**：如果你的下游处理逻辑只有 1-2 种且短期不会增加，直接写函数调用就行，插件注册表模式是在"确定会有多个、且经常变化的下游处理器"时才有意义的投入。
4. **evilpot 式靶场需要投入维护成本**，如果你的抽取规则本身就很简单固定（比如只抓一个字段、目标站点结构稳定），不需要大费周章搭建对抗性测试靶场，写几个单元测试样例 HTML 就够用。

## 8. 落地优先级建议（如果要动手实践）

如果你决定把这些经验用到自己的爬虫项目里，建议按以下顺序推进，而不是一次性全部实现：

1. **第一步**：给你现有的"抽取规则"或"识别规则"找出变化最频繁的那一类，评估是否值得做 YAML+表达式化改造
2. **第二步**：不管有没有做规则外置，先补上"单点模式"（只处理一个 URL/一条数据），这是后续一切自动化测试的基础
3. **第三步**：基于单点模式，搭建 2-3 个"陷阱样本"（不需要一开始就很完善），把回归测试跑起来
4. **第四步**：如果下游处理逻辑开始增多（超过 3 种），再引入插件注册表模式
5. **第五步（可选）**：如果规则贡献者不止你一人（团队协作或开源），再考虑加 CI 门禁做规则质量检查

这个顺序的原则是：**先解决当下最痛的问题，再逐步引入抽象**，不要一上来就照搬 xray 的全套架构——毕竟 xray 是一个运营了多年、有专职团队和活跃社区的商业产品，它的复杂度是被真实需求撑起来的，你的项目现阶段未必需要这么多层抽象。
