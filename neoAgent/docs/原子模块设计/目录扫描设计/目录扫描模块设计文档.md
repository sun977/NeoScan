## 1. 模块定位

### 1.1 职责定义

目录扫描模块（`DirScanner`）是一个原子扫描能力，负责通过字典爆破发现 Web 服务器上的隐藏路径、敏感文件、备份文件、配置暴露和管理面板。

**输入**: 已发现的 HTTP/HTTPS 服务（IP:Port 或 域名:Port）
**输出**: 命中的路径列表 + 状态码 + 响应大小
**触发条件**:
- **主动触发**: 用户执行 `neoAgent scan dir -t target -p 80`
- **Pipeline 触发**: `scan run` 全流程编排中，ServiceScanner 识别出 Web 服务后自动触发
- **ServiceDispatcher 触发**: 分发器在端口服务扫描完成后向 Web 服务发起目录扫描

### 1.2 原子性边界

遵循"原子扫描器隔离原则"，`DirScanner` 不依赖 `WebScanner` 或 `ApiScanner` 的内部实现：
- `DirScanner` 有独立的包 `internal/core/scanner/dir/`
- 字典管理有独立的包 `internal/core/scanner/dir/dict/`
- 可复用 `internal/pkg/utils/` 下的无状态纯函数（如字符串处理、正则工具）

### 1.3 与相关模块的关系

```
                    ┌──────────────┐
                    │  RunnerManager│  ← 统一注册
                    └──────┬───────┘
                           │  Execute(task)
                           ▼
              ┌────────────────────────┐
              │    DirScanner           │
              │  internal/core/scanner/dir/
              └──┬──────────┬──────────┘
                 │          │
    ┌────────────▼──┐  ┌───▼──────────┐
    │  内置字典库    │  │  外部规则文件  │
    │  (嵌入式)      │  │  (可动态加载)  │
    └───────────────┘  └──────────────┘
```

**与其他扫描器的协作**:

| 上游 | 下游 | 协作方式 |
|------|------|---------|
| ServiceScanner | DirScanner | ServiceScanner 识别出 80/443/Web 端口后，Pipeline 触发 DirScanner |
| WebScanner | DirScanner | Web 页面中发现 `/admin`、`/api` 等路径，可追加到 DirScanner 队列 |
| DirScanner | VulnScanner | DirScanner 发现 `/wp-admin`、`/phpmyadmin` 后，VulnScanner 针对性加载模板 |

### 2.2 数据流（实际实现，对应 `dir_scanner.go` 的 `Run()`/`worker()`）

```
DirScanner.Run(ctx, task)
  │
  ├── 1. 解析 task.Params → DirOptions（parseDirOptions）
  │
  ├── 2. 初始化
  │     ├── dict.New(opts.toDictOptions()) → 加载内置字典 + 用户文件 + 自定义规则 + 展开
  │     ├── engine.NewRequester(cfg) → 配置连接池/超时/代理/速率限制（defer requester.Close()）
  │     ├── engine.NewFilter(cfg) → 初始化过滤器
  │     └── engine.NewWildcardScanner(requester, baseURL) → 并对根前缀 "/" 执行 Precheck()（预采样）
  │
  ├── 3. 启动 opts.Threads 个 worker goroutine，通过 hits channel 汇态结果：
  │     worker 循环：
  │       path, ok := dictionary.Next()      → 双队列迭代器取下一个路径，耗尽则退出
  │       limiter.Acquire(ctx)                → AdaptiveLimiter 获取并发令牌
  │       resp, err := requester.Do(ctx, ...)  → 发送 HTTP 请求（内含重试）
  │       filter.Match(resp, path)             → 第一层：多层快速过滤
  │       wildcardScanner.Check(ctx, prefix, resp) → 第二层：通配符检测
  │       → unique? → hits <- DirHit{...}
  │       → shouldRecursion(resp, path, opts)? → dictionary.AddExtra(subpaths...)
  │
  └── 4. 汇总 hits 写入 DirResult，返回 []*model.TaskResult
```

> **与早期设计的差异**：没有独立的 `Scanner.New()`/`dict.New()` 工厂函数命名（实际为 `dict.New()`
> 返回 `*Dictionary`，`engine.NewWildcardScanner()` 创建通配符引擎）；没有独立的 `collectResult()`，
> 命中结果直接通过 `hits chan *result.DirHit` 传递回主 goroutine 汇总。

### 2.3 核心组件

| 组件 | 文件 | 职责 | 关键设计 |
|------|------|------|---------|
| **DirScanner** | `dir_scanner.go` | 编排入口 | `Run()` 解析 task → 初始化组件 → 并发扫描 → 返回结果；internal `worker()`/`recursionCtl` 实现递归调度 |
| **Dictionary** | `dict/dictionary.go` | 路径字典迭代器 | 双队列（main+extra）、`Next()`/`AddExtra()` 线程安全、`maxSize` 限制（默认 500K） |
| **Requester** | `engine/requester.go` | HTTP 请求 | `http.Transport` 连接池复用（`MaxIdleConnsPerHost` 对齐线程数）、重试、代理、速率限制、本地 IP/网卡绑定；**不包含** `PathPreservingRoundTripper`（见 6.1 节） |
| **Filter** | `engine/filter.go` | 快速过滤 | 状态码白/黑名单、响应大小黑名单、关键词/正则排除，共 3 层（不包含设计文档早期版本的 `MinSize`/`MaxSize` 范围过滤） |
| **WildcardScanner** | `engine/scanner.go` | 通配符检测 | 两阶段模型（`sync.Once` 采样 → 固化只读比对），详见第 4 节 |

## 3. 字典管理设计

### 3.1 字典来源

| 来源 | 路径 | 说明 |
|------|------|------|
| **内置字典** | `dict/wordlists/`（`go:embed` 嵌入） | **直接复用 dirsearch 全部字典**：`dicc.txt` + `categories/` + `templates/` + `blacklist/`，编译时嵌入二进制，零配置启动 |
| **用户自定义字典** | `rules/dir/custom/*.txt`（运行时加载） | 用户自行放置的字典文件，运行时扫描加载，**免重新编译**，参考 `web_fingerprints.json` 加载范式 |
| **递归扫描** | `Dictionary.addExtra()` | 递归过程中发现的子路径自动加入扫描队列 |
| **动态扩展** | `Dictionary.addExtra()` | Pipeline/ApiScanner 发现的路径追加 |

**设计决策**: 直接复用 dirsearch 的字典文件，不重新编写。理由：
- 零成本验证字典质量，dirsearch 多年积累的黑产路径覆盖已足够成熟
- 唯一需要做的是 Go 语言重写字典加载器（双队列 + 模板扩展 + .gz 支持）

### 3.2 字典目录设计原则

**两层分离，职责清晰：**

| 层 | 路径 | 加载方式 | 修改后是否需要重新编译 | 面向对象 |
|---|------|---------|:---:|------|
| **内置字典** | `internal/core/scanner/dir/dict/wordlists/` | `go:embed`，编译进二进制 | ✅ 需要 | 开发者维护，跟随版本发布 |
| **用户字典** | `rules/dir/custom/` | 运行时 `os.ReadFile`，启动时扫描 | ❌ 不需要 | 用户/运维，热更新立即生效 |

**为什么内置字典不放在 `rules/` 下？**

`go:embed` 不支持 `../` 跨目录引用，字典文件必须在 `internal/` 包目录内才能被编译嵌入。`rules/` 只存放运行时可热更新的规则，两者不混用，避免出现像 `nmap-os-db` 那样"改了 `rules/` 下的文件，线上行为毫无变化"的维护陷阱。

**内置字典规模**（来源 dirsearch `db/` 目录）：

| 文件/目录 | 说明 |
|---------|------|
| `dicc.txt` | 主字典，核心通用路径，实际约 9681 条 |
| `categories/` | 按技术栈分类（php/java/python/infra 等），`LoadCategoryWordlist()` 已接入：CLI `--category`（逗号分隔多个）追加到 main 队列 |
| `templates/` | 按场景分类（admin/api/auth 等），`LoadTemplateWordlist()` 未接入——与 categories 功能重叠，用户可用 `--wordlists` 达到同等效果，暂不做 |
| `blacklist/` | dirsearch 原版畸形请求探测 payload，非路径黑名单，**结论：不接入**（见 5.3 节），`LoadBlacklist()`/`AddErrorPath()` 保留为未来参考 |
| `user-agents.txt` | 随机 User-Agent 池（供 `--random-agent` 使用，已接入） |

内置主字典实际约 9681 条，通过 `Dictionary.maxSize`（默认 500,000，常量 `defaultMaxSize`）限制递归膨胀后的实际扫描量，当前不开放为 CLI 参数（无 `--max-entries`）。

### 3.3 字典双队列设计（`dict/dictionary.go` 实际实现）

```go
type Dictionary struct {
    mu       sync.Mutex
    main     []string // 主字典（预加载，初始化后不再追加）
    extra    []string // 动态扩展队列（递归子路径）
    mainIdx  int
    extraIdx int
    maxSize  int // 字典条目上限，默认 500,000
    total    int // 已生成条目计数（含展开后的数量）
}

// Next 优先消费 extra（递归新增的路径），extra 耗尽后返回 main。线程安全。
func (d *Dictionary) Next() (string, bool)

// AddExtra 追加一批路径到 extra 队列（递归扫描时调用）。超过 maxSize 的条目直接丢弃。
func (d *Dictionary) AddExtra(paths ...string)
```

> **与早期设计的差异**：`AddExtra` 实际是追加到 `extra` 队列尾部（`append`），而非早期设计注释
> 所说的"追加到头部优先扫描"——`Next()` 优先消费整个 `extra` 队列已经自然实现了"递归发现的路径
> 优先于剩余主字典"的效果，无需头插。

### 3.4 模板令牌系统（`dict/template.go` 实际实现）

实际只实现了单一令牌：

| 令牌 | 含义 | 示例 |
|------|------|------|
| `%EXT%` | 扩展列表 | `.php`, `.asp`, `.html`, `.bak` |

> **与早期设计的差异**：`%SUBJECT%` 令牌未实现，实际代码中只有 `extToken = "%EXT%"` 一个常量，
> 也没有通用的 `extractTokens()` 多令牌提取机制——因为实际使用中不需要。

**扩展模式**（`ExtensionMode` 枚举）:
- **`ExtensionModeClassic`（默认）**: 仅替换 `%EXT%`，不含令牌的行原样返回
- **`ExtensionModeForce`**: 在 Classic 行为基础上，对不含 `%EXT%` 的行额外追加 `{line}.{ext}` 变体（不是早期设计文档说的 `/.ext` 和 `/{line}.ext` 两种，实际只有后一种）

> ⚠️ **`overwrite_extensions` 不实现**：使用场景有限，`force_extensions` 已覆盖大部分需求，见参数设计文档 3.2 节。

**实际实现**（`ExpandLine`）：

```go
func ExpandLine(line string, extensions []string, mode ExtensionMode) []string {
    hasToken := strings.Contains(line, extToken) // extToken = "%EXT%"

    if len(extensions) == 0 {
        return []string{line} // 无扩展列表时原样返回
    }
    if hasToken {
        result := make([]string, 0, len(extensions))
        for _, ext := range extensions {
            result = append(result, strings.ReplaceAll(line, extToken, ext))
        }
        return result
    }
    if mode == ExtensionModeForce {
        result := make([]string, 0, 1+len(extensions))
        result = append(result, line)
        for _, ext := range extensions {
            result = append(result, line+"."+ext)
        }
        return result
    }
    return []string{line} // Classic 模式下不含 %EXT% 原样返回
}
```

## 4. 通配符检测引擎设计

> **本节与早期设计差异最大**：早期设计没有意识到高并发下"采样中"这个中间状态会产生 data race：
> 若用运行时状态（`len(samples) < threshold`）判断"是否还在采样"，多个 goroutine 会同时
> 误判未采满、同时发起探测请求、同时 append 采样数据。实际代码（`engine/scanner.go`）对齐
> dirsearch `lib/core/scanner.py` 的做法，把"采样"与"判定"严格分成两个阶段，用 `sync.Once`
> 保证同一 pathPrefix 的采样只由第一个到达的 goroutine 执行一次，其余并发到达的 goroutine
> 阻塞等待，采样完成后相关字段固化为只读，从根上消除了 data race。

### 4.1 核心数据结构（`engine/scanner.go` 实际实现）

```go
// samplePool 保存单个路径前缀的采样与判定状态。
// once.Do 返回之后，下面几个字段全部固化为只读，不再需要加锁访问。
type samplePool struct {
    once           sync.Once
    bodies         []string // 采样响应体（仅采样阶段写入，之后只读）
    staticPatterns []string // 提取出的共同静态词（只读）
    baseWordCount  int      // 基准词数（只读）
    ready          bool     // 是否已完成采样固化（采样全部失败时的兵底判断）
}

// WildcardScanner 移植 dirsearch 的 Scanner + DynamicContentParser 算法。
type WildcardScanner struct {
    requester *Requester
    baseURL   string

    sampleThreshold   int // 采样阈值，默认 5
    fingerprintThresh int // 自校准阈值，默认 10

    poolsMu sync.Mutex             // 仅保护 pools map 本身的读写
    pools   map[string]*samplePool // pathPrefix → 采样状态

    fpMu         sync.Mutex      // 保护 fingerprints/wildCardFPs 两个 map
    fingerprints map[string]int  // fingerprint → 出现次数
    wildCardFPs  map[string]bool // 已确认的通配符指纹
}
```

### 4.2 两阶段流程：Precheck 预采样 + Check 判定

```go
// Precheck 对根前缀 "/" 预先完成采样，等价于 dirsearch 在 worker 启动前
// 调用 Fuzzer.setup_scanners() 同步初始化默认 Scanner。在 dir_scanner.go 的 Run()
// 中、worker 启动前调用，避免小字典场景下采样阶段吞掉真实命中。
func (s *WildcardScanner) Precheck(ctx context.Context) {
    s.ensurePoolReady(ctx, "/")
}

// Check 判断给定路径的响应是否为独立、真实存在的内容。
// 返回 (true, "unique") 表示应当作为命中结果输出；
// 返回 (false, reason) 表示应当被丢弃（通配符/已知通配符指纹）。
func (s *WildcardScanner) Check(ctx context.Context, pathPrefix string, resp *Response) (bool, string) {
    fp := fingerprint(resp)
    if s.isKnownWildcardFP(fp) {
        return false, "wildcard"
    }

    pool := s.ensurePoolReady(ctx, pathPrefix)
    if !pool.ready {
        // 采样请求全部失败（如目标不可达），无基准可比对，保守地直接放行，
        // 交给 Filter 层的状态码/大小规则兵底，避免因通配符引擎自身故障导致全量丢失命中。
        return true, "unique"
    }

    if compareToStaticPatterns(pool, resp) {
        s.autoCalibrate(fp)
        return false, "match"
    }
    s.autoCalibrate(fp)
    return true, "unique"
}

// ensurePoolReady 第一个到达的 goroutine 负责发起 sampleThreshold 次探测请求，
// 同一 pathPrefix 上后续并发到达的 goroutine 会阻塞在 pool.once.Do 上。
func (s *WildcardScanner) ensurePoolReady(ctx context.Context, pathPrefix string) *samplePool {
    pool := s.getOrCreatePool(pathPrefix)
    pool.once.Do(func() {
        if s.requester == nil {
            return
        }
        for i := 0; i < s.sampleThreshold; i++ {
            probePath := pathPrefix + randStealthWord()
            resp, err := s.requester.Do(ctx, s.baseURL, probePath)
            if err != nil {
                continue
            }
            pool.bodies = append(pool.bodies, resp.Body)
        }
        if len(pool.bodies) >= 2 {
            pool.staticPatterns, pool.baseWordCount = extractStaticPatterns(pool.bodies[0], pool.bodies[1])
            pool.ready = true
        }
    })
    return pool
}
```

> **与早期设计的差异**：
> - 没有 `isProbableWildCard()` 模糊检测阶段，实际只有两种结果：命中静态模式（`match`）或未命中
>   （`unique`），通过 `autoCalibrate` 自校准来补充识别高频重复指纹，无需额外的模糊判定层。
> - 采样不是按每个路径（path）独立进行，而是按目录前缀（pathPrefix，由 `PathPrefixOf()`
>   提取）共享采样池——同一目录下的所有路径共用一份采样，与 7.3 节"整个扫描周期内指纹不变"的
>   决策一致。
> - 采样失败时的兵底行为是**直接放行**（`return true, "unique"`），而不是全量丢弃——
>   避免目标不可达等异常情况下通配符引擎自身故障连带真实命中一起丢失。

### 4.3 静态模式提取（`extractStaticPatterns`/`compareToStaticPatterns` 实际实现）

```go
// extractStaticPatterns 提取两个响应体中共同出现的词（静态模式），
// 并返回其中较短响应的词数作为基准词数。
func extractStaticPatterns(body1, body2 string) ([]string, int) {
    norm1 := normalizeDynamic(body1)
    norm2 := normalizeDynamic(body2)
    words1 := strings.Fields(norm1)
    words2 := strings.Fields(norm2)

    set2 := make(map[string]int, len(words2))
    for _, w := range words2 {
        set2[w]++
    }

    seen := make(map[string]bool, len(words1))
    var common []string
    for _, w := range words1 {
        if seen[w] {
            continue
        }
        if set2[w] > 0 {
            common = append(common, w)
            seen[w] = true
        }
    }

    baseCount := len(words1)
    if len(words2) < baseCount {
        baseCount = len(words2)
    }
    return common, baseCount
}

// compareToStaticPatterns 判断响应是否匹配采样阶段提取的静态模式（即为通配符响应）。
// pool 此时已经 ready，字段只读，无需加锁。
func compareToStaticPatterns(pool *samplePool, resp *Response) bool {
    if len(pool.staticPatterns) == 0 {
        return false
    }
    body := normalizeDynamic(resp.Body)
    for _, p := range pool.staticPatterns {
        if !strings.Contains(body, p) {
            return false
        }
    }
    wordCount := len(strings.Fields(body))
    if pool.baseWordCount > 0 && float64(wordCount) > float64(pool.baseWordCount)*lengthDiffThreshold {
        return false // 长度差异 > 35%（lengthDiffThreshold = 1.35）
    }
    return true
}
```

> **与早期设计的差异**：实际实现用 `map[string]int` 统计词频求交集，而不是早期设计注释所说的
> 类似 `difflib.Differ` 的序列比对——因为静态词提取只关心"是否共同出现"，不关心词序，
> map 求交集时间复杂度更低且实现更简单。

### 4.4 归一化函数（`normalizeDynamic`，与实际代码一致，4 个正则包级编译一次）

```go
var (
    reUUID = regexp.MustCompile(`[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}`)
    reHex  = regexp.MustCompile(`[0-9a-f]{32,}`)
    reTS   = regexp.MustCompile(`\d{10,}`)
    reB64  = regexp.MustCompile(`[A-Za-z0-9+/]{40,}={0,2}`)
)

// normalizeDynamic 移除响应体中的动态内容（UUID/长hex/时间戳/Base64），
// 使得同一模板渲染出的不同响应能够被归一化为相同文本用于比对。
func normalizeDynamic(content string) string {
    content = reUUID.ReplaceAllString(content, "[UUID]")
    content = reHex.ReplaceAllString(content, "[HEX]")
    content = reTS.ReplaceAllString(content, "[TS]")
    content = reB64.ReplaceAllString(content, "[B64]")
    return content
}
```

> 这 4 个正则包级变量定义，只编译一次（实施文档约束：不在函数内 `MustCompile`）。

### 4.5 自校准（`autoCalibrate`/`fingerprint` 实际实现）

```go
// autoCalibrate 统计指纹出现频率，超过阈值的指纹自动加入通配符黑名单（fingerprintThresh 默认 10）。
func (s *WildcardScanner) autoCalibrate(fp string) {
    s.fpMu.Lock()
    defer s.fpMu.Unlock()
    s.fingerprints[fp]++
    if s.fingerprints[fp] > s.fingerprintThresh {
        s.wildCardFPs[fp] = true
    }
}

// fingerprint 生成响应指纹，格式：status|contentType|bodyLen/64|bodyHash前4字节。
func fingerprint(resp *Response) string {
    limit := len(resp.Body)
    if limit > 4096 {
        limit = 4096
    }
    hash := sha256.Sum256([]byte(resp.Body[:limit]))
    return fmt.Sprintf("%d|%s|%d|%x", resp.StatusCode, resp.ContentType, len(resp.Body)/64, hash[:4])
}
```

> **与早期设计的差异**：指纹不包含 `redirect`（Location 头）字段，实际只用 4 个维度
> （状态码/Content-Type/转换后长度/body 前 4096 字节哈希前4字节），无需 `min()` 辅助函数，
> 直接用 `if limit > 4096` 截断。

## 5. 多层过滤管道设计

### 5.1 过滤层级（`engine/filter.go` 实际实现，实际只有 3 层）

```
Filter.Match(resp, path)
  │
  ├── Layer 1a: 白名单（IncludeStatus 非空时启用，不在白名单内的排除）
  ├── Layer 1b: 黑名单（ExcludeStatus，默认 [404, 500, 502, 503]）
  ├── Layer 1c: 响应大小黑名单（ExcludeSize，精确字节数匹配）
  ├── Layer 2:  错误路径黑名单（ErrorPaths[statusCode][path]，需调用方手动 AddErrorPath() 写入，
  │            结论为不接入，见 5.3 节，此层代码保留但当前 ErrorPaths 永远是空 map）
  ├── Layer 3a: 关键词排除（ExcludeKeywords，Body 包含任意关键词则排除）
  └── Layer 3b: 正则排除（ExcludeRegex，Body 匹配任意正则则排除）
```

通配符检测不在 `Filter` 内，而是在 `dir_scanner.go` 的 `worker()` 中作为独立的第二道封止调用（`filter.Match()` 通过后才调用 `wildcardScanner.Check()`），不是 `Filter` 的内部层级。

### 5.2 过滤配置（`FilterConfig` 实际字段）

```go
type FilterConfig struct {
```

> **与早期设计的差异**：没有 `MinSize`/`MaxSize` 范围过滤，实际只有 `ExcludeSize`（精确大小黑名单），
> 对应 CLI 的 `--exclude-size` 参数（逗号分隔的字节数列表），不支持范围区间。

### 5.3 错误路径黑名单（结论：不接入，2026-08-22 审查定论）

实际代码中错误路径黑名单的实现与设计文档早期构想差异较大：

```go
// engine/filter.go——Filter 提供写入入口，但需调用方主动调用
func (f *Filter) AddErrorPath(statusCode int, path string) {
    if f.cfg.ErrorPaths[statusCode] == nil {
        f.cfg.ErrorPaths[statusCode] = make(map[string]bool)
    }
    f.cfg.ErrorPaths[statusCode][path] = true
}

// dict/wordlists.go——黑名单文件已有加载函数，支持 400/403/500
func LoadBlacklist(statusCode int) (map[string]bool, error)
```

> **与早期设计的差异**：早期设计设想的是一个内置硬编码的 `Blacklist403` map，实际代码是从
> `dict/wordlists/blacklist/*.txt` 文件动态加载（`LoadBlacklist()`）。

**为什么审查后决定不接入，而不是补一行调用代码了事**：

查看 `403_blacklist.txt` 等文件的真实内容，条目形如：

```
%2e%2e//google.com
%ff
../../../../../../etc/passwd
..;/
%3f/
```

这些根本不是"目录路径"，而是 dirsearch 原版用来**探测服务器/WAF 是否对畸形请求返回假
403/500**的 payload——原版用法是拿这些 payload 单独发请求，如果目标对任意畸形请求都返回同一个
403，就把该状态码判定为噪音统一过滤，本质上是通配符检测的一个变体。

而当前 `Filter.ErrorPaths[statusCode][path]` 的查表方式是用**真实字典路径**（如 `/admin`）做
key；字典里的路径与 `%2e%2e//google.com` 这类畸形 payload 永远不会重合，就算写代码把
`LoadBlacklist()` 的结果灌进 `ErrorPaths`，`Layer 2` 也永远不会命中——这是接入方式与数据语义
从一开始就不匹配的设计错误，不是缺一行调用代码的疏漏，补上调用只会制造一个"看起来在生效、
实际上永远没有效果"的假功能，比保持现状不接入更危险（用户会误以为自己已被保护）。

**结论**：`LoadBlacklist()`/`AddErrorPath()`/`Filter.ErrorPaths`/`Layer 2` 全部保留在代码中，
但明确不接入主扫描流程。若未来确有"识别 WAF 对畸形请求返回假状态码"的真实需求，应作为独立
特性走完整设计评审——正确用法是像 `WildcardScanner.Precheck()` 一样，在扫描开始前用这批
payload 单独探测一次，判定该状态码是否可信，而不是往 `ErrorPaths` 里塞真实字典路径。

### 6.2 请求配置（`RequesterConfig` 实际字段，`engine/requester.go`）

```go
type RequesterConfig struct {
    Timeout          time.Duration     // 请求超时（默认 10s）
    MaxRetries       int               // 最大重试次数（默认 2）
    Proxy            string            // 代理 URL（字符串，内部 url.Parse）
    Method           string            // HTTP 方法（默认 GET）
    Headers          map[string]string // 自定义请求头
    UserAgents       []string          // User-Agent 列表（轮询选择，不是随机）
    RateLimit        int               // 每秒请求数限制（0 = 不限）
    Delay            time.Duration     // 请求间隔延迟
    FollowRedirects  bool              // 是否跟随重定向（默认 false）
    IP               string            // 绑定本地 IP
    NetworkInterface string            // 绑定网络接口
    MaxConns         int               // 连接池大小，通常等于扫描并发线程数（默认 100）
}
```

> **与早期设计的差异**：`Proxy` 实际是 `string`（而非 `*url.URL`），在 `NewRequester` 内部
> `url.Parse`；`UserAgents` 是轮询选择（`randomUA()` 用 `uaIndex % len(uaList)`）而非真随机；
> 新增了 `Delay`/`FollowRedirects`/`IP`/`NetworkInterface`/`MaxConns` 字段，均为实际开发中补充。
>
> **连接池复用**（重要性能修复）：曾经 `http.Transport` 设置了 `DisableKeepAlives: true`，且
> 每次请求显式声明 `Connection: close`（后者才是真正根因，即使配置了连接池也会被这一层
> 应用层声明架空）。这会导致每次请求都重新三次握手，扫一次内置字典（~9681 条）就要建立
> 近万个短连接，高并发下快速耗尽本地临时端口、堆积 TIME_WAIT，实测表现为同进程内连续多轮
> 扫描时耗时逐轮递增。参考 dirsearch（`lib/connection/requester.py` 用 `requests.Session` +
> `pool_maxsize=thread_count`）的做法，现已改为按 `Threads` 设置 `MaxIdleConnsPerHost` 并移除
> `Connection: close`，同时新增 `Requester.Close()` 在扫描结束后主动释放空闲连接。详见 11.2 节。

**设计决策**: 默认 GET 方法，理由：
1. 通配符检测需要完整响应体（body 比对），HEAD 无 body
2. dirsearch 默认就是 GET（`config.ini: http-method = get`）
3. 某些服务器对 GET/HEAD 返回不同响应，GET 更可靠
4. 后续可考虑提供 `--method HEAD` 作为轻量模式选项（当前 **未实现**，`--method` 可传任意 HTTP 方法但无专门轻量模式优化）

### 6.3 重试与错误处理（`Requester.Do()` 实际实现）

```go
func (r *Requester) Do(ctx context.Context, baseURL, path string) (*Response, error) {
    var lastErr error
    maxAttempt := r.cfg.MaxRetries + 1

    for attempt := 0; attempt < maxAttempt; attempt++ {
        if attempt > 0 {
            delay := time.Duration(1<<uint(attempt-1)) * 500 * time.Millisecond
            if delay > 5*time.Second {
                delay = 5 * time.Second
            }
            // 等待 delay 或 ctx.Done()
        }
        // 速率限制 + 请求间隔延迟（若配置）

        resp, err := r.doSingle(ctx, baseURL, path)
        if err != nil {
            lastErr = err
            // 连接类错误、本地构造请求失败均不重试（重试无法改变结果，只会浪费时间）
            if isConnectionError(err) || errors.Is(err, ErrInvalidRequest) {
                return nil, err
            }
            continue
        }
        return resp, nil
    }
    return nil, fmt.Errorf("%w: %v", ErrMaxRetriesExceeded, lastErr)
}
```

> **与早期设计的差异**：新增了 `ErrInvalidRequest`（本地构造请求失败，如字典条目含非法 URL 转义
> 序列）不重试的判断——这类错误从未发出网络请求，重试没有任何意义，否则会在含特殊字符的
> 字典条目上白白消耗 MaxRetries 次退避等待，拖慢整个扫描（真实复现过的性能 bug）。

## 7. 并发调度设计

### 7.1 Worker 池（`dir_scanner.go` 实际实现）

```go
func (s *DirScanner) Run(ctx context.Context, task *model.Task) (results []*model.TaskResult, err error) {
    opts := parseDirOptions(task.Params)
    baseURL := normalizeTarget(task.Target, task.PortRange)

    if opts.Threads > 0 {
        s.limiter = qos.NewAdaptiveLimiter(opts.Threads, 5, opts.Threads*4)
    }

    dictionary, _ := dict.New(opts.toDictOptions())
    requester := engine.NewRequester(engine.RequesterConfig{ /* ... */ MaxConns: opts.Threads })
    defer requester.Close() // 扫描结束后立即释放空闲连接，见 6.2 节连接池复用说明

    filter := engine.NewFilter(engine.FilterConfig{ /* ... */ })
    wildcardScanner := engine.NewWildcardScanner(requester, baseURL)
    wildcardScanner.Precheck(ctx) // 预采样根前缀 "/"

    // opts.MaxTime/TargetMaxTime 非零时包装 context.WithTimeout

    hits := make(chan *result.DirHit, 256)
    var wg sync.WaitGroup
    for i := 0; i < opts.Threads; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            s.worker(ctx, baseURL, dictionary, requester, filter, wildcardScanner, rc, hits)
        }()
    }
    go func() {
        wg.Wait()
        close(hits)
    }()

    dirResult := result.NewDirResult(task.Target, dictionary.Total())
    for h := range hits {
        dirResult.Add(h)
    }
    dirResult.Finish()

    return []*model.TaskResult{{TaskID: task.ID, Status: model.TaskStatusSuccess, Result: dirResult, ...}}, nil
}

func (s *DirScanner) worker(
    ctx context.Context, baseURL string, dictionary *dict.Dictionary,
    requester *engine.Requester, filter *engine.Filter,
    wildcardScanner *engine.WildcardScanner, rc *recursionCtl, hits chan<- *result.DirHit,
) {
    for {
        path, ok := dictionary.Next()
        if !ok {
            return // 字典耗尽
        }
        if err := s.limiter.Acquire(ctx); err != nil {
            return // context 取消
        }
        // Delay 配置不为零时先等待

        resp, err := requester.Do(ctx, baseURL, path)
        s.limiter.Release()
        if err != nil {
            continue // 请求失败，跳过该路径
        }

        if !filter.Match(resp, path) {
            continue
        }
        isUnique, _ := wildcardScanner.Check(ctx, engine.PathPrefixOf(path), resp)
        if !isUnique {
            continue
        }

        select {
        case hits <- &result.DirHit{Path: path, Status: resp.StatusCode, ...}:
        case <-ctx.Done():
            return
        }

        if rc.opts.Recursive && shouldRecursion(resp, path, rc.opts) {
            depth := rc.depthOf(path)
            if depth < rc.opts.MaxRecursionDepth {
                subpaths := generateSubpaths(path, rc.opts.DeepRecursive)
                for _, sp := range subpaths {
                    rc.markDepth(sp, depth+1)
                }
                dictionary.AddExtra(subpaths...)
            }
        }
    }
}

// shouldRecursion 判断该命中路径是否应当触发递归扫描（三种模式）
func shouldRecursion(resp *engine.Response, path string, opts *DirOptions) bool {
    if opts.ForceRecursive {
        return true
    }
    if opts.DeepRecursive {
        return true
    }
    // 基础递归：仅对目录类型路径递归（以 / 结尾 且 状态码属于目录类响应）
    return strings.HasSuffix(path, "/") && isDirectoryStatus(resp.StatusCode)
}

// generateSubpaths 为命中路径生成待追加扫描的子路径集合。
//   - 基础模式：命中目录路径本身作为前缀（仅 1 个元素）
//   - 深度模式：额外把命中路径的每一级父目录也加入扫描队列（"/api/users/" → ["/api/", "/api/users/"]）
func generateSubpaths(path string, deep bool) []string {
    base := ensureTrailingSlash(path)
    if !deep {
        return []string{base}
    }
    parts := strings.Split(strings.Trim(base, "/"), "/")
    subpaths := make([]string, 0, len(parts))
    for i := 1; i <= len(parts); i++ {
        subpaths = append(subpaths, "/"+strings.Join(parts[:i], "/")+"/")
    }
    return subpaths
}
```

> **与早期设计的差异**：
> - 结果汇总不是 `results chan *model.DirScanResult`，实际是 `hits chan *result.DirHit`，
>   类型在 `scanner/dir/result` 包。
> - 新增了 `recursionCtl` 结构体负责记录已知路径的递归深度（`depth map[string]int`，`sync.Mutex`
>   保护），在追加子路径前先检查 `depth < MaxRecursionDepth`，这是早期设计中没有的安全阀（对应
>   参数设计文档 7.5 节"递归深度自动限制策略"的决策）。
> - `generateSubpaths` 的基础模式不是早期设计注释所说的"/api/users 命中 → 追加 /api/ 和
>   /users/"，实际是只把命中路径本身作为新的扫描前缀加入 extra 队列（与内置字典拼接由
>   `Dictionary` 负责）；只有开启 `DeepRecursive` 时才会额外追加每一级父目录。
> - `worker` 内部循环开头有 `select { case <-ctx.Done(): return; default: }` 非阻塞检查，早期

### 12.2 递归扫描（已决定：支持，参考 dirsearch 三种模式）

**决策**: 支持递归扫描，参考 dirsearch 的三种递归模式。

| 模式 | 含义 | dirsearch flag | NeoAgent 对应 |
|------|------|---------------|---------------|
| **基础递归** | 对找到的目录路径自动继续扫描 | `-r` / `--recursive` | `--recursive` |
| **深度递归** | 对每个目录深度继续扫描（`api/users` → 扫描 `api/` 和 `users/`） | `--deep-recursive` | `--deep-recursive` |
| **强制递归** | 对每个找到的路径（不只是目录）都继续扫描 | `--force-recursive` | `--force-recursive` |

**递归深度限制**: 参考 dirsearch `config.ini` 默认 `max-recursion-depth`，建议默认 3 层，可配置上限。

**递归状态码**: 参考 dirsearch 默认 `100-999`，建议 NeoAgent 默认只扫描 `200-399` 和 `403`（排除 404/500 等无效路径）。

**递归风险评估**: 
- 最大字典膨胀 = 基础字典 × 递归深度 × 命中目录数
- 如果 5K 字典 × 3 层 × 10 个命中目录 = 150K 路径（可控）
- 通过 `wordlist_max_size`（默认 500K）防止失控

### 12.3 默认请求方法（已决定：GET）

**决策**: 默认使用 **GET** 方法，与 dirsearch 保持一致。

理由：
- dirsearch 默认就是 GET（`config.ini: http-method = get`）
- 通配符检测需要完整响应体（body 比对），HEAD 响应没有 body
- 某些服务器对 GET 和 HEAD 返回不同响应，GET 更可靠
- 后续可考虑提供 `--method HEAD` 作为轻量模式选项（仅返回状态码，不做 body 分析）
