## 一、结论先行

【核心判断】
✅ 值得做，但不是"每个 Scanner 内部各自加批量循环"，那是错误方向。

一句话说清方案：**在 `RunnerManager.Execute` 这一层加一个通用的"多目标 fan-out"编排能力，把批量能力做成所有 Runner 免费获得的公共设施，不改动任何一个现有 Scanner 的业务逻辑，不破坏任何现有 CLI/Master 用法。**

| 维度 | 现状 | 方案后 |
|---|---|---|
| `model.Task.Target` | `string`，单目标 | 不变 |
| 批量能力归属 | 无，各 Scanner 各自为政（仅 `alive` 在 Scanner 内部支持 CIDR 网段展开，属于业务语义特例） | 新增于 `runner` 包，`RunnerManager.Execute` 统一拦截处理 |
| 是否新增 `TaskType` | 不适用 | 否 |
| 是否改动现有 Scanner | 不适用 | 否，`WebScanner`/`AliveScanner`/`PortServiceScanner` 等零改动 |
| 是否改动 `Runner` 接口 | 不适用 | 否，接口签名不变 |
| CLI 改动范围 | 不适用 | 各 `cmd/agent/scan/xxx.go` 新增一个可选 `--targets` flag |
| 向后兼容性 | 不适用 | 完全兼容，新字段零值时行为与现状完全一致 |

## 二、现状分析（数据结构与执行链路）

### 2.1 核心数据流

```
CLI/Master → *model.Task{Target: string} → RunnerManager.Execute(ctx, task) → Runner.Run(ctx, task) → []*model.TaskResult
```

`Task.Target` 是 `string`（单数），这是所有原子扫描器共同的契约：

```45:54:c:/mytools/code/go/NeoScan/neoAgent/internal/core/model/task.go

	...
```

### 2.2 已排查结论：全部原子扫描器现状

| 扫描器 | `--target` 类型 | 是否批量 | 说明 |
|---|---|---|---|
| `alive`（IP存活） | `string` | ✅ 支持（网段级） | `parseTarget()` 识别 CIDR 展开成一批 IP，属于业务语义内的特例，不是通用批量能力 |
| `web`（Web扫描） | `string` | ❌ 不支持 | 单 URL；"多端口并发"是端口维度，不是目标维度 |
| `port`（端口扫描） | `string` | ❌ 不支持 | 单目标，"并发"体现在端口/速率维度 |
| `os`（操作系统识别） | `string` | ❌ 不支持 | 纯单目标 |
| `brute`（弱口令爆破） | `string` | ❌ 目标不支持，字典支持 | 批量的是 `--users`/`--pass`（已有 `loadList` 支持文件/逗号分隔），是"一个目标 × 一批凭据"，不是"一批目标" |

| `subdomain`（子域名扫描） | `string` | ❌ 未实现 | 同上 |
| `vuln`（漏洞扫描） | `string` | ❌ 未实现 | 同上 |

## 三、方案设计

### 3.1 数据结构改动：`model.Task` 新增可选字段

```go
type Task struct {
	ID        string
	Type      TaskType
	Target    string   // 保持不变：单目标场景（现状全部代码路径）
	Targets   []string `json:"targets,omitempty"` // 新增：批量场景，非空时优先于 Target
	PortRange string
	Params    map[string]interface{}
	...
}
```

`Targets` 为空是绝大多数场景（CLI 单次扫描、Master 现有下发方式）的默认状态，完全不受影响。

### 3.2 编排改动：`RunnerManager.Execute` 加批量分支

```go
func (m *RunnerManager) Execute(ctx context.Context, task *model.Task) ([]*model.TaskResult, error) {
	runner, err := m.Get(task.Type)
	if err != nil {
		return nil, err
	}

	if len(task.Targets) == 0 {
		return runner.Run(ctx, task) // 现状完全不变
	}

	return runBatch(ctx, runner, task, task.Targets)
}
```

`runBatch` 是"多目标 fan-out"通用编排函数，逻辑直接复用 `WebScanner.Run` 里"并发 + panic recover + 局部失败不影响整体"的已验证模式：

```go
func runBatch(ctx context.Context, r Runner, base *model.Task, targets []string) ([]*model.TaskResult, error) {
	limiter := make(chan struct{}, defaultBatchConcurrency) // 目标级并发上限
	resultsCh := make(chan []*model.TaskResult, len(targets))
	var wg sync.WaitGroup

	for _, target := range targets {
		wg.Add(1)
		go func(target string) {
			defer wg.Done()
			limiter <- struct{}{}
			defer func() { <-limiter }()
			defer func() {
				if rec := recover(); rec != nil {
					logger.Errorf("[Batch] PANIC RECOVERED (target %s): %v", target, rec)
				}
			}()

			sub := *base
			sub.Target = target
			sub.Targets = nil // 避免子任务再次触发批量分支
			res, err := r.Run(ctx, &sub)
			if err != nil {
				logger.Warnf("[Batch] target %s failed: %v", target, err)
			}
			resultsCh <- res
		}(target)
	}

	wg.Wait()
	close(resultsCh)

	var all []*model.TaskResult
	for res := range resultsCh {
		all = append(all, res...)
	}
	return all, nil
}
```

### 3.3 CLI 改动：复用已有的 `loadList`

`cmd/agent/scan/brute.go` 已经实现了"文件路径或逗号分隔字符串"的解析函数 `loadList`，且未耦合任何 `brute` 专属逻辑，计划将其提取到公共位置（如 `cmd/agent/scan/common.go`），供所有子命令共用：

```go
flags.StringVarP(&targetsInput, "targets", "T", "", "批量目标 (文件路径或逗号分隔，与 --target 二选一)")
...
if targetsInput != "" {
	targets, err := loadList(targetsInput)
	...
	task.Targets = targets
} else {
	task.Target = opts.Target // 现状不变
}
```

| 改动点 | 影响面 | 破坏性 |
|---|---|---|
| `model.Task` 加 `Targets []string` | 全局，但 `omitempty`，零值不影响现有序列化 | 无 |

**结论：完全增量式改动，旧用法零改动。**

## 五、明确不做的事情（边界）

- ❌ 不给 `Runner` 接口加 `RunBatch` 方法或新建 `BatchRunner` 接口——在 `Execute` 层拦截即可，不应该让 8 个实现类都感知"批量"这个概念。
- ❌ 不在 `Task.Target` 字段上做"逗号分隔自动识别"的隐式魔法——批量与否必须由显式字段/flag 表达，不能靠猜。
- ❌ 不现在就打通 Master 协议层的批量下发——`neoMaster` 的 `TaskGenerator` 已有 chunk 拆分机制，本方案只解决 Agent 单机 CLI 场景的体验缺口，两者不冲突，除非后续明确要求扩展。

## 六、待对齐的细节问题

> 以下问题逐个与用户确认，确认一项、补充一项，全部确认后进入实施文档编写阶段。

### 6.1 目标级并发如何控制？

**已确认结论：新增独立的 `--batch-concurrency` CLI 参数，语义为"目标级并发"，默认给保守值（如 5），用户可自行调大/调小。**

讨论过程与排除的方案：

| 方案 | 说明 | 是否采纳 |
|---|---|---|
| A：固定小并发，不开放配置 | 简单可控，但完全不给用户调整空间 | 否，最终选 B |
| B：新增 `--batch-concurrency`，默认保守值，用户可调 | 目标级并发是独立于 Scanner 内部并发的新维度，需要独立参数表达 | **✅ 采纳** |
| C：复用各 Scanner 已有并发参数（如 `alive` 的 `--concurrency`） | **已排除**——语义会打架。例如 `alive --concurrency 1000` 现有含义是"单个 CIDR 网段内 IP 探测并发"，若用同一个参数身兼"多个网段之间的并发"，粒度完全不同，会让用户和维护者搞不清参数到底管哪一层，属于方案中明确要否决的"隐式魔法" |
| D：默认不限，完全交给 Scanner 内部 QoS 限流器和 Go runtime 兜底 | 有失控风险（目标级并发 × Scanner 内部并发是乘法关系，叠加可能打爆目标网络或本地资源），且与 `WebScanner` 现有"默认保守、限流器兜底"的设计哲学不一致 | 否，最终选 B |

**落地要点**：
- `--batch-concurrency` 是 `runner.runBatch` 层面的新参数，与 Scanner 内部原有的并发/限流参数（`alive` 的 `--concurrency`、`WebScanner` 的 QoS `AdaptiveLimiter`）是两个独立维度，互不冲突、允许叠加存在（乘法关系，用户需自行评估总并发量）。
- 该参数只在 `len(task.Targets) > 0`（即批量模式）时生效，单目标模式不受影响。
- 默认值待定（暂定参考 `WebScanner` 现有 QoS 默认并发 5 作为基准，具体数值在实施阶段可结合各 Scanner 的资源消耗特点微调，非本方案关注重点）。

### 6.2 批量场景下"运行时错误"与"业务扫描结论"如何区分处理？

**前置概念澄清（讨论中被纠正的关键点）**：扫描存在两个完全不同层次的"失败"，不能混为一谈：

| 层次 | 举例 | 归属 | `TaskResult.Status` |
|---|---|---|---|
| 层次一：业务扫描结论 | IP 不存活、端口未开放、无匹配指纹 | 正常的、有价值的扫描结果，**不是错误** | `success`（任务正常执行完，结论就是"阴性"） |
| 层次二：运行时错误 | 网络不可达、DNS 解析失败、超时被取消、程序 panic | 扫描动作本身没能完成，拿不到任何业务结论 | `failed`，`Error` 字段有内容 |

本节只讨论**层次二**：批量场景下，若干目标因运行时错误产不出正常结果时，`RunnerManager.Execute` 整体应该如何返回。

**已确认结论**：

1. **`error` 返回策略**：只有当**全部目标**都因运行时错误失败（一条有效 `TaskResult` 都拿不到）时，`Execute`/`runBatch` 才返回非 nil 的 `error`；只要有至少一个目标成功，整体返回 `nil error` + 已有的结果集。
   - 与 `WebScanner.Run` 现有"多端口并发探测"的容错模式保持一致（`len(results)==0 && len(errs)>0` 才整体报错），批量目标场景是同一个"fan-out + 局部容错"模式的重复应用，语义统一，用户经验可复用。
   - 避免了让现有 8 个 `cmd/agent/scan/xxx.go` 的 `RunE`（普遍是 `if err != nil { return err }` 的简单模式）都要额外处理"error 非空但 results 也有效"的半成功状态，保持零改动兼容。

2. **失败目标不静默消失**：因运行时错误未能产出结果的目标，仍在最终结果列表里生成一条 `TaskResult{Status: TaskStatusFailed, Error: "具体错误信息"}` 占位记录，而不是让该目标从结果列表里悄悄消失。
   - 理由：静默消失比明确报错更危险——用户可能误以为该目标"已扫描且无问题"，而实际上它根本没被成功探测过，这类误判在安全扫描场景中是不可接受的（对应 `00.原子扫描器开发指南` 中"没有实现的功能宁可报错也不能假装成功"的同一条铁律，这里是"没扫成功的目标宁可显式标记失败也不能悄悄消失"）。
   - 该占位记录同时通过 `logger.Warnf` 输出日志，方便运维/审计场景在日志流水中定位失败目标及原因，不强制用户必须打开 JSON/CSV 结果文件才能发现问题。

### 6.3 批量结果如何关联回具体的 Target？

**问题背景**：`runBatch` 把所有目标的 `TaskResult` 合并成一个大列表返回后，现有 `TaskResult` 结构本身不带目标信息：

```57:64:c:/mytools/code/go/NeoScan/neoAgent/internal/core/model/task.go
type TaskResult struct {
	TaskID      string      `json:"task_id"`
	Status      TaskStatus  `json:"status"`
	Result      interface{} `json:"result"`
	Error       string      `json:"error,omitempty"`
	ExecutedAt  time.Time   `json:"executed_at"`
	CompletedAt time.Time   `json:"completed_at"`
}
```

大部分业务 `Result`（如 `IpAliveResult.IP`、`WebResult.URL`）自带目标信息，单目标场景下够用。但 6.2 节确认的"失败占位记录"恰恰没有 `Result`（只有 `Error` 字符串），批量场景下使用者无法知道这条 `failed` 记录到底对应哪个 Target。

**讨论过的三个方案及排除原因**：

| 方案 | 说明 | 结论 |
|---|---|---|
| A：`TaskResult` 新增 `Target string`（omitempty） | `runBatch` 统一回填；单目标场景该字段为空、序列化时省略，零影响现状 | **✅ 采纳** |
| B：不动结构体，依赖各 Scanner 的 `Result` 自带字段 | 对 `success` 结果够用，但 `failed` 占位记录没有 `Result`，只能把 Target 拼进 `Error` 字符串里表达，属于用字符串拼接代替结构化字段的补丁式设计，且失败场景恰恰是用户最需要精确定位目标的场景，不能将就 | 否 |
| C：包装成 `BatchResult{Target, *TaskResult}`，批量接口返回 `[]BatchResult` | 会让 `Execute` 出现两种返回类型语义（单目标 `[]*model.TaskResult` vs 批量 `[]BatchResult`），下游消费方（`console.PrintResults`/`reporter.SaveCsvResult`/`saveJsonResult`）现有代码都按 `[]*model.TaskResult` 写死，需要重载两套处理逻辑，违背"批量对下游消费者透明"的设计初衷 | 否 |

**已确认结论**：采用方案 A。`Target` 属于"这条结果是关于谁的"这一层元数据，与 `TaskID`/`Status`/`ExecutedAt` 同属 `TaskResult` 的信封字段，是该结构体现有设计的自然扩展，不是引入新概念。批量模式下由 `runBatch` 统一回填每条结果的 `Target` 字段；单目标模式该字段保持空值，`omitempty` 保证不影响现有 JSON 输出格式。

### 6.4 CLI 层 `--target` 与 `--targets` 的关系，以及落地范围

**问题一：同时传入 `-t` 和 `--targets` 如何处理？**

**已确认结论：合并两者**——`-t` 的值也当作一个目标加入最终的 `Targets` 列表（去重后一起处理），不视为互斥/报错，也不做优先级覆盖。用户可以用 `-t 1.2.3.4 --targets more.txt` 表达"这一个目标 + 文件里的一批目标一起扫"。

**问题二：`--targets` 参数先在哪些命令上落地？**

讨论过的三个方案：

| 方案 | 说明 | 结论 |
|---|---|---|
| A：只落地 `alive`/`web`/`port`/`os` 四个已实现命令 | 这四个命令语义清晰、单目标场景已验证，范围最小可一次性做完 | **✅ 采纳** |
| B：连带 `brute` 一起落地 | `brute` 的批量目标语义是"同一端口/服务，换一批 IP 逐个爆破"，会立刻牵扯出"批量目标 × 批量凭据要不要做笛卡尔积""并发怎么控制""找到一个成功凭据后要不要继续爆破其他目标"等 `brute` 专属复杂度，与本方案"通用批量框架"的范围不符，容易失焦 | 否，作为技术债记录（见下） |
| C：8 个命令的 CLI flag 全部一次性加上 | `dir`/`subdomain`/`vuln` 三个 Scanner 尚未实现，现在加 `--targets` flag 只会得到"参数能传但一定报错"的命令，没有实际收益，是为了表面完整性做的过度设计 | 否 |

**已确认结论：采用方案 A**。`--targets` 本次只加在 `alive`/`web`/`port`/`os` 四个命令上。

**遗留事项 / 技术债（后续接入时需重新审视，不在本次范围内）**：

1. **`brute` 命令的批量接入**：`brute` 的参数是 `Target`（单 IP）+ `Port`（单端口）+ `Service`（单服务）+ `Users`/`Passwords`（已支持批量凭据列表）的四元组合。若未来给 `brute` 加 `--targets`，需要专门设计以下问题，不能直接套用本方案的通用 `runBatch`：
   - 批量目标是否要求所有目标共用同一个 `Port`/`Service`（现实中合理，因为爆破前提是已知端口和服务类型一致），还是要支持"每个目标各自不同端口/服务"（复杂度显著提高，且现有 `BruteScanOptions` 结构不支持）。
   - 批量目标场景下，`--all`（尝试所有凭据）与"默认找到一个成功凭据即停止"的语义，停止范围是"某一个目标试出一个凭据就停止该目标"，不应误扩大为"全局只要有一个目标试出结果就停止其余目标"。
   - 目标级并发与凭据级并发（爆破字典的用户名/密码组合数量本身就可能很大）叠加后的总并发量评估，风险高于 `alive`/`web`/`port`/`os` 四个命令。

2. **`dir`/`subdomain`/`vuln` 三个命令**：目前 Scanner 未实现，CLI 直接报 `not implemented yet`，本次不加 `--targets` flag。待对应 Scanner 真正实现、接入 `RunnerManager` 之后，由于批量能力是在 `RunnerManager.Execute` 层统一提供的通用能力，这三个命令接入 `--targets` 只需照抄 `alive`/`web`/`port`/`os` 已验证的 CLI flag 接入模式（4.3 节 `common.go` 的 `loadList` 复用方式），成本很低，届时按本方案模式直接接入即可，无需重新设计批量框架本身。

### 6.5 批量结果的落盘与终端展示

**问题一：JSON/CSV 输出文件（`--oj`/`--oc`）是否需要按目标拆分？**

**已确认结论：不拆分**，批量模式下仍写入同一个文件，靠 6.3 节新增的 `TaskResult.Target` 字段区分每一行/每条记录属于哪个目标。与现有单目标场景 `--oj`/`--oc` 的用法完全一致，`saveJsonResult`/`reporter.SaveCsvResult` 不需要做任何改动——它们本来就是把 `[]*model.TaskResult` 整体序列化，批量只是这个切片元素变多，形状不变。

**问题二：终端打印是否需要汇总统计？**

**已确认结论：需要**。批量模式下（`len(task.Targets) > 0`），在 `console.PrintResults` 现有的结果表格输出之后，追加一行汇总统计，形如：

```
共 100 个目标，97 成功，3 失败
```

统计口径复用 6.2 节确认的 `Status` 语义：以每个目标是否产出至少一条非 `TaskStatusFailed` 的记录作为"成功/失败"的判定依据（具体聚合逻辑在实施文档中细化，比如同一目标可能产出多条结果——如 `WebScanner` 一个目标多端口——需要按目标去重计数，而不是按结果条数计数）。

### 6.6 Master 侧多目标丢弃问题：历史原因溯源

**背景**：分析 `task_to_core.go` 时发现，`clientModel.Task.InputTarget` 反序列化出的 `[]clientModel.Target` 明明是数组，但翻译逻辑只取了 `targets[0]`：

```27:34:c:/mytools/code/go/NeoScan/neoAgent/internal/service/adapter/task_to_core.go
targetValue := ""
meta := make(map[string]interface{})
if len(targets) > 0 {
	targetValue = targets[0].Value
	for k, v := range targets[0].Meta {
		meta[k] = v
	}
}
```

同时确认了 `neoMaster` 侧 `TaskGenerator.GenerateTasks` 会按 `chunk_size`（默认 50）把多个目标打包进同一个 `AgentTask.InputTarget`：

```123:133:c:/mytools/code/go/NeoScan/neoMaster/internal/service/orchestrator/core/scheduler/generator.go
for i := 0; i < len(targets); i += chunkSize {
	end := i + chunkSize
	...
	chunk := targets[i:end]
	targetsJSON, err := json.Marshal(chunk)
```

即 Master 协议本身天然支持批量下发，但 Agent 翻译层退化成只处理第一个目标，其余目标被静默丢弃，无日志无报错。

**历史原因溯源（通过 `git log` 追查，非臆测）**：

1. `internal/model/client/task.go`（2026-02-01，提交 `852241f3`，"实现与 Master 的完整通信协议"）首次引入 `Task.ToCoreTask()` 方法时，代码作者留下了明确注释：

   ```56:57:c:/mytools/code/go/NeoScan/neoAgent/internal/model/client/task.go
   // 假设一个任务对应一个主要目标，或者需要在CoreTask中处理多个目标
   // 这里简化处理，取第一个目标
   ```

2. 2026-01-30 提交 `b02644fe`（"重构任务适配器以使用新的客户端模型"）把这段逻辑从 `client/task.go` 搬到独立的 `internal/service/adapter/task_to_core.go`，代码原样照搬，但**这两行关键注释在搬迁过程中丢失**，导致现在的 `task_to_core.go` 只剩下裸代码，后来者无法辨别"取第一个"是遗留技术债还是既定设计。

**结论**：这是开发者在早期通信协议联调阶段（`model.Task` 尚无批量能力）主动选择的、有明确文字记录的简化方案，不是笔误或临时疏漏；作者当时已经预见到"需要在 CoreTask 中处理多个目标"才是完整方案。本方案新增的 `model.Task.Targets` 字段，恰好补上了当年缺失的承接能力，修复 `task_to_core.go` 是在完成这项已被识别但搁置的工作，不是无依据的新增判断。

**待办**：6.2 节确认的止血修复（`task_to_core.go` 改为收集全部 `targets` 到 `model.Task.Targets`）保持独立优先级，与本节溯源结论一致，修复时建议把丢失的历史注释语境以某种形式保留（如指向本方案文档），避免未来重构再次丢失这段上下文。
