**背景**：即将执行步骤 5 时，复盘原方案 `IsCDN bool` + `CDNProvider string` 两个标量字段的设计，发现一个结构性问题——CDN 识别和路线图里明确会做的 WAF 识别，本质是同一类问题："这个 Web 目标背后站着哪个/哪些边缘网络组件"。用标量字段对应类型，意味着 WAF 落地时要再加 `IsWAF`/`WAFProvider`，以后每加一种边缘组件类型（反 DDoS、云防火墙等）就要再加一对字段，且这种设计从根上无法表达"同一目标同时命中 CDN 和 WAF"的真实情况（Cloudflare 这类厂商 CDN+WAF 二合一非常常见）。这是"用字段数量对应类型数量"的错误建模，不是"以后需要再加"的锦上添花。

**决策**：在 `EdgeComponents` 字段还没写入代码库、零下游依赖的窗口期（唯一的零成本修改时机）完成重构，改为：

同步修改了实施文档步骤 5/6/7 里所有引用 `IsCDN`/`CDNProvider` 的代码示例（`pageData` 结构体、`buildWebResult` 组装逻辑、端到端验收用例的预期 JSON），确保后续按实施文档施工时不会做错。

### [2026-08-01] Web 爬虫与被动分析器：Sprint 6 完成（多端口探测与协议自适应），Phase 5.1 全部收尾
**背景**：本 Sprint 修的三个问题**都不是新需求**，是 `Run()` 现有代码里一直存在、Sprint 0-5 单元测试未覆盖到的真实 bug——之前的测试全部用 `httptest.NewServer`（单端口、单协议），没有覆盖"一个目标同时有 HTTP/HTTPS 两个独立服务"、"协议猜错"、"真实 Chromium 浏览器遇到协议不匹配时的行为"这三种场景，都是在对真实站点（`10.201.28.126`、内网多端口服务）做 Sprint 5 收尾验证时暴露出来的。

1.  **缺陷一：`--ports` 传范围字符串时从未真正探测多个端口**。`normalizeURL` 拿到 `"80,443"` 这种整串范围字符串时，既不等于 `"80"` 也不等于 `"443"`，直接落进 `default` 分支猜成 `http`，"多端口探测"从未真正发生过。**修复**：把 `Run()` 拆分成"编排层 + 单端口执行层"——原 `Run()` 函数体原样保留，改名为 `runOnePort`（自己算 `targetURL`、自己获取 QoS 令牌）；`Run()` 本身变成纯编排：`parsePortsForScan` 解析并去重端口列表 → 用 `sync.WaitGroup` + 带缓冲 channel 并发调用 `runOnePort`（每个 goroutine 独立 `recover()`）→ 汇总结果。单个端口失败不连累其他端口：只有全部端口都失败（`len(results)==0 && len(errs)>0`）才用 `errors.Join` 把错误拼接后返回顶层。`task.PortRange` 为空字符串时保持 Sprint 0-5 现状行为（只探测一次），向后兼容不break老调用方式。

2.  **缺陷二：非标准端口猜错协议后没有任何纠错机会**。对 `10.201.28.126:9000`（实际是 HTTPS）不显式指定协议时，`normalizeURL` 猜成 `http://`，拿到的是对端返回的 400（"Client sent an HTTP request to an HTTPS server."）——这是**拿到了响应但协议不对**的场景；目标沉默失败（超时/EOF/连接重置）时则完全拿不到任何响应，错误文本因平台/Go版本/对端实现而完全不一致。**设计方案在这里推翻重来过一次**：最初设想是用 `errors.As` 区分 TCP dial 阶段失败与 TLS 握手/读取阶段失败，只在后者触发一次协议翻转重试，这个方案被缺陷三的真实环境验证证伪。**最终方案**参考 `httpx` 的做法：协议不确定时不去猜错误属于哪一类，而是 http/https **直接并发各发一次**，用响应质量客观排序（`pickBestFetchOutcome`：成功且非400 > 成功但400 > 失败）选出更可信的结果，新增 `isProtocolGuessed`（判断协议是猜的还是用户显式指定的）、`flipProtocol`（翻转 URL scheme）、`fallbackFetchBestProtocol`（双发外壳）三个组件。用户显式指定协议时永远只发一次，不做自作主张的纠正。

3.  **缺陷三（真实 Chrome 环境下才暴露）：go-rod 路径会把协议不匹配的 400 响应当成"扫描成功"**。这是实现缺陷二修复方案时，在装有真实 Chrome 的机器上联调才发现的——CI/无 Chrome 的开发环境会直接走 `fallbackFetch` 降级路径，缺陷三完全不会触发。实测发现：对一个只监听 TLS 的服务发 `http://` 明文请求，Chromium **不会**导致 `page.Navigate`/`WaitLoad` 报错，根因是 Go 标准库 `crypto/tls` 服务端在握手阶段识别出明文请求后，会在同一条 TCP 连接上直接写回一段合法的 HTTP/1.0 400 文本响应——这是对端真实吐出的、状态码明确的响应，不是 Chromium 编造的错误页，`NetworkResponseReceived` 正常触发，`homeStatusCode=400`、`homeBody` 非空，原有唯一判断 `if homeBody == ""` 完全绕过，协议错误被当成扫描成功返回给用户。**修复**：`runOnePort` 里把判断条件统一为 `needsVerification := homeBody == "" || (protocolGuessed && homeStatusCode == http.StatusBadRequest)`，命中后把 go-rod 已有结果包装成 `fetchOutcome`（`homeBody==""` 时打一个哨兵 `err` 让它天然垫底）与 `fallbackFetchBestProtocol` 的双发结果一起送进 `pickBestFetchOutcome` 统一比较，不给"go-rod 完全失败"和"go-rod 拿到疑似协议错误的 400"写两套分支逻辑。fallback 侧胜出时，go-rod 的 RichContext/截图/favicon 一并丢弃（避免"错误协议截图 + 正确协议正文"的不自洽组合）；go-rod 侧胜出（比如两个协议下都是 400）则维持原样，保留只有 go-rod 才有的更完整数据。

4.  **测试**：新增 `web_scanner_multiport_test.go`（`TestParsePortsForScan` 纯函数表驱动 + `TestWebScanner_MultiPort_ScansEachPortIndependently` + `TestWebScanner_MultiPort_PartialFailureStillReturnsSuccessfulResults`）与重写后的 `web_scanner_protocol_test.go`（`TestFlipProtocol`/`TestIsProtocolGuessed`/`TestPickBestFetchOutcome` 三个纯函数单测 + `TestProtocolDualFetch_HTTPGuessedButHTTPSOnly_PicksHTTPS`/`TestProtocolDualFetch_ExplicitProtocolHint_NeverDualFetches`/`TestProtocolDualFetch_TCPUnreachable_FailsFast`/`TestProtocolDualFetch_BothFail_ReturnsError` 四个端到端集成测试，其中显式协议场景的断言方式特别调整为"检查返回的 400 状态码和标题"而不是"检查 Run() 是否返回 error"——因为 400 响应本身就是一次成功的抓取，不该也不会让顶层返回 error）。
5.  **验收结果**：`go build ./...`、`go vet ./internal/core/scanner/web/...`、`go test ./internal/core/scanner/web/... -race` 全部通过（`go vet ./...` 对全仓库会报出与本次改动无关的 `docs/references/` 第三方参考代码告警，不在验收范围内）。至此 **Phase 5.1（Web 爬虫与被动分析器）Sprint 0-6 全部验收完毕，完全收尾**。同步更新了实施文档（记录方案推翻重来的完整决策过程）与 `internal/core/scanner/web/README.md`（第 1.4 节补充多端口/协议双发能力说明，第 5 节补充 `runOnePort`/`fallbackFetchBestProtocol` 位置说明）。

### [2026-07-31] 真实站点回归测试：修复 `crawler.Options.SameHostOnly` 零值陷阱导致的同源限制线上失效
**背景**：对 `https://www.baidu.com` 跑 `scan web` 做 Sprint 5 落地后的真实站点验证时，BFS 结果里出现了 `weibo.com`、`qq.com`、`taobao.com`、`bilibili.com`、`12306.cn` 等大量与种子完全无关的外部域名——**同源限制（Same-Origin Scope）在生产环境从未生效过**。
1.  **根因**：`crawler.Options` 用 `SameHostOnly bool` 表达"是否限制同源"，注释写"默认 true"，但 Go 的 `bool` 零值是 `false`，`New()` 只对 `MaxDepth` 做了零值兜底，没有对 `SameHostOnly` 做同样处理。生产环境唯一调用点 `web_scanner.go`（`crawler.Options{MaxDepth: depth}`）以及架构方案文档里的示例代码，全部只传了 `MaxDepth`，导致 `SameHostOnly` 恒为 `false`，同源判断 `inScope()` 直接放行一切链接。专门为这条逻辑写的单测之所以一直"通过"，是因为测试自己用 `newTestOptions()` 显式传了 `SameHostOnly: true`，测试用的构造方式和生产环境的真实构造方式完全不是同一条路径，测试盲区掩盖了真实 bug。
2.  **修复**：反转字段语义，删除 `SameHostOnly`，改为 `AllowCrossHost bool`（默认 `false` = 同源限制生效）。这样零值 `Options{}` 本身就是安全的默认行为，不再需要调用方"记得"显式传参，也不需要在 `New()` 里额外写零值兜底逻辑——从数据结构层面让这类 bug 不可能再发生。生产环境调用点 `web_scanner.go` 无需任何改动。
3.  **测试补强**：新增 `TestCrawl_SameHostOnlyByDefault`，用 `Options{MaxDepth: 2}`（和生产环境一模一样的构造方式，不做任何额外配置）复现并验证同源限制生效；新增 `TestCrawl_AllowCrossHost` 验证显式开启跨域后能正常跨域爬取。同步修正了架构方案文档 `Web爬虫与被动分析器架构方案-sonnet5-v3.0.md` 里的过时示例代码。
4.  **验证**：`go build ./...` 通过；`go test ./internal/core/scanner/web/...` 全部 28 个用例通过；对 `www.baidu.com` 重新实测，BFS 结果全部收敛在 `baidu.com` 子域内，未再出现外部域名。

### [2026-07-31] Web 爬虫与被动分析器：Sprint 3 完成（被动泄露检测）
**核心交付**:
1.  **`leak.go`（新增）**: 实现 `DetectLeaks(body) []model.LeakInfo`，内置 4 条正则识别规则（`defaultLeakRules`，用 slice 而非 map 保证命中顺序稳定，便于测试断言）：
