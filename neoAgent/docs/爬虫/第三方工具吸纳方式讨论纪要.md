# 第三方工具吸纳方式讨论纪要

> 讨论背景：NeoScan 设计之初就规划了调用第三方工具的能力，但"吸纳标准"一直没有清晰文字化——面对 httpx、xray 这类工具，到底是内化其扫描原理重写成 Go 代码，还是直接调用其二进制？本文是这次讨论的过程记录与结论沉淀。
>
> 关联文档：
> - [`docs/第三方扫描工具调用.md`](../第三方扫描工具调用.md)（**既有决策文档，本次讨论的结论与其完全对齐，互为印证**）
> - [`docs/爬虫/httpx与xray参考价值评估.md`](./httpx与xray参考价值评估.md)（本次讨论的直接触发点）

---

## 一、问题的提出

NeoScan 项目里已经出现了两条互不相干的"接入外部能力"路线，但从未被写成一条清晰的标准：

1. 内化路线：读懂目标工具的检测/扫描原理，用 Go 重写一遍逻辑，变成 NeoScan 自己的代码。
2. 二进制路线：不碰实现细节，直接 fork 子进程调用目标工具的可执行文件，解析其 stdout/JSON 输出。

httpx、xray 恰好是这次触发讨论的两个具体案例，因此以它们为例展开分析。

---

## 二、先看代码里已经发生过的事，而不是凭空定标准

在动手分析"该怎么做"之前，先审查了代码库现状，发现**这两条路线在 NeoScan 历史上都已经真实存在过**，而不是一个纯理论问题：

### 2.1 活代码：`internal/core/factory` —— 内化路线的产物

`alive_factory.go`、`port_factory.go`、`os_factory.go`、`brute_factory.go`、`web_factory.go`，是当前 `PipelineRunner`/`ServiceDispatcher` 真实调用的主干代码。ICMP/ARP 存活探测、Nmap 探针协议、15+ 种爆破协议，全部是内化重写，产出统一的 `model.Task`/`TaskResult`。这条路线撑起了 `开发进度.md` 里阶段一到阶段四的全部交付。

### 2.2 死代码：`internal/executor` —— 二进制路线的失败实验

`base/`（27 方法的 `Executor` 接口）、`nmap/`、`nuclei/`、`masscan/`、`system/`、`manager/`，试图给"调用外部二进制工具"建一套通用抽象（README 里称为 "Brain & Muscle Fusion" 架构）。但实测发现：

- **`cmd/` 目录下没有任何一处引用 `internal/executor`**，也就是说这套代码从未接入过主干流程，是彻底的死代码。
- 内部实现质量也印证了"过度设计"的判断：`nmap_executor.go` 用 `strings.Fields` 手撕 nmap 文本输出，连端口号都没转成 `int`（`Port: 0, // TODO: 转换为int`）；`Pause`/`Resume` 对一次性命令行工具没有意义，两个实现都是直接 `return fmt.Errorf("not supported")`——这是"为了满足接口而存在的死方法"。
- `Executor` 接口试图用运行时类型断言（`task.Config["targets"].([]interface{})`）去兼容"任意外部工具"，是用动态类型的方式在写静态类型语言，是最坏味道的代码之一。

**结论**：这不是一个需要"制定新标准"的问题，是一个**已经有历史事故、需要先承认失败再定策略**的问题。`internal/executor` 建议直接删除，不要留着继续误导后来者以为这是官方路线。

---

## 三、真正的判断标准是什么

翻遍 NeoScan 过去所有真实决策（存活探测、端口服务、爆破协议、Web 指纹），从未真正纠结过"内化 or 调二进制"，分界线一直很清楚，只是没被写下来：

> **能力本身是否需要与自己的调度器（并发、限流、AdaptiveLimiter、Pipeline 优先级、`context.Context` 取消语义）深度融合？**
>
> - **是** → 内化重写。一旦 fork 子进程，就失去了对其内部并发/限流/取消的控制权——nmap 子进程不理解 `AdaptiveLimiter`，也不会响应 Pipeline 的优先级取消信号。
> - **否**，且目标工具本身是一个自成体系、维护成本极高、业界已有权威实现/生态的独立能力（如 Nuclei 的海量社区模板）→ 调用其二进制或 SDK/Library，没有理由重新发明一个与其生态竞争的轮子。

这个标准与 [`docs/第三方扫描工具调用.md`](../第三方扫描工具调用.md) 中"拒绝调用 / 谨慎调用 / 必须集成"三分表格的结论完全一致，本次讨论是对该文档判断逻辑的补充论证，而非另立标准。

### 3.1 httpx 的结论

不重写整个 httpx，也不调用它的二进制。评估文档（[`httpx与xray参考价值评估.md`](./httpx与xray参考价值评估.md)）给出的正确路径是：

- 参考它的 CDN 识别策略（`skipCDNPort`）和基于真实 DOM 解析的 title 提取方式，属于"抄思路，自己写 Go 实现"。
- 指纹识别不建议继续手工扩充自研 JSON 规则表，而应直接把 `wappalyzergo` 作为 **Go 依赖库**引入——这是"内化"，内化的是社区维护的规则数据和匹配算法，不是内化整个 httpx 命令行工具，也不是 fork 它的二进制。

### 3.2 xray 的结论

同理不装二进制（其核心引擎本就闭源，也调不了）。抄它的 PoC YAML 三段式 DSL 结构（`set/rules/expression`），自己用 `expr-lang/expr` 实现表达式引擎和执行调度——做的是"漏洞验证能力"这个 NeoScan 的核心竞争力，必须内化。

### 3.3 Nuclei 是当前唯一站得住脚的"调用外部能力"候选

它的模板生态是数万条社区持续维护的规则，重新发明它毫无意义，属于标准里"生态壁垒极高"的例外。但即便如此：

- **不需要**参照 `internal/executor` 那套 27 方法接口。
- 优先评估 Nuclei 官方 Go SDK（`github.com/projectdiscovery/nuclei/v3/lib`）直接库调用，输出直接是结构化 Go struct，比 fork 子进程 + 逐行解析 JSON Lines 更优、更省心。
- 如果库引用导致二进制体积过大或依赖过重，才退化为下载/调用独立二进制，这一优先级顺序与 [`第三方扫描工具调用.md`](../第三方扫描工具调用.md) 第 3.2 节完全一致。

## 四、如果确实要走"调用外部二进制"路线，该怎么落地

若某个工具最终判定为"调用外部能力"（如 Nuclei 的兜底方案、或未来的 Hydra 冷门协议按需调用），落地方式应遵循：

1. **简化数据结构**：不需要 27 方法的 `Executor` 接口，一个工具只需要两个函数——`Build(target, opts) (cmd, args []string)` 和 `Parse(output []byte) ([]model.XxxResult, error)`，直接复用 `internal/core/model` 已有的结果结构体，不要再造一套平行的结果模型。
2. **消除特殊情况**：不要给命令行工具设计 `Pause`/`Resume`/`HealthCheck`/`GetMetrics` 这类"进程管理"语义，`context.Context` 天然就是超时/取消/暂停问题的答案，`exec.CommandContext(ctx, ...).CombinedOutput()` 足矣。
3. **直接接入现有主干**：新工具挂进 `internal/core/factory`，产出统一走 `model.Task`/`TaskResult`，复用现有 `PipelineRunner`/`AdaptiveLimiter` 调度体系，不要另起一个平行的 `Executor` 世界。
4. **零破坏性**：现有 `factory` 体系不应因为接入新工具而发生任何改动。

## 五、附：为什么不参考 AI 大模型的 Function Calling / MCP 协议

讨论过程中曾考虑借鉴大模型生态的 Function Calling 和 MCP（Model Context Protocol）协议来设计 NeoScan 的工具调用架构，结论是**不适用，属于用协议设计解决一个并不存在的问题**：

- **Function Calling** 解决的是"LLM 这种不确定性的自然语言输入源，如何被翻译为一次确定性函数调用"，核心前提是调用方（模型）可能产生幻觉参数、选错函数，需要 JSON Schema 强约束兜底。NeoScan 的调用方是自己的 Go 代码，编译期就明确要调用哪个 Scanner、参数是什么强类型值，不存在"意图不确定"这个前提。
- **MCP** 解决的是"客户端与工具服务端在编译期互不知道对方存在，需要运行时动态发现、握手、声明能力"的场景（比如用户今天装了 3 个 MCP Server，明天又装 2 个）。NeoScan 的 Pipeline 调度在编译期就写死了"扫完端口派发给 web/vuln/brute"，不需要运行时"问一遍你有什么能力"。
- 如果强行引入，会把 MCP 那种"参数即弱类型 JSON（`json.RawMessage`）+ 运行时能力发现"的思维带进来，这正是 `internal/executor` 里 `task.Config["targets"].([]interface{})` 这类代码的病根——本次讨论恰好在批判这种模式，不应该用另一套包装再犯一次同样的错误。
- 唯一值得抽取的是"能力声明与能力执行分离"这个设计精神，而这一点 `factory` 模式的 `GetTaskSupport()` 已经隐含做到，不需要重新学一套协议才能获得。

若未来 NeoScan 真的要做"运行时动态插拔第三方扫描插件"（这是 MCP 场景里唯一还算沾边的部分），那是一个完全独立的产品定位问题，且现阶段连 Nuclei 这一个外部能力都还没真正接入主干，讨论插件生态属于给还没盖好地基的房子设计电梯，本末倒置，不应现在展开。
