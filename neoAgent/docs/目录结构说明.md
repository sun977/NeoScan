# neoAgent 核心代码目录结构说明

> 最后更新日期：2026-08-07
> 对应代码版本：v2.11.0（`internal/pkg/version/version.go` 中 `Version` 常量）

本文档详细说明了 `neoAgent` 核心代码 (`internal/core`) 和 CLI 入口代码 (`cmd/agent`) 的目录结构及其设计意图。其余模块（`internal/service`、`internal/handler`、`internal/executor`、`internal/app` 等）不在本文档范围内，各自目录下有独立的 README/说明文档。

## 1. 核心业务逻辑 (`internal/core`)

`internal/core` 是 neoAgent 的心脏，是一个**完全独立、可复用**的扫描引擎模块，不依赖任何上层应用逻辑（CLI/Server），包含了所有原子扫描能力、任务调度、结果输出和网络基础设施。它遵循 **高内聚、低耦合** 的设计原则，各模块职责分明。更完整的架构说明见 [internal/core/README.md](../internal/core/README.md)。

### 目录结构概览

```
internal/core/
├── factory/         # 全局能力工厂（统一实例化入口）
├── lib/             # 底层基础设施（网络、浏览器）
├── model/           # 数据模型定义
├── options/         # 任务参数解析与校验
├── pipeline/        # 编排模块（scan run 全流程串联）
├── reporter/        # 结果上报与输出
├── runner/          # 任务调度与执行器
└── scanner/         # 具体扫描能力实现
```

### 1.1 `factory/` (全局能力工厂)
作为 Agent 核心能力的**唯一构建入口**，解决"能力的构建"与"能力的使用"分离的问题，确保 CLI 模式（`runner/manager.go`）和 Pipeline 编排模式（`pipeline/auto_runner.go`）拿到的 Scanner 实例配置完全一致。
- `alive_factory.go`: `NewAliveScanner()`，IP 存活扫描器。
- `port_factory.go`: `NewPortScanner()`，端口服务扫描器（TCP Connect + Gonmap 指纹）。
- `os_factory.go`: `NewOsScanner()`，OS 识别扫描器（多引擎并发竞速）。
- `brute_factory.go`: `NewFullBruteScanner()`，注册了全部 15+ 种协议的弱口令爆破扫描器。
- `web_factory.go`: `NewWebScanner()`、`NewApiScanner()`，Web 综合扫描器 / API 接口扫描器。
- 详细说明见 [factory/README.md](../internal/core/factory/README.md)。

### 1.2 `lib/` (底层基础设施)
- `browser/`: `browser_launcher.go`、`browser_manager.go`，封装 go-rod 无头浏览器的启动与生命周期管理，供 Web 扫描器做真实渲染。
- `network/dialer/`: 统一网络连接层，提供全局超时控制、SOCKS5 代理支持，所有 TCP/UDP 连接必须经此发起。
- `network/netraw/`: 跨平台 Raw Socket 与数据包构建（Linux 完整支持，Windows/macOS 降级），供 ARP/ICMP 探测使用。
- `network/qos/`: 自适应限流器（`limiter.go`）与 RTT 估算（`rtt.go`），是全项目统一的并发/限流基础设施，Web 爬虫、爆破等模块共用同一套令牌桶机制。

### 1.3 `model/` (数据模型)
定义了系统中最基础的数据结构，是各模块间通信的通用语言。
- `task.go`: 定义了 `Task`（任务输入，含 `Type`/`Target`/`Params`/`Timeout` 等字段）和 `TaskResult`（任务输出）结构体。
- `result_types.go`: 定义了各具体扫描类型的 Result 结构（如 `IpAliveResult`、`WebResult`），以及表格化输出接口。

### 1.4 `options/` (参数层)
负责将 CLI Flags 转换为强类型的配置结构体，每种扫描类型一个文件，统一提供 `Validate()` 和 `ToTask()` 方法。
- `types.go`: 定义通用的 Option 接口。
- `output.go`: 全局输出参数定义（`--oc`、`--oj`）。
- `proxy.go`: 代理相关参数定义。
- `scan_alive.go` / `scan_port_service.go` / `scan_os.go` / `scan_web.go` / `scan_api.go` / `scan_brute.go` / `scan_vuln.go` / `scan_dir.go` / `scan_subdomain.go`: 对应各扫描子命令的参数结构体。
- `scan_run.go`: `scan run` 全流程命令的参数结构体（串联多个原子扫描器）。

### 1.5 `pipeline/` (编排层)
只服务于 CLI 的 `scan run` 全流程命令，把独立的原子扫描能力串联成有逻辑的执行流（漏斗式过滤：存活 → 端口 → 服务 → OS → \[爆破\] → 报告）。
- `auto_runner.go`: `AutoRunner`，通过 Factory 获取各扫描能力并依次调度。
- `dispatcher.go`: 任务分发逻辑。
- `target.go`: 目标生成器（CIDR/IP 范围展开）。

### 1.6 `reporter/` (输出层)
负责处理任务执行结果的展示和存储。
- `interface.go`: 定义 `Reporter` 接口和 `TabularData` 接口。
- `console.go`: `ConsoleReporter` 实现，负责将结果渲染为 CLI 表格。
- `csv.go`: CSV 文件输出实现。

### 1.7 `runner/` (调度层)
负责任务的统一执行入口、生命周期管理和结果汇总，是 CLI 单命令模式（`scan web`/`scan port` 等）和 Master 集群调度模式共用的调度层。
- `interface.go`: 定义 `Scanner`/`Runner` 接口。
- `manager.go`: `RunnerManager` 实现，通过 **Factory** 统一注册所有可用 Scanner、分发任务、汇总结果。
- `adapter_os.go` / `adapter_service.go`: 部分扫描器接口适配。

### 1.8 `scanner/` (能力层)
包含所有具体的安全扫描逻辑实现，每个子目录是一个独立的原子扫描器，互不依赖。
- `interface.go`: 定义 `Scanner` 统一接口。
- `alive/`: **IP 存活扫描**。`alive.go` 核心逻辑（自动/手动策略选择），`prober.go` 定义探测器接口，`arp_*.go` 按平台实现 ARP 探测，`icmp.go`/`tcp_connect.go` 分别是 ICMP/TCP 探测实现。
- `port_service/`: **端口与服务扫描**。`port_service_scanner.go` 是核心逻辑，`nmap_service/` 子包基于 Nmap 规则库做服务指纹识别（`engine.go`/`parser.go`/`rules.go`/内置 `nmap-service-probes` 规则文件）。
- `os/`: **操作系统识别**。`os_scanner.go` 核心逻辑，`ttl_engine.go`（基于 TTL 的快速猜测）、`service_engine.go`（基于服务 Banner）、`nmap_stack/`（基于 TCP/IP 指纹栈匹配，内置 `nmap-os-db` 规则库）三个引擎并发竞速取最优结果。
- `web/`: **Web 综合扫描**。`web_scanner.go` 是核心逻辑（go-rod 渲染优先、fallback 降级、协议双发选优、CDN 识别、深度爬取触发），`context.go` 负责富上下文/链接/表单提取的胶水代码；`crawler/` 子包是私有的 BFS 深度爬虫实现（`crawler.go` 爬取主循环、`extract.go` 链接与表单提取、`leak.go` 敏感信息被动检测），只服务于 WebScanner，不对外暴露为通用模块。
- `api/`: **API 接口扫描**（骨架阶段）。`api_scanner.go` 目前只有 `Name()/Run()` 骨架，真正的 JS 提取抓取能力待独立实现。
- `brute/`: **弱口令爆破**。`cracker.go`/`dict.go` 是核心框架与字典管理，`protocol/` 子目录按协议逐个实现（SSH、RDP、MySQL、Redis、SMB、MSSQL、Oracle、PostgreSQL、MongoDB、FTP、Telnet、SNMP、Elasticsearch、ClickHouse 等 15+ 种），其中 `protocol/rdp/` 是完整移植的 RDP 协议栈（含 `core`/`protocol/{nla,pdu,sec,t125,tpkt,x224}` 等子模块）。

## 2. CLI 入口 (`cmd/agent`)

`cmd/agent` 是程序的入口，负责处理命令行参数、初始化配置、组装 Core 组件并启动任务。它使用了 `Cobra` 库构建命令树，通过 `viper` 读取配置文件/环境变量。

### 目录结构概览

```
cmd/agent/
├── main.go          # 程序主入口（调用 Execute()）
├── root.go          # 根命令定义（NeoScan-Agent），全局 Flag、日志初始化
├── server.go        # server 子命令（集群 Worker 模式，连接 Master）
├── version.go        # version 子命令（版本/构建信息）
├── proxy/           # proxy 子命令（代理模块）
│   └── root.go
└── scan/            # scan 子命令集（单机 CLI 扫描模块）
    ├── root.go      # scan 父命令，注册全部子命令 + 全局输出 Flag（--oc/--oj）
    ├── alive.go     # scan alive  子命令：IP 存活扫描
    ├── port_service.go # scan port 子命令：端口 + 服务识别（原 service 子命令已合并于此）
    ├── os.go        # scan os    子命令：操作系统识别
    ├── web.go       # scan web   子命令：Web 综合扫描（含 --crawl/--crawl-depth 深度爬取）
    ├── api.go       # scan api   子命令：API 接口扫描（骨架阶段）
    ├── vuln.go      # scan vuln  子命令：漏洞扫描
    ├── dir.go       # scan dir   子命令：目录/文件挖掘
    ├── subdomain.go # scan subdomain 子命令：子域名挖掘
    ├── brute.go     # scan brute 子命令：弱口令爆破
    └── run.go       # scan run   子命令：自动化全流程扫描（串联 alive→port→service→os→[brute]）
```

### 关键文件说明

- **`main.go`**: 极其精简，只负责调用 `Execute()`。
- **`root.go`**: 定义全局 Flag（`--config`、`--log-level`），初始化 Viper 配置与 CLI 日志。
- **`version.go`**: `version` 命令，输出版本号（对应 `internal/pkg/version.Version`）、API 版本、构建时间、Git Commit、Go 版本。
- **`server.go`**: `server` 命令，以集群 Worker 模式运行，可通过 `--master` 连接 Master 集群。
- **`scan/root.go`**: 定义 `scan` 命令及全局持久化 Flag（`--oc` 保存 CSV、`--oj` 保存 JSON），并注册全部子扫描命令。
- **各 `scan/*.go` 子命令文件通用模式**：
  1. 用 `options.New*ScanOptions()` 构造默认参数，绑定对应 CLI Flags；
  2. `Validate()` 校验参数，`ToTask()` 转换为 `model.Task`（`Timeout` 字段也在此处设置，执行阶段的 `context` 超时必须使用这个值，不能在命令文件里另外写死）；
  3. 用 `runner.NewRunnerManager()` 执行任务（内部通过 `factory` 统一构建 Scanner）；
  4. 用 `reporter.NewConsoleReporter()` 输出表格，按需保存 CSV/JSON。

## 3. 设计哲学 (Linus Perspective)

1.  **分层架构 (Layered Architecture)**:
    - **CLI Layer** (`cmd/`) → **Option Layer** (`core/options`) → **Runner Layer** (`core/runner`，经 **Factory Layer** 构建) → **Scanner Layer** (`core/scanner`) → **Network Layer** (`core/lib/network`)。
    - 每一层只知道下一层的存在，严禁跨层调用。

2.  **原子化设计 (Atomicity)**:
    - 扫描能力被拆解为最小原子单元（Scanner），例如 `alive` 负责存活、`port_service` 负责端口与服务、`web` 负责 Web 扫描，互不干扰、互不依赖。
    - `web/crawler` 这类扫描器私有的子能力，明确不下沉为跨扫描器共享的通用模块（详见 `docs/00.原子扫描器开发指南[定稿].md` 中的"原子扫描器隔离原则"）。
    - 这种设计便于测试、维护和组合。

3.  **统一构建 (Factory Pattern)**:
    - 所有 Scanner 的实例化逻辑收敛到 `core/factory`，CLI 单命令模式（`runner.Manager`）和全流程模式（`pipeline.AutoRunner`）共用同一份构建逻辑，避免"两处初始化各写一套、配置逐渐漂移"的问题。

4.  **平台无关性与适配 (Platform Independence)**:
    - 平台差异代码（如 ARP 探测 `scanner/alive/arp_*.go`、Raw Socket `lib/network/netraw/socket_*.go`）被封装在各自模块内部，对外暴露统一接口。
    - 上层逻辑无需关心底层是 Windows、Linux 还是 macOS。

5.  **强类型参数 (Strong Typing)**:
    - 所有的 `map[string]interface{}`（`Task.Params`）最终都会在 `options` 层被转换为强类型的 `Options` 结构体再使用。
    - 拒绝在业务逻辑中传递弱类型的 Map，那是 Bug 的温床。

6.  **数据结构是唯一真相源**:
    - 任务的超时、深度等控制参数只应该在 `model.Task` 里声明一次（如 `Task.Timeout`），执行入口（CLI 命令文件）直接使用它，禁止另起一份写死的数字—— 两份配置各说各话，是"深度爬取参数生效却看起来没生效"这类问题的典型根因。
